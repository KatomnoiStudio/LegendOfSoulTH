## INV-0 — เวลาไม่ใช่ตัวแปรทางเศรษฐกิจ (RATIFIED 2026-08-13)

> **จบด่านเร็วหรือจบด่านช้า รางวัลเท่ากัน รางวัลสเกลตาม base เท่านั้น**

อยู่**เหนือ**ทุกหลักการในเอกสารนี้ ทุกสูตรต้องผ่านข้อนี้ก่อน

1. ไม่มีสูตรรางวัลใดอ่านระยะเวลาที่ผู้เล่นใช้
2. **อัตราแลกเปลี่ยนห้ามอ้างอิงเวลาด้วย** — "gold ต่อชั่วโมง" เป็นผลจากฝีมือผู้เล่น
   ไม่ใช่คุณสมบัติของระบบ
3. เทียบกับโลกจริงต้องเป็น **ราคาปะทะราคา** ไม่ใช่เวลาในเกมปะทะเวลาทำงาน

> **INV-0.a — energy ไม่ใช่ตัวแปรทางเศรษฐกิจ (RATIFIED 2026-08-13)**
> ห้ามให้ระบบพลังงานเข้ามายุ่งกับการตั้งราคาหรือการคาลิเบรตใด ๆ
>
> **เหตุผล**: `regenPerHour` **คือเทอมเวลา** รายได้ที่ผ่าน energy คือรายได้ต่อชั่วโมง
> ใส่หมวกใหม่ — main เคยเสนอ energy เป็นตัวแทนของเวลาที่ "INV-0-safe" ซึ่งเป็นการ
> ลากนาฬิกากลับเข้ามาทางประตูหลัง
>
> energy ยังอยู่ในเกมในฐานะระบบ **pacing** (คุมจำนวนรอบต่อวัน, เติมด้วย gem ได้)
> แค่ไม่ใช่อินพุตของราคา ปรับ regen = ตัดสินใจเรื่องจังหวะการเล่น ไม่ใช่เรื่องค่าเงิน

**สถานะวันนี้: ผ่าน — แต่โดยบังเอิญ** `clearTimeMs` ไหลผ่าน reward pipeline
(`dungeonOrchestrator.ts:115` → `resultFinalizer.ts:69`) แต่ปลายทางมีแค่
`formatDurationMs` (`resultViewModel.ts:71,80`) กับ `battleHistory.durationMs` —
ไม่มีจำนวนรางวัลใดอ่านมัน และ**ไม่มีเทสต์ใดห้ามคนถัดไปต่อสาย**

**กับดัก** สูตร `D` มีเทอม `eDPS = atk × mult / attackCooldownMs` ซึ่งมีหน่วยเป็นเวลา
แต่ `attackCooldownMs` เป็น **สเตตัสของศัตรู** ค่าคงที่ทุกรอบ ต่างจาก **เวลาจบด่าน**
ซึ่งเป็นผลการวัด INV-0 ห้ามอย่างหลัง ไม่ห้ามอย่างแรก

## หลักการ 1 — ดรอปผันผวนตาม base (RATIFIED 2026-08-13)

### P1.1 — base สองฝั่งคืออินพุตเดียวของรางวัล

> **base ของผู้โจมตีกับผู้ถูกโจมตี คืออินพุตเดียว ไม่มีคันโยกรางวัลแยกต่างหาก**

- **ห้ามมีตัวเลขรางวัลเขียนมือที่ไหนเลย** มีเมื่อไหร่ = มีแหล่งความจริงที่สอง
- **บัพศัตรู = จ่ายแพงขึ้นอัตโนมัติ** และลืมไม่ได้ (วันนี้ลืมไปแล้ว: บอส HP 1400 จ่าย 35)
- **อยากให้จ่ายแพงขึ้น ต้องทำให้ยากขึ้น** ไม่มีทางลัด
- **ค่า base มั่วได้ตอนนี้** กฎไม่ได้รอค่าที่ดี พอจูนค่าจริง รางวัลขยับตามเอง

### P1.2 — สูตร `D`

```
REF  = resolveFinalCombatStats('monkey-king', 1)   -> 1180 / 92 / 78
MIT  = ARMOR_MITIGATION = 0.42

spawn = template × ELITE_STAT_MULTIPLIER (ถ้า tier === 'elite')
                 × difficultyMultiplier × enemyHpScale

out(e)    = max(1, REF.atk − MIT × e.def)
swings(e) = e.maxHp / out(e)                 -- ไม่ ceil เพื่อไม่ให้เกิดหน้าผา
mult(e)   = ค่าเฉลี่ย damageMultiplier ของทุกท่าที่ e ใช้ได้
in(e)     = max(1, e.atk × mult(e) − MIT × REF.def)
eDPS(e)   = in(e) / (e.attackCooldownMs / 1000)

D(e)      = swings(e) × eDPS(e)
```

**คูณ ไม่ใช่บวก** — ราคาจริงคือเลือดที่เสียตลอดการฆ่า = (เวลาที่ใช้) × (อัตราที่โดนกิน)
ถ้าบวก ศัตรูถึกแต่ไม่ทำดาเมจ จะมีราคาเท่าศัตรูกระดาษที่ตีแรง

| พจน์               | ที่มา                                                                  |
| ------------------ | ---------------------------------------------------------------------- |
| `0.42`             | `src/game/battle/formulas.ts:2`                                        |
| `2.4 / 1.5 / 1.3`  | `stageConfig.ts` `ELITE_STAT_MULTIPLIER`                               |
| เงื่อนไข elite     | `createRealtimeBattle.ts:61` — **`template.tier`** ไม่ใช่ `combatTier` |
| `damageMultiplier` | `attacks.ts` — melee `1` · elite-slam `1.25`                           |
| `1180/92/78`       | `characters.ts:93` → resolver, level 1 growthSteps = 0                 |

**กับดักที่ทำให้ main คำนวณผิดรอบแรก**: `tier` กับ `combatTier` เป็นคนละฟิลด์ ทั้งคู่มีค่า
`'elite'` ได้ — `demon-captain` เป็น `tier: 'normal'` + `combatTier: 'elite'` อ่านผิดฟิลด์
ทำให้ `D` ของมันพุ่งจาก 139.75 เป็น 457.76 (กลายเป็นตัวเดียวกับ `demon-warlord` เป๊ะ)

### P1.3 — ทุกศัตรูดรอปทั้งสองช่องทาง

> **ไม่มีศัตรูตัวไหนให้แต่ทอง หรือให้แต่ EXP** ความหลากหลาย ("ด่านนี้เน้นทอง") เป็นเรื่องของ
> **ด่านพิเศษที่คูณดรอป** ซึ่งเป็น addon แยก ไม่อยู่ในล็อกนี้

### P1.4 — สัดส่วน EXP:gold = 1 : 1.618 (φ)

> **คงที่ทั้งเกม ทุกศัตรู ทุกด่าน**

**เลือกมา ไม่ได้ derive มา** — ต่างจาก `k_exp` (มาจากโค้งเลเวล) และ `D` (มาจากสเตตัส)
φ ไม่มีที่มาทางเศรษฐศาสตร์ เป็น base ที่ตั้งขึ้นโดยตั้งใจ เขียนครั้งเดียว
**บันทึกไว้เพื่อไม่ให้คนอ่านทีหลังไปตามหาสูตรที่ไม่มีอยู่**

**สัดส่วนไม่ใช่ปุ่มเศรษฐกิจ** ตัวคุมเศรษฐกิจคือขนาดตะกร้า (หลักการ 4) — φ คุมแค่ว่าตัวเลข
ทองควรใหญ่เท่าไหร่เทียบ EXP เป็นเรื่องอ่านง่าย/รู้สึกดี

### P1.5 — `k` ต่อช่องทาง

```
k_exp  = EXP สะสมถึง L* / ΣD(บท 1) = 4,170 / 4,783.5 = 0.8717     (L* = 10, ตาราง Ring-0)
k_gold = k_exp × 1.618                                = 1.41041

exp(รอบ)  = round( k_exp  × Σ D(ตัวที่ฆ่าได้) )      -- ปัดเศษครั้งเดียวตอนจบ
gold(รอบ) = round( k_gold × Σ D(ตัวที่ฆ่าได้) )
```

**สองช่องทางอิสระต่อกัน** ปรับโค้งเลเวลไม่กระทบทอง เพิ่มของขายไม่กระทบ EXP

### P1.10 — อะไรจะพิสูจน์ว่า `D` ผิด

`D` อ้างว่าเป็น "HP ที่ฮีโร่อ้างอิงจ่ายต่อการฆ่าหนึ่งครั้ง" — วัดได้ตรง ๆ: log HP ที่เสียไป
ต่อการฆ่า (`durationMs` มีอยู่แล้วที่ `BattleResultAdapter.ts:73`) เล่น 30+ รอบต่อด่าน
คิด `HP_lost(e) / D(e)` **ทำนาย: ค่าคงที่ค่าเดียวทั้ง 5 ชนิด · ผิดถ้ากระจายเกิน ~1.5 เท่า**

**ห้ามเช็คด้วย correlation** — Pokémon ยุคเขียนมือ correlation กับ BST = 0.898 ทั้งที่
ตรงสูตรเป๊ะแค่ 4.9% (พื้นสุ่ม 2.8%) ยุคที่มีสูตรจริง correlation แทบไม่ขยับ (0.918) แต่ตรง
สูตรเป๊ะ 99.1% **correlation สูงจะบอกว่า "ใช่" ทั้งที่ไม่ใช่**

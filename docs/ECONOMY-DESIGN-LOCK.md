## INV-0 — เวลาไม่ใช่ตัวแปรทางเศรษฐกิจ (RATIFIED 2026-08-13)

> **จบด่านเร็วหรือจบด่านช้า รางวัลเท่ากัน รางวัลสเกลตาม base เท่านั้น**

อยู่**เหนือ**ทุกหลักการในเอกสารนี้ ทุกสูตรต้องผ่านข้อนี้ก่อน

1. ไม่มีสูตรรางวัลใดอ่านระยะเวลาที่ผู้เล่นใช้
2. **อัตราแลกเปลี่ยนห้ามอ้างอิงเวลาด้วย** — "gold ต่อชั่วโมง" เป็นผลจากฝีมือผู้เล่น
   ไม่ใช่คุณสมบัติของระบบ
3. เทียบกับโลกจริงต้องเป็น **ราคาปะทะราคา** ไม่ใช่เวลาในเกมปะทะเวลาทำงาน

> **INV-0.a — energy ไม่ใช่ตัวแปรทางเศรษฐกิจ (RATIFIED 2026-08-13 · ยืนยันด้วยการวัด 2026-08-15)**
>
> **energy ห้ามเป็นตัวแปรในนิพจน์ที่เกมประเมินจริง — รางวัล ดรอป หรือราคา**
> **energy เป็น _ผลลัพธ์_ ของการออกแบบได้ ห้ามเป็น _อินพุต_**
>
> **เหตุผล**: `regenPerHour` **คือเทอมเวลา** รายได้ที่ผ่าน energy คือรายได้ต่อชั่วโมง
> ใส่หมวกใหม่ — main เคยเสนอ energy เป็นตัวแทนของเวลาที่ "INV-0-safe" ซึ่งเป็นการ
> ลากนาฬิกากลับเข้ามาทางประตูหลัง
>
> energy ยังอยู่ในเกมในฐานะระบบ **pacing** (คุมจำนวนรอบต่อวัน, เติมด้วย gem ได้)
> แค่ไม่ใช่อินพุตของราคา ปรับ regen = ตัดสินใจเรื่องจังหวะการเล่น ไม่ใช่เรื่องค่าเงิน

**บรรทัด input/output คือคำเดียวที่เปลี่ยนจากฉบับ 2026-08-13** ฉบับเดิมเขียนว่าห้าม energy
ยุ่งกับ "การคาลิเบรตใด ๆ" ซึ่ง**เข้มกว่าที่เกมไหนบนโลกทำจริง** — ทุกสตูดิโอที่วัดได้คาลิเบรต
ด้วย reward-per-energy **ตอนออกแบบ** Genshin ย้าย Condensed Resin จาก 40 resin/2 ชุด
เป็น 60/3 ชุด แล้วลงที่ **20 resin ต่อชุดพอดี** · Arknights กรอกคอลัมน์ 2,000 แถวที่
**10× sanity ราว 97%** สิ่งที่ห้ามคือ energy เป็น**ตัวแปรที่โค้ดอ่านตอนรัน** ไม่ใช่ห้ามหารดู

### INV-0.a.5 — ที่สำรวจนี้ตอบไม่ได้

**bias ของตัวอย่าง** — agent ออกไป**ล่า** coupling ซึ่ง bias ไป**หา** ข้อยกเว้น ทำให้ 27:1
หนักขึ้น แต่ "0 จาก 28" แปลว่า **หาแบบเจาะจงแล้วไม่เจอ ไม่ใช่ไม่มี**

**ความนิยมของฝั่ง authoring วัดไม่ได้และไม่ได้วัด** ธรรมเนียมตอนออกแบบมองไม่เห็นจาก
ข้างนอกเว้นแต่มี datamine เปิดให้ **เห็นแค่ 2 เกม (Genshin, Arknights)** — พอบอกว่า
ทำได้และไม่พัง ไม่พอบอกว่ากี่เกมทำ

**ลีดเดียวที่ค้าง** Blue Archive ship `LimitedStagePointPerApMin: 3` / `Max: 7`
**ขอบเขต point-ต่อ-AP ตรง ๆ** ทั้งสองสาขา ไม่มีใครหา code path ที่กินมันเจอ
**ถ้ามันทำงานจริง Blue Archive มีเทอม energy ตัวที่สองฝั่งดรอป** ยังไม่นับเข้าผล

**สถานะวันนี้: ผ่าน — แต่โดยบังเอิญ** `clearTimeMs` ไหลผ่าน reward pipeline
(`dungeonOrchestrator.ts:115` → `resultFinalizer.ts:69`) แต่ปลายทางมีแค่
`formatDurationMs` (`resultViewModel.ts:71,80`) กับ `battleHistory.durationMs` —
ไม่มีจำนวนรางวัลใดอ่านมัน และ**ไม่มีเทสต์ใดห้ามคนถัดไปต่อสาย**

**กับดัก** สูตร `D` มีเทอม `eDPS = atk × mult / attackCooldownMs` ซึ่งมีหน่วยเป็นเวลา
แต่ `attackCooldownMs` เป็น **สเตตัสของศัตรู** ค่าคงที่ทุกรอบ ต่างจาก **เวลาจบด่าน**
ซึ่งเป็นผลการวัด INV-0 ห้ามอย่างหลัง ไม่ห้ามอย่างแรก

### P0.6 — `฿ → gem` อัตราเดียวทุกใบ โบนัสอยู่ในของแจก (RATIFIED 2026-08-15)

> **`gem = ฿ × 2` ทุก package ไม่มีข้อยกเว้น · แรงจูงใจซื้อใบใหญ่ย้ายไปเป็นโบนัสครั้งแรกต่อ SKU**

นี่คือ P0.5 ประยุกต์กับเงินจริง — **ส่วนลดซื้อเยอะคือโปรโมชั่นที่ฝังในราคาฐาน** รูปแบบเดียวกับ `d`
เป๊ะ ต่างแค่มันอยู่ฝั่ง ฿ แทนที่จะอยู่ฝั่ง gem

**ที่ ship อยู่ให้อัตราสามค่า**

| package | ที่ ship | ฿/gem  | หลังแก้           |
| ------- | -------- | ------ | ----------------- |
| ฿30     | 60 gem   | 0.5000 | **60** (เท่าเดิม) |
| ฿150    | 320 gem  | 0.4688 | **300**           |
| ฿450    | 980 gem  | 0.4592 | **900**           |

**ทำไมต้องเป็น `฿0.5` ไม่ใช่ค่าอื่น — และมันไม่ใช่การเลือกของ main** `GACHA-RATE-DESIGN-LOCK.md`
§11.8 ใช้ `฿0.5 ต่อ gem` **เป็นตัวหารในการ derive `c`** (`8.01 / 0.5 = 16.02 → 16`)
**อัตรานี้จึงรับน้ำหนัก `c = 16` อยู่** — ปรับอัตราเป็นค่าอื่นเมื่อไหร่ ต้อง derive `c` ใหม่ทันที
(ที่อัตราใบใหญ่ `฿0.4592` จะได้ `c = 17.44 → 17` ซึ่งเป็นการแก้ค่าที่ ratify ไปแล้ว)

**และต้องระบุตรง ๆ ว่าอัตรานี้อยู่ตรงไหนของช่วง: `฿0.5` คือรุ่นที่ _แพงที่สุด_ ในสามใบ**
การปรับให้เท่ากันที่ค่านี้จึงทำให้ใบกลางกับใบใหญ่**แย่ลง** ไม่ใช่ดีขึ้น — เลือกเพราะมันรักษา `c = 16`
ไว้ได้โดยไม่ต้องรื้อ §11.8 **ไม่ใช่เพราะมันใจดีที่สุด** ความใจดีที่หายไปถูกซื้อคืนด้วยโบนัสด้านล่าง

**`gem = ฿ × 2`** เป็นกฎที่ผลิตตัวเลข ไม่ใช่ตารางที่คนพิมพ์ — **package ใบที่สี่ derive ได้ ไม่ต้องเดา**
และนั่นคือสิ่งที่บรรทัดเปิดเอกสารนี้บ่นไว้ตั้งแต่แรก (_"package ทองสามใบ implied อัตราแลกเปลี่ยน
สามค่าต่างกัน 10%"_)

**โบนัสครั้งแรกต่อ SKU** — Genshin (Genesis Crystal) · HSR (Oneiric Shard) · ZZZ ทำรูปนี้
ทั้งสามราย: จ่ายครั้งแรกของแต่ละ SKU ได้ **×2** ครั้งต่อไปได้ราคาปกติ ⚠️ **วัดมาสามเกม ไม่ใช่สามสิบ**
— ตัวคูณ `×2` เป็นค่าที่แนะนำ ไม่ใช่ค่าที่สำรวจยืนยันว่าเป็นบรรทัดฐานทั้งวงการ

ที่ `×2` และซื้อครบสามใบครั้งแรก: `120 + 600 + 1,800 = 2,520 gem` ที่ ฿630 (เทียบสถานะปกติ
`1,260 gem`) **โบนัสอยู่ในของแจก ราคาฐานยังเป็นเส้นตรงเส้นเดียว**

**⚠️ ค้าง: ราคา ฿ จริงต้องผ่านป้ายราคาเดียวตาม CPA s.22** ป้ายต้องบอกให้ชัดว่าอันไหนคือราคาปกติ
อันไหนคือโบนัสครั้งแรก — ดูข้อค้างเรื่องกฎหมายท้ายเอกสาร

### P1.1 — base สองฝั่งคืออินพุตเดียวของรางวัล

### P1.2 — สูตร `D`

```
REF  = resolveHeroLevelStats(REF_HERO, L)     -- L = เลเวลบัญชี (ดู P1.2a)
                                              -- L = 1 -> 1180 / 92 / 78
MIT  = ARMOR_MITIGATION = 0.42

spawn = template × ELITE_STAT_MULTIPLIER (ถ้า tier === 'elite')
                 × difficultyMultiplier × enemyHpScale

out(e)    = max(1, REF.atk − MIT × e.def)
swings(e) = e.maxHp / out(e)                 -- ไม่ ceil เพื่อไม่ให้เกิดหน้าผา
mult(e)   = ค่าเฉลี่ย damageMultiplier ของทุกท่าที่ e ใช้ได้
in(e)     = max(1, e.atk × mult(e) − MIT × REF.def)
eDPS(e)   = in(e) / (e.attackCooldownMs / 1000)

D(e)      = swings(e) × eDPS(e)
```

**คูณ ไม่ใช่บวก** — ราคาจริงคือเลือดที่เสียตลอดการฆ่า = (เวลาที่ใช้) × (อัตราที่โดนกิน)
ถ้าบวก ศัตรูถึกแต่ไม่ทำดาเมจ จะมีราคาเท่าศัตรูกระดาษที่ตีแรง

| พจน์               | ที่มา                                                                  |
| ------------------ | ---------------------------------------------------------------------- |
| `0.42`             | `src/game/battle/formulas.ts:2`                                        |
| `2.4 / 1.5 / 1.3`  | `stageConfig.ts` `ELITE_STAT_MULTIPLIER`                               |
| เงื่อนไข elite     | `createRealtimeBattle.ts:61` — **`template.tier`** ไม่ใช่ `combatTier` |
| `damageMultiplier` | `attacks.ts` — melee `1` · elite-slam `1.25`                           |
| `1180/92/78`       | `characters.ts:93` → resolver, `L = 1` growthSteps = 0                 |
| `REF_HERO`, `L`    | **P1.2a** — ไม้บรรทัดอ่านเลเวล ไม่อ่านของสวมใส่                        |

**กับดักที่ทำให้ main คำนวณผิดรอบแรก**: `tier` กับ `combatTier` เป็นคนละฟิลด์ ทั้งคู่มีค่า
`'elite'` ได้ — `demon-captain` เป็น `tier: 'normal'` + `combatTier: 'elite'` อ่านผิดฟิลด์
ทำให้ `D` ของมันพุ่งจาก 139.75 เป็น 457.76 (กลายเป็นตัวเดียวกับ `demon-warlord` เป๊ะ)

### P1.2a — ไม้บรรทัดอ่าน**เลเวล** ไม่อ่าน**พลังจริง** (RATIFIED 2026-08-15)

> **`REF` ลอยตามเลเวลบัญชี · ตัวคูณความยากเป็นของ content · ของสวมใส่ ทาเลนต์ และ

### P1.4 — สัดส่วน EXP:gold = 1 : 1.618 (φ)

> **คงที่ทั้งเกม ทุกศัตรู ทุกด่าน**

**เลือกมา ไม่ได้ derive มา** — ต่างจาก `k_exp` (มาจากโค้งเลเวล) และ `D` (มาจากสเตตัส)
φ ไม่มีที่มาทางเศรษฐศาสตร์ เป็น base ที่ตั้งขึ้นโดยตั้งใจ เขียนครั้งเดียว
**บันทึกไว้เพื่อไม่ให้คนอ่านทีหลังไปตามหาสูตรที่ไม่มีอยู่**

**สัดส่วนไม่ใช่ปุ่มเศรษฐกิจ** ตัวคุมเศรษฐกิจคือขนาดตะกร้า (หลักการ 4) — φ คุมแค่ว่าตัวเลข
ทองควรใหญ่เท่าไหร่เทียบ EXP เป็นเรื่องอ่านง่าย/รู้สึกดี

### P1.5 — `k` ต่อช่องทาง

```
k_exp  = EXP สะสมถึง L* / ΣD(บท 1 @ L=1) = 4,170 / 4,783.5 = 0.8717   (L* = 10, ตาราง Ring-0)
k_gold = k_exp × 1.618                                      = 1.41041

exp(รอบ)  = round( k_exp  × Σ D(ตัวที่ฆ่าได้) )      -- ปัดเศษครั้งเดียวตอนจบ
gold(รอบ) = round( k_gold × Σ D(ตัวที่ฆ่าได้) )
```

**สองช่องทางอิสระต่อกัน** ปรับโค้งเลเวลไม่กระทบทอง เพิ่มของขายไม่กระทบ EXP

**`k` คาลิเบรตครั้งเดียวที่ `L = 1` แล้วแช่ — `k` เป็นค่าคงที่ `D` เป็นตัวที่ลอย** ตั้งแต่ P1.2a
`REF` ลอยตามเลเวล `ΣD` จึงลอยตามไปด้วย ถ้า `k` คาลิเบรตใหม่ทุกเลเวล มันจะหักล้าง `D`
ทิ้งพอดีและรายได้จะนิ่งตลอดเกม ซึ่งลบสิ่งที่หลักการ 1 ตั้งใจให้เกิด (ลงด่านง่ายตอนเลเวลสูง
ได้น้อยลง) **`4,783.5` คือ `ΣD` ที่ `L = 1` และมันเป็นเลขในอดีต ไม่ใช่ค่าที่วัดใหม่ทุกครั้ง**

### P1.10 — ไอเทมดรอป: ผูกกับ (ศัตรู × tier) (RATIFIED 2026-08-14)

> **`drops[ศัตรู][tier]` → รายชื่อ item id · อัตราและจำนวนยัง derive จาก `D` เหมือนเดิม**

**ลำดับสามชั้นที่ shipped games ใช้** (จากรอบสำรวจ item drop):

> _"Difficulty does not enter as a multiplier on a number — it enters, in this order of
> importance: (1) which TABLE/TIER is eligible at all, (2) the RATE, (3) rarely, QUANTITY."_

ของเรามีชั้น 2 กับ 3 อยู่แล้ว (จาก `D`) — **ขาดชั้น 1 ซึ่งสำคัญที่สุด** ข้อนี้เติมชั้นนั้น

**exemplar**: Diablo II ระบุ treasure class **ต่อมอน × ต่อระดับความยาก** (Normal/Nightmare/Hell
สลับตารางทั้งใบ ไม่ใช่คูณเลข) · Monster Hunter ใช้รูปเดียวกันแต่ชัดกว่า —
`Rathalos Scale → Scale+ → Shard` **มอนตัวเดิม แรงค์ต่างกัน ชื่อไอเทมคนละอัน**

**เลือกรูป MH: ของเดิมเกรดสูงกว่า ไม่ใช่ของใหม่** (HetCreep 2026-08-14)

```
iron-essence  →  iron-essence+  →  iron-essence++
   tier 1           tier 2            tier 3
```

**ไอเทมยังบอกว่า "ฆ่าอะไรมา"** — เกรดบอกเพิ่มว่ามาจากที่ยากกว่า

**tier มาจาก `difficultyMultiplier` ที่มีอยู่แล้ว ไม่เพิ่มฟิลด์ใหม่ต่อด่าน**

```
dm < 1.04     →  tier 1
1.04 ≤ dm < 1.11  →  tier 2
dm ≥ 1.11     →  tier 3
```

**ขอบ 1.04 / 1.11 เลือกมา ไม่ได้ derive** — บันทึกแบบเดียวกับ φ และ π เลือกเพราะวัดแล้วให้
ชุดดรอปที่ต่างกันมากที่สุด: **8 แบบจาก 10 ด่าน** (ขอบ 1.06/1.13 ให้ 6 · ขอบเท่า ๆ กันให้ 6)

**และขอบนี้ fit กับ content วันนี้ ไม่ใช่ค่าสากล** — เพิ่มด่านแล้วต้องตรวจใหม่

> **AP (พลังงาน)** ซึ่งเป็นตัวอย่างของการขาย _รอบ_ ไม่ใช่ขาย _ทอง_ (ดู P0.2)

**ทางที่เลือก (2026-08-13): ราคาทวีคูณ + รีเซ็ตรายวัน ไม่มีเพดานแข็ง**

ราคาซื้อพลังงานคูณขึ้นทุกครั้งภายในวันเดียวกัน แล้วรีเซ็ตกลับตอนขึ้นวันใหม่

**ทวีคูณ ไม่ใช่บวกเพิ่ม — และนี่คือความต่างระหว่างมีขอบกับไม่มีขอบ** (วัดจากฐาน 50 gem):

| งบ       | บวก +50 ต่อครั้ง | ×1.5 | ×2       |
| -------- | ---------------- | ---- | -------- |
| ฿1,000   | +96 รอบ          | +84  | +60      |
| ฿10,000  | +324 รอบ         | +156 | +96      |
| ฿100,000 | **+1,056 รอบ**   | +216 | **+132** |

ฐานฟรี = 156 รอบ/วัน · บวกเพิ่มทำให้ต้นทุนโตแบบ `N²` งบ `B` ซื้อได้ `√B` ครั้ง — **ไม่ใช่ขอบ**
ทวีคูณทำให้ต้นทุนโตแบบ `2^N` งบ `B` ซื้อได้ `log B` ครั้ง — **ขอบจริง** เงินคูณสิบซื้อได้เพิ่ม 3 ครั้ง

ที่ ×2 คนทุ่ม ฿100,000 ยังได้ไม่ถึงเท่าตัวของคนเล่นฟรี **เพดานเกิดขึ้นเองโดยไม่ต้องประกาศ**
ต่างจาก Genshin ที่บันไดแบนกว่าเลยต้องมีเพดานแข็ง 6 ครั้ง/วันควบ

**ยังไม่เลือก: ตัวคูณ ×2 หรือ ×1.5** — `gemCostFullRefill: 50` วันนี้ยังไม่มีบันไดเลย

### P2.5a — พลังงานหักตอน**เคลียร์** ไม่ใช่ตอน**เข้า** (RATIFIED 2026-08-13)

> **แพ้ ถอย หรือปิดเกมกลางคัน = ไม่เสียพลังงาน** พลังงานจ่ายค่า*ความสำเร็จ* ไม่ใช่ค่า*ความพยายาม*

**สมมาตรกับกฎรางวัลที่มีอยู่แล้ว** — `calculateBattleReward(state, 'defeat')` คืนศูนย์ทุกช่อง
ไม่เคลียร์ = ไม่ได้รางวัล **และไม่เสียพลังงาน** สองอย่างนี้ควรจับคู่กัน

**วันนี้ทำตรงข้าม** `LobbyBattleSession.tsx:212-220` หักพลังงานก่อน `setStageId` คือหักตอนเข้า
และ `BattleResultPanel.tsx:64` บอกว่าแพ้ไม่ได้อะไร — **วายบอสหนึ่งครั้งจึงเสียโควตาเต็มรอบฟรี ๆ**
ใต้เพดานที่จำกัด นั่นคือการลงโทษคนที่สู้ของยาก

**exemplar**: Epic Seven หักตอนเคลียร์ — 1 ใน 9 ระบบที่สำรวจ แต่เป็นข้อเดียวที่แก้ปัญหานี้ตรง ๆ

**ผลข้างเคียงที่ดี**: ผู้เล่นที่อ่อนกว่าไม่ถูกเก็บค่าผ่านทางสองต่อ (แพ้แล้วยังเสียโควตา) งบต่อวัน
จึงยืดหยุ่นตามฝีมือโดยไม่ต้องมีระบบปรับความยาก **และไม่ขัด INV-0** เพราะไม่ได้อ่านเวลา —
อ่านผลแพ้ชนะ ซึ่งเป็นสถานะ ไม่ใช่ระยะเวลา

**ช่องที่ปิดไว้แล้ว**: เข้าด่าน ฆ่าบางตัว แล้วออก = นับเป็นแพ้ → ไม่ได้รางวัล ไม่เสียพลังงาน
**ไม่มีทางได้ของฟรี** สิ่งที่ฟรีคือการเข้าไปดู ซึ่งเป็นเรื่องดี

## หลักการ 4 — ราคาปลายทางคือ base (RATIFIED 2026-08-13)

### P4.1 — ราคาคือ base รายได้คือของที่ตามมา

> ตั้งราคาของที่ทองซื้อได้ก่อน แล้ว `k_gold` derive ตาม **เพิ่มของขาย = รายได้ขึ้นเอง**
> ไม่มีใครต้องไปแก้อัตราดรอป กลับทางกับวิธีปกติที่ตั้งรายได้ก่อนแล้วตั้งราคาให้พอดี

### P4.2 — ของทุกชิ้นเป็น `limited` หรือ `unlimited` เท่านั้น

> **ไม่มีชั้นที่สาม** ทุกอย่างที่ซื้อด้วยทองได้ต้องประกาศคลาสของตัวเอง

### P4.3 — คลาสไหนอยู่ตรงไหนของสูตร

```
limited    → เข้าตัวหารของ k_gold · ต้องนับมูลค่ารวมได้
unlimited  → อยู่นอกตัวหาร · ต้องมีเพดานผลลัพธ์ที่ประกาศได้
```

**ถ้าเอา `unlimited` เข้าตัวหาร ตัวหารเป็นอนันต์ สูตรพัง** — `k_gold` คำนวณไม่ได้

**และ `unlimited` ที่ไม่มีเพดานผลลัพธ์คือดีไซน์ที่พัง**:

```
✅ รีโรลสเตตัส        ต้นทุน ∞  ผลลัพธ์ตัน  →  ปลอดภัย
❌ "+1 ATK ซื้อไม่อั้น"  ต้นทุน ∞  ผลลัพธ์ ∞   →  คนขยันที่สุดแรงไม่มีที่สิ้นสุด
```

สองอย่างนี้หน้าตาคล้ายกันมากถ้าไม่ระวัง — นั่นคือเหตุผลที่ต้องบังคับให้ประกาศ

### P4.4 — `N = π` → ตะกร้า `limited` = 21,196 ทอง

```
catalog = k_gold × N × ΣD(บท 1) = 1.41041 × π × 4,783.5 = 21,196
```

**π ไม่ได้เลือกเพราะสวยอย่างเดียว** — เอา content ที่ออกแบบไว้แล้ว (skill tree + talent +
awakening ของ monkey-king) ขยายให้ครบทั้ง 7 ตัวละคร ได้ **20,580 ทอง** ห่างจากที่ π
เรียกร้อง **3.0%** ตัวเลขจึงไปถึงได้ด้วยการสร้างสิ่งที่ออกแบบไว้แล้ว ไม่ต้องคิด content ใหม่

ตัวเลือกอื่นที่พิจารณาแล้วทิ้ง: √2 (1.414) และ φ (1.618) ต่ำกว่าเป้าที่ทำได้จริง 47–54%
ตะกร้าเล็กเกินไป ทองล้นตั้งแต่วันแรก · φ ยังใช้ไปแล้วกับ P1.4 ใช้ซ้ำจะดูเหมือนมีระบบทั้งที่
ไม่มี · `2π` และ `π²` ต้องมีของขายเพิ่มอีก 2–3 เท่าจากที่ออกแบบไว้

**`N = π` เป็นตัวเลือก ไม่ได้ derive** บันทึกแบบเดียวกับ φ

**และ `N` ไม่ใช่ตัวเลขที่ตั้งได้ตามใจ** — `catalog = 6,747 × N` บอกว่าตะกร้าที่*มีอยู่จริง*
แปลเป็น `N` ได้เท่าไหร่ ตั้ง `N = 50` ไม่ได้ถ้าไม่มีของขายมูลค่า 337,350 วันนี้ตะกร้า 3,075
= `N` 0.46 **ต้องสร้าง content ให้ถึงก่อน ตัวเลขถึงจะจริง**

### P4.5 — สองคลาสทำหน้าที่คนละอย่าง และนี่คือเหตุผลที่ไม่ขัดกัน

```
limited    มีจุดจบ  →  ทุกคนที่เล่นนานพอไปถึงจุดเดียวกัน
                       คนเก่าซื้อครบ ทองส่วนเกินตาย นำต่อไม่ได้ → คนใหม่บรรจบ
unlimited  ไม่มีก้น  →  ความขยันส่วนเกินลงตรงนี้ ไม่มีวันตัน
```

**แก้ข้อขัดที่เคยยกไว้**: "เพดานเตี้ยให้คนใหม่ไล่ทัน" กับ "เพดานลึกให้ความขยันมีที่ไป" ขัดกัน
ตราบใดที่มีชั้นเดียว — **สองชั้นแยกกันแล้วไม่ขัด** ชั้นจำกัดทำให้บรรจบ ชั้นไม่จำกัดรับส่วนเกิน

**คนใหม่ไล่ทันเพราะเพดาน ไม่ใช่เพราะอัตรา** — เคยเข้าใจผิดว่าตะกร้าโตขึ้นแล้ว `k_gold` โตตาม
ทำให้คนใหม่ตามทัน ไม่จริง เพราะอัตราขึ้นทั้งสองคน ช่องว่างสัมบูรณ์ไม่แคบลง สิ่งที่ทำให้บรรจบ
คือคนเก่าชนเพดานแล้วทองส่วนเกินไม่มีที่ใช้

### P4.6 — รีโรลสเตตัส: `unlimited` ตัวแรก

> **รีโรลได้ไม่จำกัด ผลลัพธ์คือสเตตัส +1–5% (ต่อเนื่อง)**

เก็บค่าที่ดีที่สุด ค่าคาดหวังจากการรีโรล `n` ครั้ง = `1 + 4n/(n+1)` — derive ได้ ไม่ต้องจูน

| รีโรล  | ได้     |
| ------ | ------- |
| 1      | 3.0000% |
| 10     | 4.6364% |
| 100    | 4.9604% |
| 1,000  | 4.9960% |
| 10,000 | 4.9996% |

```
ทอง 100 เท่า   → สเตตัสห่างกัน 0.360%
ทอง 1,000 เท่า → สเตตัสห่างกัน 0.363%
```

**เพิ่มทองอีก 10 เท่า ได้เพิ่ม 0.003%** — ช่องว่างบีบตัวเองจนแทบเป็นศูนย์ เพดาน 5% เข้าใกล้ได้
ไม่มีวันถึงเพราะเป็นค่าต่อเนื่อง **นี่คือรูปที่ P4.3 ต้องการเป๊ะ: ต้นทุนอนันต์ ผลลัพธ์ตัน**

**และมันไม่ใช่การพนัน เพราะ P2.2 ห้ามขายทอง** — ไม่มีเงินจริงเข้ามาเกี่ยวข้องกับการสุ่ม
มันคือการฟาร์ม ถ้าวันหนึ่งทองซื้อได้ด้วยเงิน ข้อนี้กลายเป็นพื้นที่กำกับดูแลทันที

### P4.7 — เทสต์ที่ต้องเขียน

1. ของทุกชิ้นในแคตตาล็อกมีฟิลด์คลาส (`limited` / `unlimited`) — ไม่มีชิ้นไหนเว้นว่าง
2. ผลรวมมูลค่าของ `limited` ทั้งหมด = ตัวหารที่ `k_gold` ใช้จริง
3. ของ `unlimited` ทุกชิ้นประกาศเพดานผลลัพธ์เป็นตัวเลขได้
4. `k_gold` คำนวณสดจาก base ไม่ใช่ literal

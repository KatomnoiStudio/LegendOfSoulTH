# 11. Boss System

> Category: Enemy / Boss · Generated via gold-standard FILL + adversarial CB-lite verify (2 seats), 2026-08-07 · **revised after verify flagged an issue**.

### Scope

Boss System owns the **HP-threshold phase-transition state machine** for boss-tier encounters only: `Current Action → Finish Current Action → PhaseTransition → Invulnerable → Phase 2` (§3.6.9), the boss attack-set swap on transition, and the telegraph feedback-layer contract (ground marker required + cast bar/tint/SFX, §3.6.8) for boss attack rows. It does **not** own: the generic enemy AI loop (`EnemyAISystem.ts`, system #9 — currently `idle|chase|attack|recover|hit|dead`, no `Telegraph` state exists yet, `src/game/realtimeBattle/EnemyAISystem.ts:17`); Mini-boss/Elite tier, which is explicitly single-phase, no transition (§3.8.4); per-move data schema (#5, §3.6.7); knockdown/hit-reaction eligibility (#6, §3.6.5); or stage/wave placement of the boss encounter (#16/#17, `stageConfig.ts`).

**Current code state: not implemented.** Only a type-level tag exists — `EntityType = 'player' | 'enemy' | 'boss'` (`src/game/realtimeBattle/types.ts:31`). Grepping the full `src/` tree for `boss`/`Boss` (case-insensitive) returns only that one line — no boss template, no phase logic, no telegraph state, no boss attack table. §3.6's own header confirms this is intentional: "Implementation: separate PRs only — this section is documentation, not gameplay code" (`docs/MASTER_BLUEPRINT_v3.0.md:147`).

### Inputs/Outputs

- **In**: a boss template (new — no `RealtimeEnemyTemplate`-equivalent exists for bosses today; the closest analog is `RealtimeEnemyTemplate` in `src/game/realtimeBattle/stageConfig.ts:29-54`) carrying per-phase attack rows, each row needing `telegraphMs`, `attackShape`, and phase eligibility per §3.6.7's "Boss/enemy attacks additionally define" clause (`docs/MASTER_BLUEPRINT_v3.0.md:217`); an HP-threshold config (baseline 50%, §3.6.12); the boss's live `RealtimeBattleEntity` (`types.ts:33-69`).
- **Out**: mutated `entity.state`/`invulnerableUntilMs` (existing field, `types.ts:62`, already consumed by `HitboxSystem.ts:92`'s damage gate — reuse it, don't add a second invulnerability flag); a swapped active attack-row pool per phase; telegraph feedback data for the render layer (ground marker position/shape, cast-bar progress, tint state) — likely as a new `BattleEffectEvent` kind alongside the existing `hit-spark|skill-spin|death|spawn` union (`types.ts:80`).

### Dependencies

- **Enemy AI System (#9)** — extends its core loop; must not fork a parallel state machine. The `Telegraph` state referenced in §3.6.8 doesn't exist in `EnemyAISystem.ts` yet — Boss System is what has to add it.
- **Elite / Mini-boss Tier System (#10)** — sibling tier, shares stat/knockdown baseline, explicitly does **not** share the phase-transition machinery (§3.8.4).
- **Per-Move Property Schema (#5)** — boss attack rows extend the same `AttackDefinition`-family schema (§3.6.7).
- **Hit Reaction System (#6)** — knockdown-eligibility gate still applies to boss normal hits; phase-transition invulnerability is a separate mechanism, not a knockdown override.
- **Stage / Adventure System (#16) & Stage Variation System (#17)** — boss encounters are placed via the `stageConfig.ts` single-source-of-truth pattern (`stageConfig.ts:6-9`).
- **Reward System (#18)** — feeds boss-clear rewards downstream; Boss System does not compute rewards itself.

### Done-criteria

1. HP crossing the phase threshold **mid-`AttackActive` or mid-`Recovery`** does not cut the current action — transition only fires after the action completes (test: force boss HP below 50% while `stateElapsedMs` is inside an active attack window, assert state stays `attack`/`recover` until it naturally finishes).
2. During `PhaseTransition`, `boss.invulnerableUntilMs` is set past the transition's full duration so `HitboxSystem.ts:92`'s existing `target.invulnerableUntilMs > elapsedMs` check rejects every incoming hit — no new invulnerability path.
3. Post-transition attack-row pool is provably different from pre-transition (reference/array-content assertion), matching "swaps attack set for new phase" (§3.6.9).
4. `Telegraph` becomes a real `EnemyAIState` value (extends the union at `EnemyAISystem.ts:17`), holds for the attack row's own `telegraphMs` (800–1200 ms boss baseline, §3.6.12), and emits at least the required ground-marker feedback event before `AttackActive` starts.
5. The `PhaseTransition → Invulnerable → Phase 2` sequence is single-use per boss instance — re-crossing the threshold after already being in Phase 2 does not re-trigger a second transition (test at repeated/oscillating HP values around the threshold).

### World-class bar

Real exemplar: **FromSoftware's Dark Souls-series boss phase transitions** (e.g. Ornstein & Smough, most DS3 bosses) — a scripted, fully unskippable "moveset-swap" animation at an HP gate during which the boss takes zero damage and no player input can shorten or interrupt it. The one concrete pattern worth borrowing: make the transition itself a **hard, player-uninterruptible state** (not merely an HP check gating a flag) — exactly what §3.6.9 already specs ("Boss stops attacking / Plays transition animation / Invulnerable"). The done-criteria above are written to pin that specific property, since it's the part easiest to accidentally undermine (e.g. a generic damage-application path that forgets to check the new invulnerability window).

### Stay-current note

Telegraph feedback today is deliberately capped at "ground marker + cast bar + sprite tint" with heavy 3D telegraph VFX explicitly excluded for now (§3.6.10, `docs/MASTER_BLUEPRINT_v3.0.md:270`). As the project's R3F/WebGPU material pipeline matures (AGENTS.md law #11, `.claude/skills/threejs-webgl/`), shader-based telegraphs (rim glow, ground decals via shader) may become cheap enough to be worth revisiting — this is a named, bounded "later" already flagged in the blueprint itself, not invented churn.

### Low-maintenance-cost design

**Single source-of-truth data table, no premature class hierarchy.** Every boss attack row is data ("Each boss attack is its own data row," §3.6.8) — it belongs in a `stageConfig.ts`-pattern table (that file's own header comment bans hard-coding stage/enemy data in components: "ห้าม hard-code ข้อมูลด่านไว้ใน Component... ทุกอย่างที่ห้องต่อสู้ต้องรู้... อยู่ในไฟล์นี้ไฟล์เดียว," `stageConfig.ts:6-9`), extended with per-phase attack pools and `telegraphMs`/`attackShape` fields — not a new file format. On the logic side, extend the existing function-based `stepEnemyAI` (`EnemyAISystem.ts:76`) with boss-gated branches (`entityType === 'boss'`) rather than introducing a `BossAI` class/interface: **zero boss or Elite/Mini-boss AI code exists anywhere in `src/` today** (confirmed by the full-tree grep in Scope, plus a separate grep for `elite`/`mini-?boss` returning no matches) — there is nothing yet to generalize over, which is exactly when an interface/class is premature. (§3.7's Monkey King kit is the _player_ hero's moveset, not a boss reference kit — no boss-specific reference kit exists anywhere in the blueprint; the closest thing, P6 "Boss prototype," is still an unstarted future item.) With no existing implementation to abstract across, and Elite/Mini-boss explicitly _not_ sharing the phase-transition machinery (§3.8.4) even once it is built, a single boss-gated branch in the shared AI loop is the smallest thing that could work — split it into its own type only if/when a second, meaningfully different boss AI shape actually shows up.

### Known scars (real historical precedent)

- **Scar**: Dark Souls speedrunners found that switching weapons during the loading-screen transition into the Ornstein & Smough fight suspends both bosses' AI activation for several seconds after the fight begins — a community-named "AFK glitch" that exploits the gap between entity spawn and the AI loop's first activation, letting the player land free hits before the bosses "wake up." The technique generalizes across many Dark Souls bosses, not just O&S. — Source: PC Gamer, "Dark Souls speedrunners came up with a hilarious way to beat bosses: turn their brains off" (pcgamer.com). A separate, community-documented technique with the same net effect — a "trigger skip" rather than the load-screen weapon-switch — is covered in "Dark Souls Remastered O&S Trigger Skip Tutorial" (YouTube); the two are distinct named exploits with a shared symptom (exploitable AI-inactive window), not one technique under two names.
  **Test-for-us**: Spawn a boss and immediately probe its `EnemyAIState` before any player-triggered event fires — try to land damage or force a state read in the window between entity spawn and the AI loop's first `stepEnemyAI` tick, and check whether the boss is combat-capable (or exploitably passive) during that gap.

- **Scar**: After Smough dies, "Super" Ornstein (phase 2) can cancel his attack windups and transition immediately into a different attack, making his telegraphs unreliable to read — community-documented as having gotten more frequent after a 2013-era patch. — Source: Fextralife Dark Souls Wiki, "Bugs and Glitches" (darksouls.wiki.fextralife.com/Bugs+and+Glitches).
  **Test-for-us**: During a boss's post-transition (Phase 2) attack-row execution, try to interrupt/cancel a `Telegraph`-state attack mid-windup (e.g. via a state re-entry, a second HP-threshold crossing, or an animation-event race) and check whether the emitted ground-marker/cast-bar event still matches the attack that actually executes — i.e. verify the telegraph the player sees can never be canceled into a different, unforeshadowed attack.

- **Scar**: If Gwyn is parried and backstabbed in the same instant (two simultaneous lethal-condition triggers), he ends up still showing a health bar and standing frozen in place instead of completing his death/transition sequence — a race condition between two state-machine triggers resolving in an inconsistent state. — Source: Fextralife Dark Souls Wiki, "Bugs and Glitches" (darksouls.wiki.fextralife.com/Bugs+and+Glitches). (Gwyn is a DS1 final boss and this scar is a separate addition to the exemplar set above — it is not part of the O&S citation in docs/agent-blueprint/11-boss-system.md.)
  **Test-for-us**: Fire two damage events that both cross the phase threshold (or one threshold-cross plus a lethal hit) on the exact same tick/frame and check whether `PhaseTransition` and death/other-state entry can both fire, leaving the boss in a contradictory state (e.g. `invulnerableUntilMs` set but action loop frozen, or Phase 2 attack pool swapped but state stuck outside `Phase 2`) — this is the direct stress test for done-criterion #5's "single-use per boss instance" guarantee.

- **Scar**: Ornstein can sometimes warp through a wall and disappear for good during the phase-2 portion of the same fight, and players are warned to avoid fighting him near the fog walls in that room. — Source: Fextralife Dark Souls Wiki, "Bugs and Glitches" (darksouls.wiki.fextralife.com/Bugs+and+Glitches).
  **Test-for-us**: While a boss is in the post-transition phase, drive it toward arena boundaries/scripted trigger volumes during an active attack or telegraph and check whether the boss entity's position/state can desync from the state machine (e.g. AI thinks it's mid-attack but the entity has left the playable/renderable area, or a stage trigger fires while the boss is off-bounds) — a positional edge case the phase-transition logic and the stage/arena bounds need to agree on.

This project's own spec — `docs/MASTER_BLUEPRINT_v3.0.md` §3.6 and `docs/agent-blueprint/11-boss-system.md`'s done-criteria — is what "correct" means here; the exemplar above only names the _shape_ of failure to probe for (uninitialized AI window, telegraph-cancel races, simultaneous-trigger state corruption, position/state desync), never how Dark Souls happened to (not) fix it.

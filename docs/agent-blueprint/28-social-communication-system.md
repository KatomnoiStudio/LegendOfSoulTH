# 28. Social / Communication System

> Category: Social · Generated via gold-standard FILL + adversarial CB-lite verify (2 seats), 2026-08-07 · **revised after verify flagged an issue**.

### Scope

Owns two currently-shipped surfaces: (1) **World Chat** — a single global text channel with a hidden admin command grammar (`/givecharacter`, `/givegold`, `/giveitem`, `/help`) plus **public** player-facing commands (`/block`, `/unblock`, `/blocklist` — not admin-gated, revised 2026-08-09 item #10), rendered as a lobby-corner panel (`src/components/WorldChat/WorldChat.tsx:9-10`, `WorldChat.module.css:2`); and (2) **Friends** — UID-based player lookup (via `find_player_by_uid` RPC, `supabase/migrations/0012_public_profile_lookup.sql`) + one-way "add friend" snapshot storage (`src/components/AddFriendModal/`, `src/types/player.ts:30-35,66`). It does NOT own: guild/clan systems (no code, "แชทกิลด์" tab is a disabled stub, `WorldChat.tsx:229-231`), private/DM chat (same stub), friend requests/accept/reject flow (does not exist — see Inputs/Outputs). **Revised 2026-08-09 — 3 claims here were stale**: player blocking is now real and wired (`/block`/`/unblock`/`/blocklist` + `blockList.ts`, client-local, filters the chat feed by `authorName` — item #10), the admin gate is a real server-side security boundary (`admin_accounts` table + `SECURITY DEFINER` RPC checks, not client-only — `src/data/admins.ts`'s old static-list gate was already replaced before this doc's original 2026-08-07 pass), and `docs/MASTER_BLUEPRINT_v3.0.md` §7.5 now DOES lock this system (data ownership, moderation) — this doc's own "zero coverage" claim is what's now stale, not the blueprint. **Still genuinely true**: World Chat data ownership doesn't yet match §7.5's server-authoritative lock — it's 100% `localStorage`, no Supabase (item #9, code fix pending, see `chatStorage.ts`).

### Inputs/Outputs

- **World Chat** — in: `playerName: string`, `isAdmin: boolean`, `onGiveCharacter`, `onGiveGoldAdmin`, `onGiveItemAdmin` (props, `WorldChat.tsx`); message shape `ChatMessage { id, authorName, text, createdAt }` (`chatStorage.ts:21-26`), persisted to `localStorage` key `los:worldchat:v1`, capped at 200 messages, fanned out same-device/cross-tab only via `BroadcastChannel` — **no server, no cross-device delivery** (unchanged, item #9 pending). **Revised 2026-08-09**: `resolveCommandForSender(isAdmin, raw) => ParsedCommand | null` (`commands.ts`) now gates by **command name** (not parsed result kind — a prior version leaked admin-command usage-syntax to non-admins via the error path, fixed same session) against `ADMIN_ONLY_COMMAND_NAMES` (`givecharacter`/`givegold`/`giveitem`); `ParsedCommand` adds `give-gold`, `give-item`, and the public `block`/`unblock`/`blocklist` kinds. Block/unblock results are also local-only system entries (never posted to the shared feed), but unlike admin-command results they're reachable by every player, not secret.
- **Friends** — in: UID string (10 digits, `game/uid.ts`) via `onSearch(uid) => Promise<FriendCandidate | null>`; out: `FriendCandidate { uid, name, level, title }` (`types/player.ts:30-35`), a point-in-time snapshot, appended to `Player.friends: FriendCandidate[]` through `onPlayerChange(next: Player) => Promise<boolean>` (`AddFriendModal.tsx:8-15`, `AddFriendPanel.tsx:47-71`). Server-side: `public.friends` table, one row per `(profile_id, friend_uid)`, RLS `auth.uid() = profile_id` for both select and write (`supabase/migrations/0001_init.sql:55-60,112-113`) — **write-your-own-row only, no reciprocal accept step, no notification to the added player.**

### Dependencies

- **hero** (`game/characters.ts` — `ROSTER`, `getCharacter`) for `/givecharacter` command resolution and display (`commands.ts:1,26-41`, `WorldChat.tsx:2,123`).
- **backend** (Supabase `profiles`/`friends` tables + RLS) for friend persistence and `findPlayerByUid` — the live path is `src/hooks/useAuth.ts` → `src/data/accountRepository.supabase.ts:202` (queries `profiles`/`friends` via the Supabase client), migration `0001_init.sql:55-60`. Note: `src/data/accountRepository.ts` (including its own `findPlayerByUid` at line 605) is the **legacy localStorage implementation** — its own header comment says "ฐานข้อมูลผู้เล่น (เวอร์ชันเก็บใน localStorage)" — and is dead in the running app; every non-type import of it across the codebase (AuthModal, CurrencyShopModal, ErrorBoundary, LobbyBattleSession, SettingsModal, TopBar, WorldChat, LobbyPage) is `import type` only. `AGENT_BLUEPRINT.md:85` already documents this local-vs-production split and flags the two files as hand-mirrored with no shared contract.
- **economy** — indirectly, since `/givecharacter` grants an owned character through the same account-mutation path currency/inventory grants use (`accountRepository.ts` `CharacterGrantResult` type).
- Feeds **none** of the other 28 systems currently — no other system reads chat or friends data (grep confirms no cross-imports of `WorldChat`/`AddFriendModal` outside `LobbyPage.tsx:4,7,182,224`).

### Done-criteria

1. `npm run test` passes `src/components/WorldChat/commands.test.ts` unchanged in behavior (admin-gate: non-admin sender always returns `null` regardless of text).
2. A message posted in one tab appears in another tab of the same browser within one `BroadcastChannel` tick, and survives a page reload (localStorage round-trip) — manually or via a Playwright check against `chatStorage.ts`.
3. Typing `/anything` as a non-admin (or admin on a non-admin account) sends it as a literal chat message character-for-character — never dropped, never intercepted.
4. Adding a friend that fails to persist (`onPlayerChange` resolves `false`) shows the error toast and does **not** show the success toast (`AddFriendPanel.tsx:62-71`) — this is the one existing regression test worth pinning if not already covered.
5. `docs/MASTER_BLUEPRINT_v3.0.md` gap is closed with an explicit HetCreep-approved section before any of the following ship: guild chat, private/DM chat, friend request/accept flow, or player blocking — none of these may be silently implemented against the disabled UI stubs.

### World-class bar

**Guardian Tales** (already the project's own cited exemplar for the single-active-hero combat model, `docs/MASTER_BLUEPRINT_v3.0.md:334`) also ships a comparably lightweight social layer: a single global/local chat channel plus a friend list gated by an in-game numeric ID — not a full social graph, matching this project's UID-based friend lookup almost exactly. ⚠️ unverified: whether Guardian Tales' friend list surfaces a presence/last-active signal next to each entry — targeted searches did not turn up a source confirming this detail, so it should not be treated as settled. If confirmed, it would be the one pattern worth borrowing: this project's `FriendCandidate` snapshot (`uid, name, level, title`, no timestamp) cannot show presence today — worth a `lastSeenAt` field if/when friends move off snapshot semantics, contingent on verifying the exemplar first.

### Stay-current note

The client-only admin gate (`src/data/admins.ts`) and the `BroadcastChannel`-only chat delivery are both explicitly marked in-code as placeholders for "when there's a real backend" (`chatStorage.ts:11-15`, `admins.ts:9-11`) — this design will need revisiting the moment Social gets a real-time backend channel (Supabase Realtime is already used elsewhere in the project's backend), since both the trust boundary and the fan-out mechanism are named-in-comment as temporary.

### Low-maintenance-cost design

The existing split between **command parsing** (`commands.ts`, pure functions, no React, unit-testable) and **command execution** (`WorldChat.tsx`, calls into `accountRepository` via props) is the one structural choice worth preserving and extending — it's already the project's proven pattern (`commands.ts:6-8` states this explicitly as the reason it was split out). Any new admin command or social action should follow the same shape: a pure resolver function with a discriminated-union return type, no new abstraction/interface layer, no speculative "command registry" class until there are enough commands that a flat `if` chain (`commands.ts:69-83`) actually hurts — YAGNI per this repo's own established style (`.agents/rules/ecc`). For the friends-list-growth pattern specifically, follow the **live** Supabase path's shape — `friends` built inline via `.map()` over the query result in `accountRepository.supabase.ts:102` — rather than the `Player.friends: FriendCandidate[] ?? []` guard in `accountRepository.ts`'s `normalizePlayer`, which is real but lives in the dead localStorage file and isn't demonstrated as current production practice.

### Known scars (real historical precedent)

- **Scar**: Guardian Tales' guild chat had a bug where a member's chat message would disappear when it overlapped with a (re)connection event. — Source: Guardian Tales official patch notes, November 30, 2021 (mirrored at guardiantalesguides.com/game/patches/view/22 — "An issue where the guild member chat disappears when it overlaps with the connection is fixed").
  **Test-for-us**: In this project's `chatStorage.ts`, send a message from Tab A at the same moment Tab B does a full reload (not just a re-subscribe — per `chatStorage.ts:69` the `BroadcastChannel` is a module-level singleton created once at import, so only a full reload actually recreates it; a bare re-subscribe on the existing channel wouldn't reproduce the gap). Try to reproduce a window where the message is neither delivered live (channel not yet re-attached after reload) nor recovered from the localStorage round-trip on Tab B's reload, i.e. it's silently lost rather than eventually consistent.

- **Scar**: In the same patch, Guardian Tales reduced guild chat to 10 messages per minute per user — the patch note frames this as a reduction from a prior, looser throttle, not a move from fully unthrottled to capped. — Source: Guardian Tales official patch notes, November 30, 2021 (guardiantalesguides.com/game/patches/view/22 — "Guild chat is reduced to 10 times per minute").
  **Test-for-us**: Fire a rapid burst of messages into `WorldChat` from one session and check two things: (a) whether anything in this project's chat path throttles or degrades gracefully, and (b) since delivery is `localStorage`-backed, whether an unbounded flood grows the stored chat log without bound and visibly stalls/lags the receiving tab.

- **Scar**: When Guardian Tales migrated its friend system to mutual-acceptance, it introduced a hard cap of 30 pending friend requests per user; the patch note states requests exceeding the maximum limit "will not be sent" once a user is at capacity. — Source: Guardian Tales official patch notes, September 19, 2023 (guardiantalesguides.com/game/patches/view/62).
  **Test-for-us**: This project's `AddFriendPanel.tsx:62-71` already distinguishes only two outcomes from `onPlayerChange` — success toast vs. generic error toast (pinned by the existing regression test, per this doc's item 4). Try a friend-add that fails for a capacity/limit-shaped reason (or any reason other than plain persistence failure) and check whether it collapses into the same undifferentiated error toast as a real save failure — i.e. whether the current two-outcome contract can actually distinguish "your request didn't go through" from "it went through but was silently dropped/undeliverable."

This project's own spec — `docs/MASTER_BLUEPRINT_v3.0.md` and `docs/agent-blueprint/28-social-communication-system.md` — decides what "correct" looks like here; Guardian Tales' patch notes only indicate what _kind_ of chat/friend-list failure to go looking for, not how to fix it.

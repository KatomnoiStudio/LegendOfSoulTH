# 5. Per-Move Property Schema

> Category: Combat core · Generated via gold-standard FILL + adversarial CB-lite verify (2 seats), 2026-08-07 · **revised after verify flagged an issue**.

### Scope

Owns the shared TypeScript data contract that every attack/skill/enemy-move definition must satisfy — the single `AttackDefinition` interface in `src/game/realtimeBattle/attacks.ts` (currently: phase timing, combo window, damage multiplier, hit geometry, knockback) plus the full superset from blueprint §3.6.7 (`castDelayMs`, `interruptible`, `movementDuringCast`, `lungeDistance`, `hitstunMs`, `knockdown`, `multiTarget`, `effects[]`) — all eight are now shipped as optional fields on the interface, each with a real runtime consumer (`combatMoveSchema.ts`, `HitboxSystem.ts`, `EffectsSystem.ts`, `DamageSystem.ts`, `EnemyAISystem.ts`; see `attacks.test.ts`'s `OPTIONAL_FIELDS` list for the authoritative shipped set). It does **not** own how the fields get consumed (hit-geometry resolution → `HitboxSystem.ts`; damage application → `DamageSystem.ts`; combo chaining → `ComboSystem.ts`; cooldown/cast → `SkillSystem.ts`/`skills.ts`; enemy timing → `EnemyAISystem.ts`) — those are separate system entries (#3, #4, #6, #7, #8), matching AGENT_BLUEPRINT.md line 21's own statement that "#3/#4/#6/#7/#8 all silently depend on it existing" — that read this schema. It also does not own boss/enemy-only phase-eligibility or geometry decisions from §3.6.7 ("Boss/enemy attacks additionally define: telegraphMs, attackShape, phase eligibility") even though the fields themselves already shipped here: `telegraphMs` is a plain optional field on `AttackDefinition` (`attacks.ts:68`), and `attackShape` was deliberately resolved as unnecessary — it reuses the existing `hitShape` field rather than adding a duplicate (see `stageConfig.ts:84-91`). Boss attack data literals (`SPIRIT_GUARDIAN_BOSS_PHASE_1_ATTACKS`, `SPIRIT_GUARDIAN_BOSS_PHASE_2_ATTACKS`, `attacks.ts:257-294`) already exist; phase eligibility is expressed by table position, owned by the Boss System (#11), not this schema.

### Inputs/Outputs

Not a runtime system — a compile-time data contract plus data literals.

- **Type contract**: `export interface AttackDefinition` (`attacks.ts:18-83`) — required fields: `id, animationId, startupMs, activeMs, recoveryMs, comboWindowStartMs, comboWindowEndMs, damageMultiplier, range, hitShape: 'horizontal'|'radial', arcDegrees, depthTolerance, knockback`; shipped optional fields (each with a real consumer): `targetLock, effects, knockdown, lungeDistance, telegraphMs, hitstunMs, knockdownMs, getUpMs, interruptible, phaseOverrides, strikeCount, castDelayMs, movementDuringCast, multiTarget` (see `attacks.test.ts`'s `REQUIRED_FIELDS`/`OPTIONAL_FIELDS` for the authoritative list).
- **Data output**: literal objects/arrays satisfying it — `PLAYER_ATTACK_CHAIN: AttackDefinition[]` (3-hit combo, now defined per-hero in `src/game/heroes/attackChains.ts` and re-exported from `attacks.ts:89-93` for backward compat), `MONKEY_SPINNING_STAFF` (`attacks.ts:114-128`), `MONKEY_STAFF_THRUST` (`attacks.ts:131-146`), etc.
- **Downstream wrapping**: `RealtimeSkillDefinition` (`skills.ts:18-27`) embeds an `attack: AttackDefinition` plus skill-only fields (`cooldownMs`, `invulnerableMs`) — the pattern any future field addition (e.g. `effects[]`) must follow: extend the shared struct, not fork a parallel one per consumer.

### Dependencies

Consumed by (reads this schema): Basic Attack System (#3), Skill/Cast System (#4), Hit Reaction System (#6), Effects System (#7), Skill-Targeting System (#8), Enemy AI System (#9), Elite/Mini-boss System (#10), Boss System (#11), Hero Kit/Archetype System (#12).
Feeds/depended on by: none — it is the foundational leaf data type; only depends on the TS compiler.

### Done-criteria

1. `AttackDefinition` remains the single exported type every attack/skill literal satisfies — `tsc`/typecheck is the check, no duplicate/parallel move-data interface appears anywhere in `src/game/realtimeBattle/`.
2. Any new field added from §3.6.7's un-shipped set (`interruptible`, `lungeDistance`, `hitstunMs`, `knockdown`, `multiTarget`, `castDelayMs`, `movementDuringCast`, `effects[]`) ships in the **same PR** as the system that reads it — no field added ahead of a consumer (see Low-maintenance-cost below).
3. Existing tests (`SkillSystem.test.ts`, `HitboxSystem.test.ts`, `EnemyAISystem.test.ts`) pass unmodified unless the PR explicitly updates them to cover the new field.
4. `hitShape` union is extended (not replaced) when the projectile/line archetype from §3.8.2 lands — old `'horizontal'|'radial'` literals keep compiling.
5. No attack/skill data value lives outside `attacks.ts` — grep for a timing field name immediately followed by a numeric literal (e.g. `startupMs:\s*\d`, `recoveryMs:\s*\d`, not a bare `startupMs:` key match) outside that file should return nothing, per the file's own docstring mandate (`attacks.ts:4-5`). The bare-key form is too loose: it currently matches `EnemyAISystem.ts:331-335`'s `ENEMY_ATTACK_TIMING` block (`startupMs: getEnemyAttackById('enemy-melee').startupMs` / `recoveryMs: getEnemyAttackById('enemy-melee').recoveryMs`) — a legitimate (if now `@deprecated`) re-export that reads the single source of truth rather than hard-coding a number, not a violation. The numeric-literal-anchored pattern correctly passes that file and only fires on an actual duplicated constant.

### World-class bar

Exemplar: **this project's own locked design**, not an external one — `phaseOverrides` is required because Monkey King's Ultimate intentionally differs by phase: telegraph/startup/active are non-interruptible while recovery is interruptible. A move-wide boolean cannot express this shipped lock, so every phase consumer must resolve the optional override before falling back to the move default.

### Stay-current note

`hitShape: 'horizontal' | 'radial'` is a closed union with only two members; §3.8.2 (exemplar: Genshin Impact — bow/catalyst basics reuse the same melee state machine with `lungeDistance≈0` and a projectile hitbox) already locks that a ranged/projectile archetype needs a third shape (projectile/line) reusing this same schema — this is a near-term, blueprint-flagged extension, not invented churn.

### Low-maintenance-cost design

Keep `AttackDefinition` a **single flat interface**, not a discriminated union or per-shape subtype hierarchy (`HorizontalAttackDefinition` vs `RadialAttackDefinition`), even though `arcDegrees` only matters for `radial` and `depthTolerance` only for `horizontal`. Splitting into subtypes now would be a premature abstraction with two members and no proven pain point — YAGNI per AGENTS.md's own top-level law item 12 (`.agents/rules/proven-good-do-it-now.md`, "proven-good goes in now" — everything else is weighed, not scaffolded ahead of need). The file's own docstring already states the operative principle: one file, one source of truth, because balancing combat means editing numbers in one place (`attacks.ts:4-5`). Only fork the type once a third `hitShape` variant proves the flat-optional-field shape genuinely wrong.

Exemplar used: Genshin Impact (miHoYo/HoYoverse) — the exemplar named in the file's Stay-current note (§3.8.2, cited for ranged/melee state-machine reuse). Genshin is **not** an exemplar for the World-class bar section: that section's own declared exemplar is this project's own locked design (interruptible/phaseOverrides), not an external one. The World-class bar section mentions Genshin only inside a parenthetical that explicitly disclaims it — the doc's own words are that the Genshin citation "is unrelated to this point... that citation belongs to the Stay-current note below, not here." The phrase "§3.8.2's actual Genshin citation" is quoted from that disclaimer, sourcing where the citation lives (§3.8.2), not asserting Genshin has any exemplar role in the World-class bar section itself.

### Known scars (real historical precedent)

- **Scar**: Citlali's Normal Attack range would abnormally shrink and become inconsistent with her regular Normal Attacks whenever she entered her leaping (bow/aiming-adjacent movement) state — a per-character geometry field silently diverging depending on which motion-state the move ran from. — Source: icy-veins.com, "Genshin Impact Patch 5.5 Patch Notes, Bug Fixes and Primogem Compensation" (the fix shipped in patch 5.4; quoted here from that article's patch-notes text: "Fixes an issue whereby when Citlali enters her leaping state, her attack range would abnormally decrease and become inconsistent with her Normal Attacks.")
- **Test-for-us**: Try authoring two `AttackDefinition` entries for the same move where one is entered from a normal ground state and another from an alternate movement/aiming state (e.g. a jump-attack or dash-attack variant) — does anything in the resolution path let `range`/`hitShape`/`arcDegrees` silently differ between the two entry paths instead of both reading the same locked field, and would `HitboxSystem.ts` catch it if they diverged?

- **Scar**: Raiden Shogun's Elemental Burst ("Chakra Desiderata") failed to gain Resolve stacks specifically when Yelan's Elemental Burst was the trigger — a cross-character field/effect-trigger interaction broke for one specific combo while working for others, live for over a week before a fix + compensation. — Source: sportskeeda.com, "Genshin Impact developers to compensate players with 100 Primogems for Raiden Shogun kit bug in 2.7" (⚠️ unverified against primary source: the sportskeeda article and the Genshin wiki's 2.7 changelog could not be loaded directly to confirm the original patch-note wording verbatim; a separate secondary source describes a same-era Raiden/Yelan Resolve-stack bug running in the _opposite_ direction — Yelan's burst mis-costed at 140 energy causing a double stack gain — which may be a distinct/earlier bug rather than a contradiction of this one, but the primary text itself is not directly confirmed here)
- **Test-for-us**: `effects[]` and `multiTarget` are already shipped on `AttackDefinition` (`attacks.ts:54,82`) with real consumers (`EffectsSystem.ts`; `HitboxSystem.ts:152`) — try pairing two different skills/characters whose effects are meant to interact (e.g. one move's effect entry is supposed to trigger a stack/counter another move reads) — does the interaction only work for the "obvious" pairing tested first, and silently no-op for a second valid pairing that reads the same shared field?

- **Scar**: The enemy "Eroding Avatar of Lava"'s "Rock Swings" attack had its damage-judgment timing (i.e., when the hit actually registers) out of sync with its animation, requiring a patch to adjust timing to match the visual. — Source: sportskeeda.com, "Genshin Impact 5.1 patch notes" ("The damage judgment timing of the skill 'Rock Swings' unleashed by the enemy 'Eroding Avatar of Lava' was adjusted to better match its animation.")
- **Test-for-us**: For an enemy move using this schema's `startupMs`/`activeMs`/`recoveryMs` phase split (feeding `EnemyAISystem.ts`), try comparing the animation clip's visible impact frame against the numeric phase boundaries that actually drive `HitboxSystem.ts` — does the hitbox window (derived from the schema's ms values) line up with what the animation shows on-screen, or can startup/active be authored independently of the animation asset with nothing catching the mismatch?

This project's own spec (`docs/MASTER_BLUEPRINT_v3.0.md`, `docs/agent-blueprint/05-per-move-property-schema.md`) — not how Genshin fixed any of the above — decides what "correct" looks like here; these scars only mark the failure-mode shape worth trying to reproduce against our schema.

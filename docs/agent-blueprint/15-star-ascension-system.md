# 15. Star Ascension System

> Category: Hero / Progression · Generated via gold-standard FILL + adversarial CB-lite verify (2 seats), 2026-08-07 · **revised after verify flagged an issue**.

### Scope

Owns the hero power layer that converts duplicate gacha pulls into a bounded stat/tier upgrade: the ★1–★N star tier per owned hero, the duplicate-consumption/ascension-threshold rule, and the per-star stat-multiplier table. Does **not** own: the gacha pull/rate mechanic itself (economy system), Hero Level or Skill Level progression (separate phase-1 layers per §4.2), combat stat resolution/damage math (combat system — this system only supplies the star-tier multiplier as an input), Ranked PvP match setup/normalization (a separate, later-phase system per §6 — this system only supplies the unnormalized star-derived stat delta it consumes), or Talent/Awakening/Equipment/Loot affixes/Set bonus (explicitly deferred, §4.2).

### Inputs/Outputs

- In: `ownedCharacter` (character_id, current `star` tier, duplicate/shard count) + a data-driven ascension table `{ star: number → duplicatesRequired: number, statMultiplier: number }`.
- Out: mutated `owned_characters` row (star tier incremented, duplicates consumed) + a `statsAtStar(character, star): CharacterStats` pure function consumed by the combat/PvP stat resolver.
- Shipped: `star`/`shards` columns exist on `owned_characters` with `owned_characters_star_range` (1-6) and `owned_characters_shards_nonnegative` (>=0) check constraints (`supabase/migrations/20260808204905_p9_star_ascension_server_authority.sql:4-21`), and `OwnedCharacter` (`src/types/player.ts:44-49`) carries matching optional `star?`/`shards?` fields (absent = ★1 / 0 shards for pre-P9 accounts). `Character`/`CharacterStats` (`src/game/characters.ts:34-40,42-63`) deliberately do **not** carry a star field — star is per-owned-copy save state on `OwnedCharacter`, not roster template data, and `statsAtStar(character, star)` (`src/game/heroes/starScaling.ts:18-29`) takes star as an explicit parameter instead.

### Dependencies

- **Economy** (gacha pull system — `src/game/gacha/`, server-authoritative `perform_gacha_pull` RPC, TASKS.md row 22 at 90%) — is the sole source of the duplicates this system consumes; a duplicate pull already grants into the same `shards` field this system consumes (`src/game/gacha/gachaService.ts:90`: `shards: (existing.shards ?? 0) + 1`).
- **Hero system** (`src/game/characters.ts`) — this system extends `Character`/`CharacterStats`, does not replace them.
- **Backend** (`src/data/accountRepository.ts` + Supabase `owned_characters`) — persistence of record.
- Feeds **Combat** (star multiplier is an input to stat resolution) and **PvP** (§3.8.5/§4.3: ranked normalizes Hero Level and Skill Level to baseline — star tier is the _only_ axis left creating a power gap, and that gap must stay ≤130%, ★6 vs ★1, per fork issue #35). PvP ranked-match setup itself is §6, a separate later-phase system not scheduled alongside this one — see Stay-current note for the integration item this dependency implies once PvP ships.

### Done-criteria

1. Ascension consumes the configured duplicate count and increments star tier by exactly 1 per threshold crossing — unit-testable against a mock `owned_characters` mutation.
2. ★1 kit is complete: no skill/effect definition is gated to star ≥2 — testable by asserting no skill config carries a star-gate below the hero's max unlocked-at-★1 set.
3. `statsAtStar(hero, 6).total / statsAtStar(hero, 1).total ≤ 1.30` at equal Level/Skill Level for every hero in `ROSTER` — a single parametrized test over the roster enforces §4.3's locked bound.
4. Star tier round-trips through backend persistence (save → reload → same tier).

### World-class bar

**Fire Emblem Heroes' Merge Allies system** (duplicate copies merge into the base unit, advancing a capped +1→+10 rank ladder with fixed, diminishing per-rank stat deltas rather than unbounded compounding). The pattern worth borrowing: the star ladder is **finite and its per-tier stat delta is a fixed lookup table, not a growing formula** — this is exactly what keeps §4.3's 130% bound provably true instead of re-derived per hero.

### Stay-current note

§4.2 explicitly defers Talent/Awakening/Equipment/Loot affixes/Set bonus; when any of those ship, §3.8.5's ranked-PvP normalization (which currently assumes star is the _only_ un-normalized power axis) will need revisiting to decide whether the new layer also gets baseline-normalized in ranked. Separately: when §6 Ranked PvP ships and exposes match setup, add an integration test there (not here) asserting Level/Skill Level normalize to baseline while the star-derived delta survives unnormalized — Star Ascension's own done-criteria (above) are satisfiable and testable without PvP existing, since PvP match setup is out of this system's scope.

### Low-maintenance-cost design

Per-star stat multiplier as a **plain data table**, not a formula or a generic "ascension engine" abstraction — this matches the project's own locked pattern: §5.1 states stage/chapter scaling is "consistent with the config-driven pattern already locked for gacha rates, star ascension, and skill-level scaling — never a hardcoded formula in code," and the existing hero data (`ROSTER` in `src/game/characters.ts:59+`) is already a flat static array, not a class hierarchy. Add `STAR_MULTIPLIERS: Record<number, number>` alongside it — no interface/factory for "ascension strategies," since there is exactly one ascension rule and no second implementation to justify one (YAGNI, per project ponytail/ECC style).

Exemplar used: Fire Emblem Heroes — Merge Allies system (same exemplar the file cites; no substitution needed)

A later adversarial pass flagged "Ascend Traits" as an unfamiliar FEH feature name from memory alone (not from re-checking the page) — that pass could not re-fetch the source to settle it (WebSearch budget exhausted, direct fetches to nintendoeverything.com and FEH Wiki mirrors returned 404/402 this session). Treat the incident and quote as solid; treat only the exact feature-name label as ⚠️ unverified until someone re-pulls the full patch-note context._
  **Test-for-us**: After an ascension mutates `star` tier and consumes duplicates, try reading the hero's displayed stats immediately (same session, no reload) and compare against a fresh `statsAtStar(character, star)` call / a save→reload — see whether any cached or stale UI stat value can diverge from what the pure function and persisted row actually say.

- **Scar**: Promoting a hero across a rarity/tier boundary (Unlock Potential, 4★→5★) silently zeroed all merge-level (+10) stat progress while other progression on the same hero (SP, skills, IVs, Dragonflower stat boosts) was retained — an inconsistent, undocumented-to-players retention rule across one state-transition operation. — Source: Fire Emblem Heroes Wiki / gamerant.com, "Unlock Potential, Explained (Upgrading Rarity)" — verified live: "When a unit's potential is unlocked, their level is reset to 1, and they lose any stats gained through Merging" / "An upgraded unit will keep their Skill Points (SP), skills, Individual Values (IVs), and Dragonflower enhancements."; corroborated by player.one
  **Test-for-us**: Try crossing a star-tier threshold (or any other hero state transition this system doesn't explicitly own, e.g. a future rarity/awakening bump per the Stay-current note) and check whether `star` tier, consumed-duplicate count, and any other per-hero progression all survive together — or whether one silently resets while others don't.

- **Scar**: A legitimate, intended consumption action (merging a duplicate into a target) could be silently blocked by a precondition the player didn't expect.   **Test-for-us**: Drive `ownedCharacter` into edge-case states (duplicate count exactly at the threshold, duplicate count one below/above threshold, star already at max, zero duplicates) and try to trigger ascension in each — check whether the system gives an unambiguous accept/reject with no silent no-op, and whether a duplicate can ever be consumed without the star tier actually advancing (or vice versa).

- **Scar**: A merge between two owned copies of the same hero, when one side was a lower rarity than the target, was not rejected — it silently completed as a _degraded_ outcome instead: the merge granted SP only, with no simultaneous stat boost, unlike a same-rarity merge. This is a different failure shape from the scar above — a silent partial-success with a lesser-than-expected result, not a rejected action — so it's called out separately rather than folded into the "silently blocked" bucket. — Source: new-guide.fire-emblem-heroes.com and serenesforest.net (rarity-mismatch merge behavior), per a live citation-check pass.
  **Test-for-us**: If two owned copies of the same character can ever differ along a merge-relevant dimension analogous to rarity (e.g. attempting to merge copies at different `star` tiers, if that's ever reachable before consolidation), try that merge and check whether the outcome the system actually delivers matches what it _tells the player_ it delivered — full effect, or an explicit, disclosed partial outcome — rather than quietly doing less than a normal merge with no signal distinguishing it from a full one.

- **Scar**: When two owned copies of the same hero each carried their own accumulated secondary progress (Dragonflower stat boosts) and were merged, the resolution rule discarded one side's accumulated progress outright (only the higher value carried over) rather than combining or erroring — an implicit, easy-to-miss data-loss rule at a merge/consume boundary. — Source: Fire Emblem Heroes Wiki, "Use Dragonflowers" — verified live: "only the higher amount of enhancements carries over to the resulting unit. The lower amount of enhancements is lost."; corroborated on a GameFAQs thread ("Do dragonflowers transfer over if merged into another copy?", confirmed to exist at gamefaqs.gamespot.com/boards/204447-fire-emblem-heroes/78147786). _Sourcing-quality flag, not a defect: the corroborating link is a user-generated forum thread, weaker footing than the official-FAQ/patch-notes/wiki sourcing used elsewhere in this doc — disclosed rather than hidden._
  **Test-for-us**: If `owned_characters` ever carries per-copy state beyond the shared duplicate/shard counter (e.g. two rows for the same character_id before consolidation, or any per-copy metadata), try ascending/merging them and check what happens to each side's individual state — confirm the consumption path either defines an explicit combine/keep rule or is structurally impossible to hit, rather than silently dropping one side.

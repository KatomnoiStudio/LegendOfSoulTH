# 25. Backend / Server-Authority System

> Category: Backend / Infra · Generated via gold-standard FILL + adversarial CB-lite verify (2 seats), 2026-08-07 · **revised after verify flagged an issue**.

### Scope

Owns: account persistence (auth/session), the player profile row and its child records (currency balances, owned characters, team slots, inventory, friends, battle history log), and the **server-authority enforcement mechanism** for currency/item/character grants — i.e. the boundary that decides what the client is allowed to write directly vs. what must go through a validated server transaction. Implemented today as two parallel repositories behind one function-export contract: `src/data/accountRepository.ts` (localStorage, non-authoritative, dev/offline path) and `src/data/accountRepository.supabase.ts` (Supabase Auth + Postgres, the live/production path — `src/hooks/useAuth.ts:2` imports the Supabase one). Does **not** own: combat resolution (client-simulated, no server validation of damage/hits), PvP matchmaking/rank/MMR authority (§8, netcode explicitly deferred to P12 per `AGENT_BLUEPRINT.md:75`), gacha roll logic (no RPC exists — #23), payment/monetization gateway (`topUpGold`/`topUpGems` are stubbed to always fail server-side, `accountRepository.supabase.ts:267-272`), or hero stat/progression formulas (owned by Progression System #14). Blueprint is explicit this is **not** a full game-authority backend — "Supabase work in repo is early seam toward this — not full game authority yet" (`docs/MASTER_BLUEPRINT_v3.0.md:481`).

### Inputs/Outputs

- Auth: `register(email, password)` / `login(email, password)` / `logout()` → `AuthResult = {ok:true, player: Player} | {ok:false, error: string}`.
- Session: `getSessionPlayer()` → `Player | null`; `getSessionEmail()` → `string | null` (sync, cached from `onAuthStateChange`, `accountRepository.supabase.ts:183-200`).
- Currency: `earnGold(uid, source: GoldSource, amount, refId?)`, `redeemCoupon(uid, code)`, `topUpGold/topUpGems(uid, packageId)` → `CurrencyResult = {ok:true, player, amount} | {ok:false, error}`. `GoldSource = 'quest'|'drop'|'topup'`, `GemSource = 'topup'|'coupon'` — enforced both in TS types and DB `CHECK` constraint `currency_source_match` (`supabase/migrations/0001_init.sql:76-80`).
- Items/characters: `grantItem(uid, itemId, quantity, source: ItemSource)`, `grantCharacter(uid, characterId)` → `ItemResult`/`CharacterGrantResult`.
- Read: `getTransactions(uid)` → `CurrencyTransaction[]`; `findPlayerByUid(uid)` → `FriendCandidate | null`; `savePlayer(player: Player)` → `boolean`.
- Local-only, no Supabase equivalent: `importSave(json)` (`accountRepository.ts:548`) has no counterpart in `accountRepository.supabase.ts` — that file only has a stubbed `exportSave` that always fails ("ฟีเจอร์นี้ใช้กับบัญชี Supabase ไม่ได้", `accountRepository.supabase.ts:333-334`). The two files do **not** currently export the same function set.
- Underlying Postgres contract (`supabase/migrations/0001_init.sql`, `0002_grant_character_rpc.sql`): `profiles`, `owned_characters`, `team_slots`, `inventory_items`, `friends`, `currency_transactions`, `battle_history` tables, all RLS-enabled, mutated only via `SECURITY DEFINER` RPCs `earn_gold`, `redeem_coupon`, `grant_item`, `grant_character`.

### Dependencies

- **Economy/Currency System** (#22) — shares this exact RPC/RLS layer; currency taxonomy is defined here.
- **Hero Collection / Gacha System** (#23) — will need a new RPC following this file's pattern once P9 lands; no RPC exists yet.
- **Progression System** (#14) — hero level/exp/star fields live in `profiles`/`owned_characters`, persisted via `savePlayer`.
- **Social System** (#28) — `friends`/`friend request` state lives in the same migration/schema (`public.friends`), read via `findPlayerByUid`.
- **PvP / Ranked System** (#19) — blueprint names rank/MMR as server-authoritative data (§8) but no rank/MMR table or RPC exists yet; this system is the seam it will attach to.
- Feeds into: every screen that reads `Player` (Lobby, TopBar, inventory, team builder) via `useAuth.ts`.

### Done-criteria

1. `accountRepository.test.ts` continues to pass and cover the local path (register/login happy-path, `earnGold` with invalid source/amount rejected, coupon double-redeem rejected) — this is the achievable scope today. Extending coverage to the Supabase path (`accountRepository.supabase.ts`) needs one of two undiscussed prerequisites named explicitly before it's scoped as done-criteria: (a) mock scaffolding for `@supabase/supabase-js` (none exists — zero test files reference `supabase` or `supabaseClient.ts`), or (b) a local Supabase instance via CLI/docker (no `supabase/config.toml` or local test setup exists). Pick one and scope a follow-up criterion once chosen; don't claim Supabase-path coverage against the current harness.
2. Direct `supabase.from('currency_transactions').insert(...)` from an authenticated client fails (no INSERT policy exists — verify against `0001_init.sql:91-115`, no `create policy ... for insert` on that table).
3. `earn_gold`/`grant_item` RPCs reject an out-of-taxonomy `source` (e.g. `earn_gold` with `source='coupon'`) with a raised exception, not a silent no-op. (Verifying this against a live/mocked RPC call has the same harness gap as #1 — same prerequisite applies.)
4. `accountRepository.ts` and `accountRepository.supabase.ts` do **not** currently export the same function set — `importSave` exists only locally (`accountRepository.ts:548`, used by `accountRepository.test.ts`); Supabase has no equivalent import path, only a stub `exportSave` that always fails. A shared `interface`/`satisfies` contract is still the right fix for the _rest_ of the surface (auth, session, currency, items, characters, reads), but it must explicitly exclude `importSave`/`exportSave` from the shared shape (or the Supabase file needs a real import path decided first) — otherwise the interface won't typecheck against `accountRepository.supabase.ts` as it stands today. Concrete deliverable: the shared interface, scoped to the functions both files can actually implement, both files typecheck against it (flagged in `AGENT_BLUEPRINT.md:85,101`).
5. `grep` for `.gold =` / `.gem =` / `.currency =` direct assignment outside `appendTransaction` (local) and the four RPC call sites (Supabase) returns zero matches — i.e. no new code path sets currency without a `source`.

### World-class bar

**Path of Exile** (Grinding Gear Games) — the genre's most cited example of an ARPG economy where the client never holds source-of-truth for currency or items; every currency/item-affecting action is a single server-validated transaction, client only renders state handed back to it. GGG's server-authoritative model is why dupe exploits, when they occur, get hotfixed as bugs rather than being structurally recoverable — not a claim that the model has been dupe-free; PoE has had multiple publicly-documented dupe exploits over its history, each patched at the server-validation layer rather than requiring a client update. The one pattern worth borrowing (and already the direction this repo took, just not finished): **no client-writable balance field, ever** — every mutation is a named, source-tagged RPC that the server validates and commits atomically, exactly what `earn_gold`/`grant_item`/`grant_character` already do. The gap vs. that bar isn't philosophy, it's coverage — gacha and PvP rewards don't have their RPC yet.

### Stay-current note

The dual-repository split (`accountRepository.ts` local vs. `.supabase.ts` production) will need revisiting once the local/localStorage path is no longer needed as a dev fallback or gets formally deprecated — right now nothing decides which one loads except which file `useAuth.ts` happens to import, and that's a manual switch, not an env-driven one. Also revisit `AGENT_BLUEPRINT.md` line citations in this contract if that file is edited again before this lands — line numbers drift.

### Low-maintenance-cost design

Keep enforcement **in the database, declaratively**, not duplicated as branching TS logic — the `currency_source_match` `CHECK` constraint (`supabase/migrations/0001_init.sql:76-80`) plus `SECURITY DEFINER` RPCs are already the single source of truth for "what's a legal currency mutation"; new grant types (e.g. a future gacha RPC) should extend that same constraint/RPC pattern rather than adding a parallel validation layer in the client. For the flagged local/Supabase drift, the fix is a shared `interface`/`type` contract scoped to the shared surface (excluding the `importSave`/`exportSave` asymmetry noted in done-criterion #4) — **not** a runtime repository-abstraction class or DI container. There are exactly two implementations and one is a dev fallback; per this repo's own YAGNI stance (`AGENT_BLUEPRINT.md:111` explicitly declines to scaffold anti-cheat/event-bus/repository-interface infra "ahead of need"), a type-level contract is the right-sized fix, not an interface abstraction neither implementation currently needs beyond typechecking.

### Known scars (real historical precedent)

- **Scar**: In Path of Exile 1, a client disconnect during a state-changing action (trade/drop) followed by a server rollback repeatedly produced duplicated items/currency; GGG's own community-acknowledged mitigation was a periodic offline "find dupes and delete" sweep run after the fact, not a transaction-time block — the exploit trigger (disconnects) couldn't even be fully attributed to deliberate abuse vs. accident. — Source: official Path of Exile forum, "Rollback fix will stop the dupes?" (pathofexile.com/forum/view-thread/3082955)
  **Test-for-us**: In our system, simulate a network drop / timeout right after an `earn_gold`/`grant_item`/`grant_character` RPC commits server-side but before the client receives the `{ok:true}` response, then have the client retry the same call (as a naive timeout-retry would). Check whether the retry causes a second grant, or whether the RPC path is actually idempotent/duplicate-safe under a lost-response scenario — don't assume "it's a `SECURITY DEFINER` RPC" alone proves this.

- **Scar** (⚠️ downgraded from the original draft — see note below): A Mirror of Kalandra duplication exploit was reported and hotfixed in Path of Exile 2 early access, but the specific mechanism, hotfix version, and any market-price impact are inconsistently reported across community sources and could not be pinned to a primary GGG source in this research pass. Two different exploit shapes show up in secondhand accounts — one describing vendoring 5 Mirror-of-Kalandra divination cards to duplicate the card stack (tied by a Reddit-sourced account to a hotfix labeled "0.1.0f Hotfix 3"), a separate one describing forced "instance crashing" during trades/crafting as grounds for later bans — and they disagree on the hotfix's own version string ("0.1.0f Hotfix 3" per one account vs. a YouTube video titled "0.1.1 HOTFIX 3"). No source could be located for the original draft's "~375 to ~234 Divine Orbs" price-crash figures — those numbers do not appear in any locatable source and have been **dropped as unverifiable/likely fabricated**, not softened. The original "aoeah.com, 'PoE 2 Mirror Dupe Glitch'" citation is also dropped: no URL was ever attached to it, no matching article could be located at that description, and the accompanying "corroborated by Steam Community discussions, YouTube coverage" clause is exactly the vague, unlinked pattern to flag rather than accept. — Source: ⚠️ unverified in this pass — no primary GGG patch-notes thread (pathofexile.com) or single corroborated article was located/confirmed; treat "a Mirror-dupe exploit existed and was hotfixed in PoE2 early access" as plausible-but-unconfirmed, and do not cite a specific mechanism, version number, or price figure until someone locates and links the actual GGG patch-notes thread.
  **Test-for-us**: Independent of this scar's citation problems, the failure _category_ it points at is real (confirmed by Scar 1 and Scar 3, and by common industry precedent): try racing two near-simultaneous requests against the same `uid` and the same balance-affecting RPC (e.g., two overlapping `grantItem`/`earnGold`/`redeemCoupon` calls fired back-to-back, or a call fired twice while a prior one is still in flight) and see whether both can land against the same pre-transaction balance snapshot — i.e., does concurrent/duplicate submission actually get serialized by DB-level locking, or is that only true in the happy path that's been manually tested so far? Treat this as a same-category test motivated by Scars 1 and 3, not as evidence this specific PoE2 incident happened as originally described.

- **Scar**: In Path of Exile 2, the unique "Freedom of Faith" Tablet stacked with specific Atlas tree nodes reduced a reward-reroll action's cost to zero, letting players reroll Ritual reward shops indefinitely and "print" high-tier currency (Divine Orbs, Mirrors) at effectively no cost — an interaction GGG's own QA hadn't caught. It was closed ~8 hours after public discovery; GGG banned roughly 300 accounts and clawed back the wealth generated, rather than the fix being invisible/silent. — Source: Vice, "Path of Exile 2 Studio Grinding Gear Games Is Banning Players Because of Their Own QA Fumble" (vice.com); corroborated by Sportskeeda and Gamepressure coverage of the same incident. (The "~8 hours" fix-time detail is not independently confirmed beyond this coverage, but isn't contradicted by anything found either — treat it as the one soft detail in an otherwise well-corroborated scar.)
  **Test-for-us**: Audit every place in our design (current and any near-future gacha/reward-reroll/discount feature per #23) where a "cost" or "consumption" check and the matching reward grant are two logically separate steps instead of one atomic server statement. Specifically try stacking every discount/bonus source that can legally apply to the same action at once and see whether the combined effect can drive the effective cost to zero while the reward-grant path still fires unmodified — the failure shape here isn't a classic dupe, it's a cost-and-grant pair that isn't atomic against modifier-stacking.

This project's own spec (`docs/agent-blueprint/25-backend-server-authority-system.md` Done-criteria, `docs/MASTER_BLUEPRINT_v3.0.md`) — not how GGG happened to fix any of the above — is what "correct" means here; these scars only say what shape of failure to go try to reproduce against our RPCs.

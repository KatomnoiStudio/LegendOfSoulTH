# 14. Progression System

> Category: Hero / Progression · Generated via gold-standard FILL + adversarial CB-lite verify (2 seats), 2026-08-07 · **revised after verify flagged an issue**.

### Scope

Owns the two implemented "simplified" layers of §4.2's `Hero Level → Star → Skill Level` chain: **Hero Level** (player-account level and per-owned-character level, both EXP-curve-driven) as it actually exists in `src/game/realtimeBattle/RewardSystem.ts:127-149` (`applyBattleExp`), plus the **Skill Level** layer that §4.2/AGENT_BLUEPRINT.md:85 locks architecturally and which, as of `feat(progression): P8 character progression system v0.12.0` (2026-08-07), is **fully implemented and shipped**: `skillLevels: SkillLevels` on `OwnedCharacter` (`src/types/player.ts:37`), EXP-based leveling via `SkillProgressionSystem.ts`'s `applySkillExp`/`getEffectiveLevels` plus cost-gated leveling via `progressionService.ts`'s `upgradeSkill()`, and UI in `HeroProgressionPanel.tsx`/`CharacterStats.tsx` — `TASKS.md`'s system #14 row and DF21 both show 🟢 graduated, 100% (2026-08-08). This entry's job going forward is: keep the Skill Level data model + level-up flow and Hero Level's EXP curve/formula centralized here as the system evolves. It does **not** own: Star Ascension (separate system #15, §4.3 — duplicate→star, its own cost table deferred to P9), reward/EXP _generation_ (`calculateBattleReward` in the same file is system #18, Reward System — this contract only consumes its `earnedExp` output), stage/difficulty tuning (#16), Equipment/Loot affixes/Set bonus (still deferred, §4.2), or PvP normalization logic (#20 — that system _reads_ this one's level/skill-level and overrides it to ranked baseline, it doesn't live here; this contract's job stops at exposing a readable shape, per Done-criterion #5 below). **Revised 2026-08-09 (item #7)**: Talent and Awakening are **un-deferred** and, unlike Skill Level below, already fully built end-to-end (`progressionSchema.ts`'s `TalentProgressState`/`AwakeningProgressState`, `progressionService.ts`'s `unlockTalent()`/`advanceAwakening()`, persisted live in `0008_progression_state.sql`) — this contract's own "not owned" list above no longer applies to them; they own the same slice of this system Skill Level does, UI just stays hidden (`showTalentAwakeningUi:false`) until ready to reveal.

### Inputs/Outputs

Currently shipped (Hero Level and Skill Level):

- **In**: `Player` (`src/types/player.ts:69-113`, has `level/exp/expToNext` at account root and per-`OwnedCharacter`), `earnedExp: number` from `BattleReward` (`RewardSystem.ts:15-19`).
- **Out**: new `Player` with account `level/exp/expToNext` bumped and the lead hero leveled the same way. The "lead hero" is **not** literally `teamSlots[0]` — it's the first non-null entry in `teamSlots`, resolved via `player.teamSlots.find((id): id is string => id !== null)` (`RewardSystem.ts:130`). If slot 0 is empty and slot 1 holds a hero, EXP silently goes to whoever occupies slot 1, not slot 0 — a real edge case worth a regression test if this logic is touched. Curve: `expToNext = max(1, round(expToNext * 1.2))` per level, capped at 20 level-ups per single EXP grant (`guard` loop, `RewardSystem.ts:111-117,138-144`) — this cap is a real, load-bearing safety valve, not incidental.
- **Skill Level** (shipped): `skillLevels: SkillLevels` (4 slots — `skill1`/`skill2`/`skill3`/`ultimate`, each `{level, exp, expToNext}`) on `OwnedCharacter` (`src/types/player.ts:12-23,37`), leveled via EXP through `SkillProgressionSystem.ts`'s `applySkillExp` and via cost-gated `upgradeSkill()` (`progressionService.ts:113-224`) resolved against `skillProgressionResolver.ts`/`SKILL_PROGRESSION_FIXTURES` (`progressionConfig.ts:77-146`), and already mirrored into Supabase as `skill_levels`/`talent_state`/`awakening_state` columns (`src/data/accountRepository.supabase.ts:454-456,598-600`, `0008_progression_state.sql`) — the local/Supabase hand-mirror-with-no-shared-type gap flagged under system #25 remains a real standing risk for _future_ fields, but this one is already mirrored on both paths today.

### Dependencies

- **Feeds from**: Reward System (#18, `RewardSystem.ts` `calculateBattleReward`) and transitively Stage/Adventure System (#16, §5.1) — battle clears are the only EXP source today.
- **Feeds into**: PvP Power Normalization (#20, §3.8.5) — ranked matches override Hero Level and Skill Level to a fixed baseline, leaving only Star as the power-gap axis; Hero Collection (#13, §4.1) — `OwnedCharacter` entries this system levels are created there.
- **Sibling, not dependency**: Star Ascension (#15) — same §4.2 chain, independent duplicate-driven axis, no data coupling today.
- **Backend/Server-Authority (#25)**: both local (`accountRepository.ts`) and Supabase (`accountRepository.supabase.ts`) paths must persist level/exp identically; no shared interface enforces this yet.

### World-class bar

Named exemplar already locked into this project's own blueprint: **Summoners War's Arena normalization** (§3.8.5, `docs/MASTER_BLUEPRINT_v3.0.md:365`) — "the standard ranked-arena pattern in gacha PvP... normalizes level so rarity/investment differences are the only intended axis." The one pattern worth borrowing: normalize Hero Level and Skill Level to a ranked baseline for PvP matches only, leaving Star (the bounded, intentional gap per §4.3) as the sole axis of separation — PvE progression stays untouched. This is already the locked design; the implementation gap is making Skill Level exist at all so there's something to normalize.

### Low-maintenance-cost design

Keep the level-up curve minimal per level-type rather than adding a `LevelCurveStrategy` interface. Account-level EXP (`applyAccountExp`, `RewardSystem.ts`) and Skill Level EXP (`SkillProgressionSystem.ts`'s `applySkillExp`) both still use the `expToNext * 1.2` formula constant. Per-character Hero Level EXP (`heroExpService.ts`, reached via `progressionService.applyHeroExp` — the current path for Dungeon rewards, since `applyBattleExp` is now legacy/`LobbyBattleSession`-only) intentionally uses a **table+formula curve** instead (`PLACEHOLDER_HERO_EXP_TABLE` for Lv1-10, then `10n²+10n+100` for Lv11+ — Ring-0-locked P8 balance lock, MEMORY.md 2026-08-09, fixing a non-monotonic seam the old `*1.2`-everywhere formula had at the Lv10/Lv11 boundary). So this is two curve _shapes_ across three call sites, not one — still not worth a strategy-interface abstraction (matches this repo's existing config-driven-only-where-values-actually-vary pattern, e.g. `stageConfig.ts`'s per-enemy data tables vs. the hardcoded-formula curve here). When Skill Level lands, resist adding a generic "leveling strategy" interface for two nearly-identical curves (Hero Level, Skill Level) — inline both as plain functions first; only extract a shared helper once a third curve or a real divergence appears (YAGNI, consistent with `RewardSystem.ts` already being pure/dependency-free by design, line 12).

### Known scars (real historical precedent)

- **Scar**: A bug in Summoners War: Sky Arena's ranked Arena stopped losses from being recorded against a player's rank, so a losing match still left the rank/rating state showing a win — players discovered they could grind an artificial ~99-100% "win rate." Treat any claim of an official Com2us response as unverified pending that primary source. — Source: Com2us official forum thread "Summoners War huge bug - arena 100% win rate" (Feb 19, 2018) — title/date only, not directly read; bug existence/virality corroborated via the YouTube titles and blog post above (three independent hits, not a single unconfirmed source; the _response_ sub-claim specifically has zero corroboration and should not be treated as established).
  **Test-for-us**: Once PvP Power Normalization (#20) exists and reads this system's `getEffectiveLevels()`-style output, deliberately force a ranked-match loss (including a mid-match disconnect/client-kill) and check whether the outcome actually gets written back to whatever rank/rating state consumes it downstream — try to find any code path where a loss's write can be skipped, retried into a no-op, or raced by a duplicate "win" read of the same match.

- **Scar** (⚠️ different but closely related title — Summoners War: Chronicles, not Sky Arena; Sky Arena's own skill-up mechanic had no well-documented public incident found): An error in the "Expedition" content let players illegitimately farm skill points and rare progression items ("Magician's Research Journals"). - **Scar** (⚠️ weakly documented — single unconfirmed player report, no visible official acknowledgment or fix; different title, Summoners War: Chronicles): A player reported their account's EXP bar displaying as "max" at level 60 while unable to advance to level 61 — the displayed progression state and the actual level-up outcome disagreed, with no resolution visible in the thread. — Source: Summoners War: Chronicles official forum, player report by user "×ZeruweL×" (May 15, 2023, community.summonerswar.com/chronicles/eng-gb/board/24/33671, directly fetched — poster handle, date, and content verified against the live page). Feed it an `earnedExp` value large enough to blow past that cap in one grant and check whether the resulting `exp`/`expToNext` display and the actual `level` field end up consistent — i.e. confirm the UI never shows "maxed"/near-max EXP for a character whose `level` field didn't actually advance because the guard cut the loop short.

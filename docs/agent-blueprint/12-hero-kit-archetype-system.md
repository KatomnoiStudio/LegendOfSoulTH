# 12. Hero Kit / Archetype System

> Category: Hero / Progression · Generated via gold-standard FILL + adversarial CB-lite verify (2 seats), 2026-08-07 · **revised after verify flagged an issue**.

### Scope

Owns the data-driven definition of each hero's moveset (basic 3-hit combo + S1/S2/S3/ultimate) and the archetype-specific targeting/effect resolution rules that let non-melee kits (Support/Ranged/Summoner/Control) reuse the same combat schema instead of forking code (blueprint §3.7, §3.8). It does **not** own: the enemy/boss AI state machine itself (§3.6.8 — hero kit only feeds a `summon` effect into it per §3.8.3), gacha/star-ascension math, PvP matchmaking, or skill-button UI (`src/components/BattleScene/*`). Currently shipped scope is narrower than the locked design: only one hero (Monkey King, melee/Fighter) has a real kit; Support/Ranged/Summoner/Control are design-locked resolutions with **zero implementing code**.

### Inputs/Outputs

- In: `characterId: string` → `getRealtimeSkillKit()` → `RealtimeSkillKit { characterId, skill1, skill2, skill3, ultimate: RealtimeSkillDefinition }` (`src/game/realtimeBattle/skills.ts:18-35`).
- Each `RealtimeSkillDefinition` wraps an `AttackDefinition` (`src/game/realtimeBattle/attacks.ts:15-42`): timing (`startupMs/activeMs/recoveryMs`, combo window), `damageMultiplier`, `range`, `hitShape: 'horizontal'|'radial'`, `arcDegrees`, `depthTolerance`, `knockback`.
- Out: consumed by `HitboxSystem`/`DamageSystem`/`ComboSystem`/`SkillSystem` (`src/game/realtimeBattle/*.ts`) to resolve hits against enemy entities.
- **Not yet real**: `castDelayMs`, `interruptible`, `movementDuringCast`, `knockdown`, `multiTarget`, `effects[]` (heal/buff/cc/summon), `targetLock`, `lungeDistance`, `hitstunMs` — all locked as required fields by §3.6.7/§3.6.12/§3.7 but absent from the actual `AttackDefinition` interface today.

### Dependencies

- **Depends on**: combat/hitbox-damage-combo runtime (`src/game/realtimeBattle/`) as its consumer; enemy system for the summon effect's reused state machine (§3.8.3 — summons run enemy AI's `Idle→Chase→Telegraph→AttackActive→Recovery`); hero/progression system for Hero Level/Skill Level scaling feeding `attacker.atk` (§3.8.5 design lock, **not yet implemented** — grepping `src/` for `skillLevel`/`heroLevel` returns zero hits and no progression module exists; `damageMultiplier` itself is a fixed per-move constant in `attacks.ts`, e.g. `MONKEY_GOLDEN_FURY`'s `2.4`, per `DamageSystem.calcDamage`: `base = attacker.atk * attack.damageMultiplier * variance` — any future level scaling would feed `atk`, not `damageMultiplier`).
- **Feeds**: pvp system, which must normalize Hero Level/Skill Level to ranked baseline before applying this system's kit data (§3.8.5/§6.2 design lock, **not yet implemented** — no PvP module exists anywhere in `src/`) — this system does not enforce that normalization itself.

### Done-criteria

1. `AttackDefinition` gains `castDelayMs`, `interruptible`, `movementDuringCast`, `knockdown`, `multiTarget`, `effects[]`, `targetLock`, `lungeDistance`, `hitstunMs` per §3.6.7, defaulted to §3.6.12's baseline table (e.g. `lungeDistance` 32/36/44, `hitstunMs` 200), without breaking `HitboxSystem.test.ts` — the test file that actually constructs literal `hitShape`-bearing `AttackDefinition` objects and is the one at risk from new required fields.
2. A type/test guarantees every entry in `REALTIME_CHARACTER_KITS` has all 4 slots populated (skill1/skill2/skill3/ultimate) — enforces §4.3 "★1 fully playable."
3. Only kit entries explicitly marked `targetLock: 'nearest'` auto-acquire a target; a test asserts Monkey King's ultimate has it and S1/S2/S3/basic do not (§3.7 "not a global assist").
4. Adding a second, non-melee hero (e.g. Ranged) requires only a new kit entry + `AttackDefinition` rows (`lungeDistance≈0`, longer `range`, reusing the existing `hitShape: 'horizontal'` value rather than adding a new shape) — zero edits to `SkillSystem.ts`/`HitboxSystem.ts`/`DamageSystem.ts` (proves §3.8.2's "data difference, not architecture gap" claim; a new `hitShape` union member would itself force editing `HitboxSystem.findHitTargets`'s hard branch on `hitShape`, violating "zero edits").
5. A `singleAlly`/`allAllies` effect resolves to `self` when no ally entity is on field — unit test with zero allies present (§3.8.1).

### World-class bar

**Genshin Impact** (miHoYo) — named directly in blueprint §3.7 (ultimate strike-phase lock/hyper-armor convention, shared with Star Rail) and §3.8.2 (bow/catalyst basics reuse the same startup→active→recovery machine as melee, varied only by `lungeDistance`/`range`/`hitShape`). The pattern worth borrowing, already locked as the target: **one state machine, N archetypes via data, never a per-archetype subclass**.

### Stay-current note

The "per-hero kit file pattern" is named in the blueprint (line 308) but today is one file (`skills.ts`) with a single `Record` entry — as the roster grows past a handful of heroes this will plausibly need splitting into literal per-hero files to stay navigable; not urgent at n=1.

### Low-maintenance-cost design

Keep the existing single-source-of-truth rule already stated in the file's own header comment (`attacks.ts:1-5`: "ค่าจังหวะทุกตัวอยู่ในไฟล์นี้ไฟล์เดียว ห้ามกระจายไปเขียนใน component หรือใน system") — all balance numbers live in `attacks.ts`/`SKILL_CONFIG`, never duplicated into components or systems. Extend archetypes the same way §3.8.2 mandates: **data variation on the existing `AttackDefinition` shape, not a new interface per archetype** (no `IRangedAttack`/`ISupportAttack`). This is the project's established YAGNI stance — §3.8.2 explicitly rejects a new per-move property for Ranged, and nothing here justifies breaking that with premature polymorphism for a one-hero roster.

### Known scars (real historical precedent)

- **Scar**: Yae Miko's Elemental Skill (Sesshou Sakura turrets) was changed in patch 2.6 from random targeting to "nearest enemy" targeting. This made target selection unpredictable — players "found themselves unable to tell which enemies would sit on the receiving end of the attacks" — and, because nearest-enemy selection concentrated hits on whatever was closest instead of spreading across the field, it reduced the number of distinct enemies actually taking damage compared to the old random targeting. It was a coverage/value nerf, not a targetability-deadlock bug: miHoYo reverted the change and paid 100 Primogem compensation. — Source: ScreenRant, "Genshin Impact Fixes Yae Miko Nerf After Backlash" (https://screenrant.com/genshin-impact-yae-miko-nerf-fix-sesshou-sakura/); GamingBolt, "Genshin Impact Update Coming Today, Reverts Yae Miko's Sesshou Sakura Targeting Change" (https://gamingbolt.com/genshin-impact-update-coming-today-reverts-yae-mikos-sesshou-sakura-targeting-change)
- **Test-for-us**: For any kit entry with `targetLock: 'nearest'` (Done-criteria #3), place multiple valid enemies at different distances and check two things: (1) whether the player can predict/read which enemy is about to be hit, or whether "nearest" flips silently as enemies shuffle position mid-fight, and (2) whether "nearest" targeting quietly reduces total value delivered on a multi-enemy pull — e.g. repeatedly re-hitting one close enemy instead of spreading effect coverage the way a non-"nearest" mode would — since a targeting mode can be a functional nerf without ever failing to find a target at all.

- **Scar**: Raiden Shogun's burst (Chakra Desiderata) was supposed to gain "Resolve" stacks whenever any party member cast their own Elemental Burst, but a bug silently broke stack accumulation specifically when Yelan was the triggering caster — it went unnoticed until players reported it, and miHoYo had to acknowledge the bug and compensate affected players. — Source: Sportskeeda, "Genshin Impact developers to compensate players with 100 Primogems for Raiden Shogun kit bug in 2.7" (https://www.sportskeeda.com/esports/genshin-impact-developers-compensate-players-100-primogems-raiden-shogun-kit-bug-2-7); Gurugamer, "Gets 100 Primogems For Raiden Shogun Kit Bug Compensation" (https://gurugamer.com/mobile-games/raiden-shogun-kit-bug-compensation-20566)
- **Test-for-us**: Once `effects[]` (heal/buff/cc/summon, per §3.6.7) can be triggered by one entity's action feeding a resource/stack onto a _different_ entity, test that trigger path per distinct source — e.g. if a support hero's ultimate is meant to grant stacks/buffs whenever _any_ ally casts a skill, verify it separately for each ally archetype/kit rather than assuming one working caster proves the cross-entity link works for all of them.

- **Scar**: Genshin's per-attack startup→active→recovery timing (the same three-phase shape this project's `AttackDefinition` uses) can be interrupted mid-recovery by a dash/jump input, letting players skip the recovery window entirely to reset combos for extra damage and cancel Elemental Burst end-lag to farm energy particles for free — a community-documented, patch-surviving interaction known as "animation canceling." — Source: TheGamer, "How To Animation Cancel Effectively In Genshin Impact" (https://www.thegamer.com/genshin-impact-animation-canceling-explained-guide/); BitTopup News, "Animation Canceling Guide: Double Your Genshin DPS Instantly" (https://news.bittopup.com/news/animation-canceling-guide-double-your-genshin-dps-instantly)
- **Test-for-us**: Once `interruptible`/`movementDuringCast`/`castDelayMs` land on `AttackDefinition` (Done-criteria #1), try interrupting an attack's recovery phase with the next queued input (dash, dodge, next combo hit) and check whether the combo window/hitstun/knockback resolve as intended once, or whether any per-use effect (damage tick, resource/energy gain, summon spawn) can be triggered more than once per actual cast by chaining the interrupt.

- **Scar**: Separate from the Yae Miko case, Genshin's auto-lock for Elemental Skill/Burst targeting has been criticized as a recurring combat problem where proximity silently overrides the player's own aim: Venti will "lock on to the wrong enemy despite facing his intended target" when casting his Burst; wide single-direction attacks like Diluc's Burst can whiff because "it becomes easy for auto-aim to fail" on that shape of attack; and mobile enemies like Abyss Mages — which "can teleport to and away from an attack" — can pull a lock-on away from where the player was actually aiming mid-cast. — Source: ScreenRant, "Genshin Impact's Biggest Combat Issue Is Auto-Lock" (https://screenrant.com/genshin-impact-auto-lock-target-combat-bad-fix/)
- **Test-for-us**: With a `targetLock`-ed cast in flight, introduce a second enemy that becomes nearer/more "eligible" than the one the player is visibly facing/aiming at (or have the original target teleport/reposition, for any future enemy with a blink-style move) and check whether target resolution silently re-locks onto the new nearest candidate instead of respecting the player's original facing/aim — i.e. whether proximity can override player intent and produce a "miss" the player didn't choose, not just whether a lock ever fails to resolve at all.

Note: none of the above prescribes how Genshin fixed these — only what broke, mechanically. What "correct" looks like for the Hero Kit / Archetype System here is defined entirely by this project's own `docs/MASTER_BLUEPRINT_v3.0.md` and `docs/agent-blueprint/12-hero-kit-archetype-system.md` (its Done-criteria above are the actual bar); the exemplar only points at what kind of scenario is worth trying.

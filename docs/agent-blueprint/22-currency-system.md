# 22. Currency System

> Category: Economy · Generated via gold-standard FILL + adversarial CB-lite verify (2 seats), 2026-08-07 · **revised after verify flagged an issue**.

### Scope

Owns the player's `PlayerCurrency` balance (`gold`, `gem`) and its append-only audit trail (`CurrencyTransaction[]`), plus the one rule that makes the trail meaningful: every balance change is a transaction with a declared `source`, and `appendTransaction` is the function that touches `player.currency` for every mutation _after_ account creation (`src/data/accountRepository.ts:214` comment: "จุดเดียวที่แก้ currency ได้"). The one documented exception is `createNewPlayer` (`accountRepository.ts:387`), which sets `currency: { gold: 500, gem: 20 }` directly for a brand-new account — no `CurrencyTransaction` is logged for the starting balance, and the code's own comment at lines 384-386 calls this out explicitly ("ข้อยกเว้นเดียวที่ตั้งค่าทอง/หยกตรง ๆ ได้", the one exception that sets gold/gem directly). It owns `earnGold`, `topUpGold`, `topUpGems`, `redeemCoupon`, `getTransactions` (`accountRepository.ts:631-746`) and coupon anti-replay/quota logic. It does **not** own: deciding _how much_ gold a kill/quest/stage is worth (that's Reward System, #18 — `RewardSystem.ts` computes amounts but has no caller of `earnGold` yet, confirmed by its own comment "ไม่แตะคลังทอง/ไอเทม (ทองต้องผ่าน earnGold...)" at `RewardSystem.ts:94`); item inventory (`grantItem`/`InventoryItem`, a sibling system with the same source-provenance pattern but a separate table); real payment processing (topUp "succeeds" unconditionally, no gateway — `accountRepository.ts:35`); or gacha currency spend (Gacha System, #23, not built).

### Inputs/Outputs

```
type GoldSource = 'quest' | 'drop' | 'topup'
type GemSource  = 'topup' | 'coupon'

interface CurrencyTransaction {
  id: string; currency: 'gold' | 'gem'; source: GoldSource | GemSource
  amount: number; createdAt: string; refId?: string
}

type CurrencyResult =
  | { ok: true; player: Player; amount: number }
  | { ok: false; error: string }

earnGold(uid, source: GoldSource, amount: positive int, refId?) -> CurrencyResult
topUpGold(uid, packageId: string)  -> CurrencyResult   // packageId ∈ GOLD_PACKAGES
topUpGems(uid, packageId: string)  -> CurrencyResult   // packageId ∈ GEM_PACKAGES
redeemCoupon(uid, code: string)    -> CurrencyResult
getTransactions(uid)               -> CurrencyTransaction[]  // oldest→newest
```

Side effect: `Player.currency.{gold,gem}` mutated and one `CurrencyTransaction` appended, atomically, per call (`accountRepository.ts:214-234`) — except the `createNewPlayer` starting-balance exception noted in Scope, which has no transaction. `PlayerCurrency` shape at `src/types/player.ts:6-9`.

### Dependencies

- **Backend/Server-Authority System (#25)**: two parallel implementations satisfying the same exported names — `src/data/accountRepository.ts` (localStorage) and `src/data/accountRepository.supabase.ts` (Supabase, `earnGold`/`redeemCoupon`/`grantItem` via `SECURITY DEFINER` RPC per `accountRepository.supabase.ts:34`; `topUpGold`/`topUpGems` have **no RPC yet** and are stubs pending "fork issue #19" per `accountRepository.supabase.ts:37,266`).
- **Adventure/Reward System (#18)**: upstream producer of gold _amounts_ — not yet wired to call `earnGold` (dead link, confirmed both in `RewardSystem.ts:94` and `.agents/rules/currency-ledger-retention.md:18`).
- **Gacha System (#23)** and **Monetization/Shop System (#24)**: downstream consumers — `CurrencyShopModal.tsx` takes an injected `onBuy` callback rather than calling `topUpGold`/`topUpGems`/`redeemCoupon` itself; it's `App.tsx` that imports the real functions and wires them down through props. Gacha will need a "spend gold/gem" path that doesn't exist yet.
- No dependency on Combat/Hero/PvP systems directly.

### Done-criteria

- `grep -n "player.currency" src/data/accountRepository*.ts` shows mutation only inside `appendTransaction` (local) / the RPC boundary (supabase) — no other function assigns `currency.gold`/`currency.gem` directly. **Note:** this grep does not catch the `createNewPlayer` exception (Scope) — that line reads `currency: { gold: 500, gem: 20 },`, not `player.currency = ...`, so it won't match the pattern. Treat that path as a known, accepted exception rather than something this check verifies; if a stricter guarantee is ever wanted, the check needs to also assert `createNewPlayer` is the only other currency-setting site.
- `earnGold` rejects `amount <= 0` or non-integer amount (`accountRepository.ts:637-639`) — currently **untested**: `src/data/accountRepository.test.ts` has zero `earnGold`/`redeemCoupon`/`topUpGold`/`topUpGems` cases (grep confirmed). A pickup task should add unit tests for: reject bad amount, duplicate coupon rejected per-account, `maxRedemptions` enforced cross-account, `getTransactions` ordering.
- `redeemCoupon` duplicate-redemption and `maxRedemptions` checks (`accountRepository.ts:711-727`) pass equivalent tests on both local and supabase implementations (supabase enforces server-side per its RPC per file header, but no test currently pins that either).
- Local/Supabase parity: same `CurrencyResult` shape for every implemented function; `topUpGold`/`topUpGems` on Supabase intentionally return `{ok:false}` until RPC exists — a done-criteria check must not flag that as a bug, only confirm the error path is graceful (`CurrencyShopModal` shows the error, doesn't crash).
- If/when this pickup wires `earnGold`/`grantItem` to an automatic gameplay trigger (quest/drop/battle-end), the archive pattern in `.agents/rules/currency-ledger-retention.md` lands in the **same PR**, not after.

### World-class bar

**Path of Exile's currency-as-item / stash-tab audit model.** PoE never lets any code path silently mint or vanish currency — every orb gain/spend is a discrete, sourced, replayable event, which is exactly the shape this project already independently arrived at (`GoldSource`/`GemSource` tagging + append-only `CurrencyTransaction[]`, `accountRepository.ts:214`'s "single choke point" comment). ⚠️ unverified: PoE's specific reconciliation mechanics (client/server authority split, reconnect behavior) aren't sourced here and shouldn't be asserted as a named exemplar detail without a citation — drop the mechanism claim and keep the general principle: never trust a purely local delta once a server ledger exists, always reconcile against it. That's the gap worth closing in this project, not the transaction-log design itself (which is already sound).

### Stay-current note

The moment `earnGold`/`grantItem` get wired to an automatic trigger (quest complete, enemy drop), the unbounded `CurrencyTransaction[]` in local storage stops being a "not a real problem yet" — `.agents/rules/currency-ledger-retention.md:10-12` already measured the failure mode (~20ms per write, ~34,000-transaction ceiling on a 5–10MB `localStorage` quota) and pre-decided the fix pattern (archive, never delete; never touch `source==='coupon'|'topup'` entries). This is the one plausible near-term churn point, everything else about the taxonomy (`gold` soft / `gem` premium, source-tagged provenance) is stable.

### Low-maintenance-cost design

The system's real strength is that it has **no premature abstraction to preserve**: one function (`appendTransaction`) is the sole write path for every post-creation mutation, both the local and Supabase implementations are plain modules exporting the same function names rather than a shared `interface`/class hierarchy (matching this repo's documented swap pattern at `accountRepository.ts:14-17`, "เปลี่ยน import ที่ src/hooks/useAuth.ts จุดเดียว หน้าจอไม่ต้องแก้เลย" — swap the import, not an injected abstraction). Keep it that way: don't introduce a `CurrencyService` interface or DI layer for "future backends" — YAGNI per this project's own `proven-good-do-it-now.md` standard, cited verbatim by the retention rule itself (`currency-ledger-retention.md:23-24`) to justify _not_ building a ledger cap today. The single genuine gap worth a typed contract (already flagged, not yet acted on) is that `accountRepository.ts` and `.supabase.ts` hand-mirror exported signatures with nothing catching drift if one gains a new export (`AGENT_BLUEPRINT.md:85`, restated at `:101`) — that's the one structural addition worth making, and only a `satisfies`/shared type check, not a runtime abstraction.

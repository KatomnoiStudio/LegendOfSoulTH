# 19. PvP / Ranked System

> Category: PvP · Generated via gold-standard FILL + adversarial CB-lite verify (2 seats), 2026-08-07 · **revised after verify flagged an issue**.

### Scope

Owns: the ranked 1v1 PvP loop end to end — hero select for the match, matchmaking queue (rank/MMR band matching with expansion), the match itself (reusing PvE's realtime combat core), win/lose resolution, and rank/MMR update. Owns applying the "ranked baseline" normalization (Hero Level + Skill Level forced to max for match duration; only star tier still creates a power gap) per blueprint §3.8.5/§6.2. Does NOT own: the combat tick/hit/damage engine itself (that's `src/game/realtimeBattle/*`, reused not forked), hero/skill data or star-ascension math (hero system), account/currency/session persistence pattern (backend system, `src/data/accountRepository.ts`), or PvE stage/adventure content (adventure system). Not built yet — blueprint marks it P12 (prototype) / P13 (matchmaking/rank), explicitly "later phase" (`docs/MASTER_BLUEPRINT_v3.0.md:446`, `:511-512`), and repo-wide search confirms zero PvP/rank/MMR/matchmaking code exists under `src/` today.

### Inputs/Outputs

- In: `{ playerUid, selectedHeroId, currentMMR, currentRankBand }` → queue join request.
- Queue engine output: `{ opponentUid, opponentHeroId, matchSeed }` once matched within band, or band-expanded after a wait threshold (thresholds themselves deferred to P13, `docs/MASTER_BLUEPRINT_v3.0.md:459`).
- Into combat core: both heroes' stats **post-normalization** (Level/SkillLevel clamped to ranked baseline, star tier passed through unmodified) — shape matches whatever `RealtimeBattleRuntime`/`createRealtimeBattle` in `src/game/realtimeBattle/` already accepts (no new battle-state shape to invent).
- Out of match: `{ winnerUid, loserUid, durationMs }` → rank/MMR update function → `{ newMMR, newRankBand, rankDelta }`, persisted via the same repository-swap pattern as `src/data/accountRepository.ts` (a `rankRepository` with a local impl now, Supabase impl later, one import swap point).

### Dependencies

- **combat** (`src/game/realtimeBattle/*`) — hard dependency, reused as-is for the actual fight; PvP does not reimplement movement/hitbox/damage/combo systems.
- **hero** — hero stats, Level, Skill Level, star tier as normalization inputs (§3.8.5).
- **backend** — server-authoritative MMR/rank storage once real (§8: "rank, MMR → server authority"); local dev seam follows the `accountRepository.ts` local→Supabase swap pattern.
- **economy** — none identified; §7's monetization rule ("Must not: sell best power primarily via direct purchase") is written generally and never mentions PvP, but extends naturally here — no gold/gem coupling beyond maybe cosmetic rewards (TBD, not in scope now).
- Feeds into: none yet (no season/leaderboard system exists to consume PvP output).

### Done-criteria

1. Two hero loadouts with different Level/Skill Level but same star tier enter a ranked match and combat-log/state shows both normalized to identical effective Level+SkillLevel before first hit resolves (regression test pinning §3.8.5).
2. Star-tier gap in a normalized match stays within the existing ★6 ≤ 130% ★1 bound (§4.3/§6.2, fork issue #35) — assert via existing power-gap test fixture if one exists, else new test computing effective power at both star extremes post-normalization.
3. Queue matches two players within the same rank band before expanding search; a test simulates a queue with only far-band opponents available and asserts no match until expansion fires.
4. Match result writes exactly one rank/MMR update per completed match (idempotent — resubmitting the same match result must not double-apply delta), mirroring the currency-ledger no-silent-mutation discipline already enforced in `accountRepository.ts`.
5. PvP win/loss never mutates PvE progression state (hero XP, currency) — assert player record's PvE fields are byte-identical pre/post a ranked match.

### World-class bar

The blueprint's own §3.8.5 (`docs/MASTER_BLUEPRINT_v3.0.md:364`) names "Summoners War's arena" as the inspiration for normalizing level/skill so star/rarity is the only intended power axis. That citation should be treated with caution here rather than repeated as verified precedent: checked against how Summoners War's Arena and Guild War actually work (rune guides, stat-scaling references, Guild Battle docs), the game does **not** normalize hero level, skill level, or rune investment in either mode — rune grinding is exactly what drives PvP power there, and it's the game's best-known source of grind pressure. So there's nothing to borrow from Summoners War's live implementation specifically, and no basis for a claim about how it's built server-side — that would be fabricating an implementation detail behind a mechanic that doesn't exist. A better-fitting, actually-documented analog for "normalize investment so only kit/deck-building differentiates" is Clash Royale's tournament/challenge mode, which caps card level for exactly that reason.

The requirement that matters for this contract doesn't need a borrowed exemplar anyway — it's already locked by this project's own blueprint: §8 states "rank, MMR → server authority" for valuable data, and normalization inputs (Level, Skill Level, star tier) feed that same rank outcome. So the normalization function must live behind the server-authority boundary §8 already mandates, computed at match start from server-held hero data — not trusted from a client-submitted payload a modified client could forge.

### Stay-current note

The Elo/tier/K-factor numbers and queue-expansion thresholds are explicitly deferred tuning parameters, not architecture (§6.2, fork issue #39) — expect these to be revisited repeatedly post-launch based on real queue-time/win-rate telemetry, unlike the rest of this contract.

### Low-maintenance-cost design

Follow the same pattern `accountRepository.ts` already establishes and documents inline (`src/data/accountRepository.ts:11-17`): one `rankRepository` module with a local/in-memory implementation now, swapped for a Supabase implementation later at a single import site (`useAuth.ts`-style), never an `IRankRepository` interface with two concrete classes built up front — YAGNI until the second implementation is actually being written. Keep Elo/K-factor/band-width as plain data constants (not a "MatchmakingStrategy" abstraction) since exactly one ranked mode is LOCKED (§6.1: "no separate Casual/Normalized modes at launch") — a pluggable-strategy layer for modes that don't exist yet is premature abstraction this codebase's own style (ECC + repo's existing single-impl-until-needed repository pattern) argues against.

Exemplar used: Clash Royale (Supercell) — specifically its tournament/challenge-mode level normalization. This is the exemplar the file's own "World-class bar" section already substitutes in, after debunking the blueprint's original "Summoners War's arena" citation as not actually normalizing anything in live play. **This research additionally extends the same exemplar to Clash Royale's ranked ladder/trophy (MMR) system** for the queue/rank/MMR scars below (scars 2 and 3) — that extension is this research's own scope choice, made because this system's done-criteria 3–4 cover queue/rank/MMR directly; it is not a claim that the file's World-class bar section itself already endorsed the ladder/MMR side.

### Known scars (real historical precedent)

- **Scar**: A July 2024 Clash Royale exploit let players field duplicate copies of the same card and use special/event-exclusive cards (Super Archers, Santa Hog Rider, Super Magic Archer) that should have been unavailable or capped — Supercell posted on X warning that using the exploit could result in account suspension. ⚠️ **Partially unverified — four specifics dropped**: the original draft of this scar also claimed the exploit hit specifically the **Global Tournament** mode, involved "eight Little Prince" duplicates, that Supercell "ran maintenance," and that the tournament was "re-run for everyone the following week." None of those four could be corroborated this session: the two originally-cited X/Twitter status URLs return HTTP 402 (paywalled) on every fetch attempt, have no Wayback Machine snapshot available, and the one independently fetchable secondary source (Sportskeeda) describes the exploit hitting "regular game modes" — not Global Tournament specifically — and does not mention Little Prince, maintenance, or a re-run. Those four claims are dropped here rather than asserted as fact; treat them as unconfirmed if encountered elsewhere.
  Source: Sportskeeda, ["Devs warn using Clash Royale duplicate and special cards exploit may lead to account suspension"](https://www.sportskeeda.com/esports/news-devs-warn-using-clash-royale-duplicate-special-cards-exploit-may-lead-account-suspension) (Jul 2024) — confirms the core exploit (duplicate + special cards usable outside their intended restriction) and the account-suspension warning. Original X sources kept for reference but unverifiable this session: [status/1810269734379626764](https://x.com/ClashRoyale/status/1810269734379626764), [status/1810703054473138236](https://x.com/ClashRoyale/status/1810703054473138236) — both return HTTP 402 to every fetch tool, so a reader without X access cannot check the quoted tweet text either.
  **Test-for-us**: Try to join a ranked match with a client/request that reports pre-normalization Level/Skill values, or that submits duplicate/disallowed entries the restriction is supposed to reject, and see whether server-side validation actually rejects every such path into the match — not just the "happy path" queue-join — before combat starts. The done-criteria already assert normalization/validation happens for the honest client; this is about whether a dishonest one can skip it.

- **Scar**: Supercell shipped a trophy-loss-on-defeat increase in Season 18 aimed at "better matchmaking and ladder pushing," and had to publicly revert it after community feedback showed it created "a frustrating mid-ladder experience for many" specifically in the 4000–6000 trophy band, while leaving it in place for newer sub-4000 players where it worked as intended; they also had to reduce the seasonal trophy reset from 50% to 25% to compensate players whose personal bests got disrupted by the bad tuning window. — Source: Supercell official blog, ["Trophy Change Revert"](https://supercell.com/en/games/clashroyale/blog/release-notes/trophy-change-revert/).
  **Test-for-us**: When Elo/K-factor tuning parameters (explicitly flagged in this doc as "expect these to be revisited repeatedly post-launch") get changed, check the effect isn't uniform-by-assumption — segment by rank band and see whether one band (e.g. mid-tier) degrades while others are fine, and whether a tuning-parameter change can be reverted for future matches without corrupting or needing to retroactively recompute rank deltas already written for matches that happened under the old parameters.

- **Scar**: A February 2025 bug in Clash Royale's 2v2 Ladder caused per-match reward-chest state to stop refreshing between games (players kept getting the same chest type repeatedly) and, per Supercell's own release note, the corruption risk was severe enough that they pulled the entire 2v2 Ladder mode offline rather than patch it live, fixed it, then had to reconcile "incorrect Badge" (rank-tier) assignments retroactively once the ladder reopened, and extended the season to compensate for the downtime. — Source: Supercell official blog, ["Balance Changes & 2v2 Ladder Bug Fix"](https://supercell.com/en/games/clashroyale/blog/release-notes/balance-changes-and-2v2-ladder-bug-fix/).
  **Test-for-us**: Try feeding the match-result → rank/MMR update pipeline a malformed or partially-applied result (e.g. a crash mid-write, or the same match result resubmitted) and check whether the corruption stays contained to that one match/player record, or whether it's the kind of thing that would force taking the whole ranked queue offline to untangle — done-criterion #4's idempotency assertion is exactly the boundary this incident blew through.

None of the above prescribes Supercell's fix as correct for us — this project's own contract (`docs/agent-blueprint/19-pvp-ranked-system.md` done-criteria, `docs/MASTER_BLUEPRINT_v3.0.md` §8 server-authority) decides what "correct" looks like here; these scars only name the failure shape to go try and break.

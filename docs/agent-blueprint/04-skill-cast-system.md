# 4. Skill/Cast System

> Category: Combat core · Generated via gold-standard FILL + adversarial CB-lite verify (2 seats), 2026-08-07 · **revised after verify flagged an issue**.

### Scope

The Skill/Cast System owns **per-hero active-ability execution**: the skill1/skill2/skill3/ultimate cast lifecycle (`Input → Cast/Wind-up → AttackActive → Recovery`), cooldown/ultimate-gauge gating, i-frame windows during cast, and mapping a hero's kit data to hitbox activation ticks. It owns the _data schema_ for per-move properties (§3.6.7) and the _state machine_ (`SkillState`) that drives it. It does **not** own: hitbox-vs-target collision resolution (`HitboxSystem.ts`), damage math (`DamageSystem.ts`), basic-attack combo chaining (`ComboSystem.ts`), enemy/boss AI (`EnemyAISystem.ts`), or hero roster/leveling data (hero system). It currently implements exactly one hero kit (Monkey King, `src/game/realtimeBattle/skills.ts:38-76`) — the registry (`REALTIME_CHARACTER_KITS`) is the extension point for more.

### Inputs/Outputs

- **In:** `RealtimeSkillDefinition` (`skills.ts:18-27` — `id/name/slot/characterId/attack/cooldownMs/invulnerableMs`), a `SkillState` (`SkillSystem.ts:13-17` — `definition/sinceStartMs/hitTargets`), the acting `RealtimeBattleEntity` (`types.ts:33-69`), and `deltaMs`/`elapsedMs` from the battle loop.
- **Out:** `canStartSkill()` → boolean gate; `startSkill()` → mutates entity (`state='skill'`, zeroes velocity, sets cooldown or consumes ultimate gauge, sets `invulnerableUntilMs`) and returns boolean; `stepSkill()` → `SkillTick { hitboxActive: boolean; attack: AttackDefinition | null }` consumed by `HitboxSystem`.
- `AttackDefinition` (`attacks.ts:15-42`) is the actual move-data shape shipped today: `startupMs/activeMs/recoveryMs/comboWindowStart/EndMs/damageMultiplier/range/hitShape('horizontal'|'radial')/arcDegrees/depthTolerance/knockback`. It does **not** yet carry the §3.6.7-locked fields `castDelayMs`, `interruptible`, `movementDuringCast`, `lungeDistance`, `hitstunMs`, `knockdown`, `multiTarget`, or `effects[]` — grep across `src/game/realtimeBattle/` confirms none of these identifiers exist in code. The blueprint itself flags this ("extend `AttackDefinition` / skill defs in implementation PRs", line 201) — treat the full §3.6.7 schema as **designed, not implemented**. (`targetLock` is a separate, hero-kit-level flag introduced in §3.7 (lines 318/320) on the Monkey King Ultimate row — it is not part of the §3.6.7 per-move schema, so it's out of scope for this particular gap list.)

### Dependencies

- **hero system** — kit registry keyed by `characterId` (`getRealtimeSkillKit`), pulls hero identity.
- **combat system** (`HitboxSystem`, `DamageSystem`) — consumes `SkillTick.attack` to resolve hits/damage; skill system feeds it, doesn't call it.
- **enemy system** (`EnemyAISystem`) — §3.8.3 locks that summon effects (once `effects[]` ships) will reuse the enemy AI state machine rather than a bespoke one; not yet wired since `effects[]` doesn't exist.
- No dependency on economy/backend/social/pvp/adventure systems today.

### Done-criteria

1. `canStartSkill` returns `false` when: player is `dead`, mid-hitstun, already casting (`skill.definition !== null`), mid-basic-attack, on cooldown (skills), or ultimate gauge not full (`SkillSystem.ts:37-40`). **Coverage today is partial, not the six-for-six it should be:** `SkillSystem.test.ts` directly exercises only cooldown-gating (line 87) and ultimate-gauge-not-full (line 113) via `canStartSkill`; "already casting" is only indirectly touched (the same cooldown test flips `skillCooldownsMs` to 0 then calls `startSkill` before re-checking, so it isn't isolated) and there is **no test at all** that calls `canStartSkill` with `player.state === 'dead'`, with `hitStunRemainingMs > 0`, or with `isAttacking = true`. Extend the test file to add the three missing branches and an isolated already-casting case before treating this criterion as met.
2. `startSkill` sets `player.state = 'skill'`, zeroes velocity, sets `invulnerableUntilMs = elapsedMs + definition.invulnerableMs`, and either zeroes `ultimateGauge` or sets the correct `skillCooldownsMs[slot]` — verified per-slot.
3. `stepSkill` returns `hitboxActive: true` only during `[startupMs, startupMs+activeMs)` (`isActiveWindow`), and clears `skill.definition`/`hitTargets`/`sinceStartMs` and resets `state` to `idle` exactly once total duration elapses.
4. `stepSkill` resolves `interruptible` per phase: Monkey King's Ultimate survives hits during telegraph/startup/active, while recovery can be interrupted. Tests must pin both sides so hyper-armor cannot silently spread to recovery or disappear from the strike.
5. Adding a new hero kit requires zero changes to `SkillSystem.ts` — only a new `RealtimeSkillKit` entry in `skills.ts` (proves the registry is genuinely data-driven, not hardcoded to Monkey King).

### World-class bar

**Exemplar: Genshin Impact's elemental skill/burst state machine** — the pattern worth borrowing is that **basic attacks, skills, and bursts all run through the identical startup→active→recovery state machine**, differentiated purely by data (cast delay, hitbox shape, interrupt flags), never by bespoke per-ability code paths. The blueprint's own on-point citation for this is §3.8.2's "Ultimate strike-phase resolution" passage (line 320: "genre convention, e.g. Genshin/Star Rail ultimates... the entire 4-phase sequence is non-interruptible") — that's the passage actually about interrupt/poise data on skills, and it's exactly item 4 above. (§3.8.2's other Genshin citation, line 342, is about ranged _basic attacks_ reusing the melee schema via `lungeDistance≈0` — a related but distinct point about "same shape, different data" that this codebase already satisfies for ranged heroes, not the skills/bursts interrupt gap.)

### Stay-current note

None specific to this system beyond the interrupt-schema gap already tracked in done-criteria — the state-machine shape (`startup→active→recovery`, cooldown/gauge gating) is a stable, genre-standard surface unlikely to need architectural revisiting as the project grows to more heroes.

### Low-maintenance-cost design

Keep **`attacks.ts` as the single source of truth for all move timing/data** (its own header comment already states this rule explicitly: "ค่าจังหวะทุกตัวอยู่ในไฟล์นี้ไฟล์เดียว ห้ามกระจายไปเขียนใน component หรือใน system" — attacks.ts:4-5) and extend it by **adding fields to the existing flat `AttackDefinition` interface**, not by introducing a new abstraction layer (e.g. a `SkillEffect` class hierarchy or strategy-pattern per effect kind) for the still-single-implementation `effects[]` need. §3.6.7 itself frames `effects[]` as data (`kind: heal/buff/cc/summon` + `target`), not polymorphic code — resolve it with a plain discriminated union and a switch in `DamageSystem`/a new small resolver, consistent with this project's YAGNI stance (no interface for one implementation) and its existing all-data-driven `AttackDefinition`/`REALTIME_CHARACTER_KITS` pattern. No new dependency needed — this is plain TypeScript unions plus the existing Vitest setup already used by `SkillSystem.test.ts`.

### Known mechanic (not a scar — no incident, no patch, no compensation; listed separately from the two real-bug post-mortems above)

- **Mechanic**: Genshin's "animation cancel" is a long-standing, community-documented, intentional/tolerated mechanic — a player can skip a move's entire recovery-phase animation by queuing another Skill, Burst, dash, jump, or weapon swap before recovery finishes playing. This demonstrates that in Genshin's own implementation, the developers chose to make the recovery phase escapable by a differently-timed input — it is evidence of one game's design choice, not proof that a "recovery phase" is universally escapable or that any particular resolution is correct. Whether our own recovery window _should_ be interruptible is this project's call (see `docs/agent-blueprint/04-skill-cast-system.md` §3.6.4/§3.6.6/§3.6.7); this entry only flags a class of assumption worth checking for. — Source: KeqingMains community combat-mechanics wiki ("Frames" page) plus independent guide writeups (BitTopup, TheGamer).
  **Test-for-us**: Feed a new skill/dash/basic-attack input while a hero is still inside another skill's `recoveryMs` window and check whether `stepSkill`'s phase clock, `skillCooldownsMs` write, or `hitTargets` reset assume recovery always runs to completion uninterrupted — does the queued input let the hero re-enter `active`/re-hit early, or skip whatever recovery was supposed to gate (cooldown start, hit-once bookkeeping)? This is a neutral order-of-input question; it does not presuppose our recovery phase should or shouldn't be interruptible.

None of the above prescribes how Genshin resolved (or left unresolved) these — this project's own spec in `docs/MASTER_BLUEPRINT_v3.0.md` and `docs/agent-blueprint/04-skill-cast-system.md` (§3.6.4/§3.6.6/§3.6.7, the `interruptible`/`castDelayMs` design already flagged as a gap) is what "correct" means here; the exemplar only points at what shape of bug (or, for the animation-cancel entry, what shape of design assumption) to go looking for.

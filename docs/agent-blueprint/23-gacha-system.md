### Scope

Owns: gacha roll resolution (rate table, pity counter, banner cost), converting a roll result into hero-ownership writes, and the config that drives rates/pity/cost. Does **not** own: currency balance mutation itself (that's `accountRepository.ts`'s `appendTransaction`/gold-gem ledger, §8 server-authority), hero stat/kit data (`src/game/characters.ts`), star-ascension math or duplicate-conversion rules (§4.3, owned by the Star Ascension system, #15 in `AGENT_BLUEPRINT.md` line 63 — a sibling of, not the same system as, Hero Collection #13), or the shop/purchase UI for buying roll currency (§7 secondary monetization, System #24). Gacha consumes currency and hero-ownership as dependencies; it does not define either.

**Current state: shipped and live (P9, PR #97).** `MainNavigation.tsx`'s `'summon'` nav item is wired to `onOpenSummon()`, which opens `GachaModal.tsx`; pulls route through `accountRepository.supabase.ts::pullGacha` to the server-authoritative Postgres RPC `perform_gacha_pull` (`supabase/migrations/20260809073000_p9_gacha_server_authority.sql`) — an atomic, request-id-idempotent function covering rate-table-sum validation, hard pity, Gem debit, hero/shard grant, and private pull-history RLS. Two test files cover it (`src/data/gachaAuthority.integration.test.ts`, `src/components/GachaModal/GachaModal.test.tsx`). The migration was applied and verified in production 2026-08-10 (MEMORY.md item 176). `src/game/gacha/gachaEngine.ts`/`gachaService.ts` (a client-side pure-function PRNG resolver from an earlier, since-superseded client-authoritative iteration — see MEMORY.md item 169) was never wired into the live pull path and has been deleted (design-fork 2.b, 2026-08-10) rather than kept — see Done-criteria #1.

### Inputs/Outputs

Shipped, as of P9 (`supabase/migrations/20260809073000_p9_gacha_server_authority.sql`):

- **In:** `p_request_id` (client-generated UUID, idempotency key), `p_banner_id`, `p_pull_count` (1 | 10) passed to the RPC `perform_gacha_pull`; the caller's `uid` comes from `auth.uid()` server-side, never client-supplied. Currency spend routes through `currency_transactions` with `source = 'gacha'` (added to `currency_transactions_source_check`/`currency_source_match` alongside `'quest'|'drop'|'topup'|'coupon'|'admin'`).
- **Out:** `GachaPullResult` (`src/data/accountRepository.shared.ts:86-96`) — one or more `{ characterId, rarity, isPity, isNew, shardsGranted }` results, `cost`, `currencyUsed`, `newPity`, and `replayed` (true when the same `request_id` was already processed). New heroes and duplicate-shard increments both write to `owned_characters` inside the same RPC transaction as the currency debit.
- **Config in:** `gacha_banners` + `gacha_banner_pool` tables. The shipped seed predates the rate lock and does **not** match it — the locked configuration (`docs/GACHA-RATE-DESIGN-LOCK.md`, authoritative) is four bands rather than three:

  | rarity      | `B[r]` band rate | pity `P[r]`  | notes                                                      |
  | ----------- | ---------------- | ------------ | ---------------------------------------------------------- |
  | `legendary` | `0.0330000`      | `100`        | corridor midpoint of 9 exemplars (0.6% Genshin – 6% FEH)   |
  | `epic`      | `0.0886663`      | `10` (floor) | secondary/floor pity, invariant `I18`                      |
  | `rare`      | `0.2382337`      | —            |                                                            |
  | `common`    | `0.6401000`      | —            | absorbs rounding so `SUM(B) = 1` exactly; **zero members** |

  Cost: `c = 16` gem single, `cost_multi = 160` gem ×10, with `d = 0` — no multi-pull discount. `cost_multi` must fall out of `ceil(K × c × (1 - d))` and never be typed independently (`I17`); the old `900` silently encoded an undeclared `d = 0.10`. Featured share `u = 0`, permanently — there is no featured-character mechanic and none is planned. Duplicate shards `S[r]` are a frozen table (`common 1 / rare 3 / epic 7 / legendary 19`), deliberately **not** derived from the band ratio, so re-ratifying `B` never silently reprices the shard economy. Star ladder is a uniform 6 duplicates to terminal at every rarity (★2→★5), which puts a maxed legendary at 364 pulls — inside Genshin's C6 range and just under FGO's NP5. `preserve_relative_progress = true` for this permanent banner: a change to `P` migrates existing players proportionally (`count_new = round(count_old × P_new/P_old)`) rather than resetting them.

  **The `common` band has no characters in it**, which is deliberate and is what currently blocks the banner: invariant `I3` holds the whole Standard Banner closed until a real `common`-rarity character exists. There is no second banner type and none is needed — no surveyed exemplar segregates a single rarity into its own banner.

### Dependencies

- **hero system** (`src/game/characters.ts`, `Character`/`Rarity` types) — gacha rolls _from_ the hero pool; needs rarity/archetype data to weight against.
- **economy** (`src/data/accountRepository.ts` currency ledger) — gacha spends gold/gems, feeds into `currency_transactions`.
- **backend** (§8 server-authority) — gacha outcome is "valuable data" per §8 line 480; this dependency is already satisfied — `perform_gacha_pull` (`supabase/migrations/20260809073000_p9_gacha_server_authority.sql`) resolves RNG, pity, currency debit, and hero/shard writes entirely server-side (SECURITY DEFINER), not client-trusted.
- Feeds **Star Ascension** (§4.3, System #15) — every roll is an input to star ascension math (owned by that system, not this one).

### Done-criteria

1. Roll output is statistically verified, not deterministically reproduced — a fixed-seed/no-`Math.random()` criterion is incompatible with a server-authoritative RNG a client can never legitimately predict (predictable server rolls are a real-money-adjacent risk surface, not a testing convenience). Verified instead by running N pulls against the live `perform_gacha_pull` RPC (via the PGlite-backed integration harness, `src/data/gachaAuthority.integration.test.ts`) and asserting: the observed rarity distribution stays within tolerance of the banner's configured `drop_rate`s, and pity guarantees the banner's configured `pity_rarity` by `pity_threshold` pulls, every time, with zero exceptions across the run. (Decided as design-fork 2.b, 2026-08-10 — see MEMORY.md; supersedes the deterministic-seed criterion this contract shipped with. `src/game/gacha/gachaEngine.ts`/`gachaService.ts`, the only code that met the old criterion, was dead — never called from the live pull path — and has been deleted, not kept as a reference module, since a client-predictable resolver for a server-authoritative RNG isn't a shape worth preserving.)
2. A roll never succeeds without a matching `currency_transactions` debit of the correct source/amount — verifiable by replaying a test account's transaction log against its `owned_characters` diff.
3. Pity counter writes are serialized by a real Postgres row lock (`perform_gacha_pull` takes `for update` on the player's `profiles` row and, per-banner, on `gacha_pity`), not the client-side multi-tab conflict-reject pattern this criterion originally anticipated — the shipped design supersedes it with server-side atomicity rather than implementing it, since the live gacha path never touches `accountRepository.ts`'s localStorage store (`useAuth.ts` calls `accountRepository.supabase.ts::pullGacha`, which invokes this RPC directly).
4. Rate table sums to 100% per banner at config-load time — a broken/misconfigured table fails a build-time or test-time assertion, never fails silently at runtime.
5. A roll can never produce a `characterId` outside the banner's configured hero pool, and every roll writes exactly one ledger debit and at most the rolled count of `owned_characters` rows — no partial/duplicate writes on retry.

### World-class bar

**Nine games, measured — not one exemplar copied.** An earlier version of this contract named Genshin's soft/hard pity ramp as the one pattern to borrow. That bar is retired: every formula this project locked has been flat-rate since its first invariant (`reach = (1-q)^(P-1)`, flat by construction), which is FGO-shaped, not Genshin-shaped, and `docs/MASTER_BLUEPRINT_v3.0.md` §7.1 was amended to match the math rather than the other way round. Copying one game's headline number was the failure mode; the replacement bar is a **corridor**, and every locked value sits inside one measured across Genshin, Honkai Star Rail, FGO, Arknights, Blue Archive, Fire Emblem Heroes and three more.

What the panel actually establishes, and what this system must keep clearing:

- **A bounded free-to-play floor, disclosed.** Universal across all nine. Pity is a real ceiling on bad luck, and the bound is published — not a marketing footnote. This is what carries §7's "must not sell best power primarily via direct purchase."
- **Rate corridor, not a chosen number.** 0.6% (Genshin/HSR) to 6% (FEH); this project sits at the midpoint. A future re-tune is legitimate only if it stays inside a corridor someone measured.
- **No undeclared multi-pull discount.** Genshin, HSR, Arknights and Blue Archive all charge exactly `K × c` on the main banner. Nobody discounts the headline price. `d = 0` follows the panel, and `I17` makes an undeclared discount structurally impossible rather than merely discouraged.
- **Duplicates are a side-grade, not the power curve.** Arknights requires zero duplicates for core power. The 6-duplicate ladder here was rebuilt after a first draft priced a maxed legendary at 909 pulls — three times FGO's NP5, worse than the most duplicate-hungry game in the panel.
- **Price against local wages, not a global USD figure.** Regional pricing is real (SEA runs 50-70% below USD nominal), so the burden comparison was rebuilt on local-currency price against local _average_ wage, with no exchange rate in the calculation at all.

Read `docs/GACHA-RATE-DESIGN-LOCK.md` for the derivation of each. The disclosure obligation from the old bar survives unchanged and is strengthened: rates, pity thresholds **and** the absence of a featured mechanic (`u = 0`) are all publishable, because none of them is a secret this design depends on.

### Stay-current note

Gacha regulatory disclosure requirements (drop-rate publication, pity disclosure) vary by platform/region and have tightened over time (e.g. mobile storefront policies, some jurisdictions' loot-box laws) — whatever rate/pity numbers P9 locks in should be revisited against current platform policy at implementation time, not assumed stable from this contract's writing date.

### Low-maintenance-cost design

**Rate/pity/cost as one data table, not scattered constants** — mirrors the project's own already-established pattern: `RewardSystem.ts` centralizes its per-enemy reward numbers in a single `TEMPLATE_REWARD` const rather than inline math (`src/game/realtimeBattle/RewardSystem.ts:28`), and §5.1 explicitly locks the same principle for stage difficulty ("data-driven per-stage/per-chapter table... never a hardcoded formula in code," line 421). Gacha should follow suit: one config object (or one JSON/table file) is the single source of truth for rates/pity/cost per banner, tunable without touching roll logic. Per ponytail/YAGNI: do not build a banner-authoring UI, a generic "rules engine," or an abstraction over multiple gacha "modes" until a second banner type actually exists — P9 only needs the one banner shape the blueprint describes.

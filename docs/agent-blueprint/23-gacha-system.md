# 23. Gacha System

> Category: Economy · Generated via gold-standard FILL + adversarial CB-lite verify (2 seats), 2026-08-07 · **revised after verify flagged an issue**.

### Scope

Owns: gacha roll resolution (rate table, pity counter, banner cost), converting a roll result into hero-ownership writes, and the config that drives rates/pity/cost. Does **not** own: currency balance mutation itself (that's `accountRepository.ts`'s `appendTransaction`/gold-gem ledger, §8 server-authority), hero stat/kit data (`src/game/characters.ts`), star-ascension math or duplicate-conversion rules (§4.3, owned by the Star Ascension system, #15 in `AGENT_BLUEPRINT.md` line 63 — a sibling of, not the same system as, Hero Collection #13), or the shop/purchase UI for buying roll currency (§7 secondary monetization, System #24). Gacha consumes currency and hero-ownership as dependencies; it does not define either.

**Current state: no roll-resolution logic exists in code; UI scaffolding does.** No `gacha`/`summon`/`pity`/`roll`/`banner` resolution module, service, or test exists anywhere under `src/` — but the entry point already has a placeholder: `MainNavigation.tsx:25` registers a `'summon'` nav item (label "อัญเชิญ", icon `ui/navigation/summon.webp`), and `GameIcons.tsx:63-64` exports a doc-commented `SummonIcon` ("รูนอัญเชิญ — Summon"). Neither wires to any roll logic. This is pre-implementation, matching roadmap priority **P9** (`docs/MASTER_BLUEPRINT_v3.0.md` line 508); `AGENT_BLUEPRINT.md` line 80 (item 23, "Gacha System") states "rate/pity/cost numbers deferred to P9 (business-model call)."

### Inputs/Outputs

Not yet defined in code — inferred contract from adjacent schemas:

- **In:** `uid` (account), `bannerId` (config key), currency spend (gold or gem, per banner config) — spend must route through the existing `appendTransaction` pattern in `src/data/accountRepository.ts` (source enum would need a new value, e.g. `'gacha'`, added alongside `'quest'|'drop'|'topup'|'coupon'` at line 27).
- **Out:** one or more `{ characterId, isNew: boolean }` roll results. New heroes write to the `owned_characters` table shape already documented at `accountRepository.ts:22` (`uid FK, character_id, level, exp, exp_to_next, obtained_at`); duplicates hand off to the Star Ascension system (out of scope, §4.3) rather than being resolved here.
- **Config in:** a data-driven rate/pity table (rarity weights, pity counter threshold, per-banner cost) — no schema exists yet; must be authored new, following the same "data table, not hardcoded formula" pattern already locked for stage difficulty (§5.1 line 421) and used in `RewardSystem.ts`'s `TEMPLATE_REWARD` const.

### Dependencies

- **hero system** (`src/game/characters.ts`, `Character`/`Rarity` types) — gacha rolls _from_ the hero pool; needs rarity/archetype data to weight against.
- **economy** (`src/data/accountRepository.ts` currency ledger) — gacha spends gold/gems, feeds into `currency_transactions`.
- **backend** (§8 server-authority) — gacha outcome is "valuable data" per §8 line 480, must eventually be server-resolved, not client-trusted, once Supabase becomes full authority.
- Feeds **Star Ascension** (§4.3, System #15) — every roll is an input to star ascension math (owned by that system, not this one).

### Done-criteria

1. Given a fixed seed and pity counter, roll output is deterministic and reproducible in a unit test (no live `Math.random()` — see Stay-current note).
2. A roll never succeeds without a matching `currency_transactions` debit of the correct source/amount — verifiable by replaying a test account's transaction log against its `owned_characters` diff.
3. Pity counter writes follow the same multi-tab conflict-reject pattern `accountRepository.ts` already uses for every other localStorage write (lines 179-181: reject a write if another tab wrote first, rather than silently overwrite) — no bespoke concurrency model invented for gacha specifically, since the store is client-only/localStorage-backed with no cross-request atomicity to build against (§8 marks gacha outcome as eventually server-authoritative, not today).
4. Rate table sums to 100% per banner at config-load time — a broken/misconfigured table fails a build-time or test-time assertion, never fails silently at runtime.
5. A roll can never produce a `characterId` outside the banner's configured hero pool, and every roll writes exactly one ledger debit and at most the rolled count of `owned_characters` rows — no partial/duplicate writes on retry.

### World-class bar

**Genshin Impact's gacha system (miHoYo/HoYoverse)** — the one concrete pattern worth borrowing: **hard/soft pity with a guaranteed rarity within a bounded pull count** (⚠️ unverified: whether Genshin's live wish UI displays a running numeric pity counter to the player is disputed — that specific UI feature spawned third-party pity-tracking tools/spreadsheets precisely because the in-game display doesn't show it; verify current UI before citing "visible counter" as the differentiator). The soft/hard-pity mechanic itself is accurately Genshin's and is the industry-referenced standard for "gacha the player can trust the fairness of" without requiring drop-rate secrecy. It directly supports this project's §7 "must not sell best power primarily via direct purchase" stance by making the free-to-play pity path a real, bounded floor rather than a marketing footnote — regardless of whether the counter itself is player-visible, the bound should be, at minimum, disclosed in-game text (rules, FAQ, or similar) even if not a live running number.

### Stay-current note

Gacha regulatory disclosure requirements (drop-rate publication, pity disclosure) vary by platform/region and have tightened over time (e.g. mobile storefront policies, some jurisdictions' loot-box laws) — whatever rate/pity numbers P9 locks in should be revisited against current platform policy at implementation time, not assumed stable from this contract's writing date.

### Low-maintenance-cost design

**Rate/pity/cost as one data table, not scattered constants** — mirrors the project's own already-established pattern: `RewardSystem.ts` centralizes its per-enemy reward numbers in a single `TEMPLATE_REWARD` const rather than inline math (`src/game/realtimeBattle/RewardSystem.ts:28`), and §5.1 explicitly locks the same principle for stage difficulty ("data-driven per-stage/per-chapter table... never a hardcoded formula in code," line 421). Gacha should follow suit: one config object (or one JSON/table file) is the single source of truth for rates/pity/cost per banner, tunable without touching roll logic. Per ponytail/YAGNI: do not build a banner-authoring UI, a generic "rules engine," or an abstraction over multiple gacha "modes" until a second banner type actually exists — P9 only needs the one banner shape the blueprint describes.

The v2.4 event title itself ("Flowing Lights and Colors") could not be re-confirmed live this pass (WebSearch exhausted, direct fetch to destructoid.com now 404s) — flagging rather than asserting: it may in fact be "Fleeting Colors in Flight." Re-verify the exact event name before treating it as locked.
  **Test-for-us**: Fire the same reward/grant call twice against our own currency-ledger + roll-resolution path (double-submit, client retry after a timed-out response, replayed/duplicate network request, re-processing the same claim/mail id) and confirm the system rejects or dedupes the second call outright at write time — never lets it land and only gets noticed after the fact. Our design has no "just double it for everyone" escape hatch once a duplicate roll has already resolved into a real `owned_characters` row and a currency debit, so the dedup has to hold _before_ that write, not be a policy decision made after the fact. Note on scope: the "replayed/duplicate network request" scenario specifically targets the future server-authoritative phase of gacha — per this project's own spec (Done-criteria #3), gacha today is client-only/localStorage-backed with no cross-request atomicity to build against (§8 marks server-authoritative as "eventually," not now). The double-submit/client-retry and duplicate-claim-id scenarios apply to the current client-only system now; the network-replay-defense half of this test is a requirement to carry into the server phase, not something to build against today's implementation.

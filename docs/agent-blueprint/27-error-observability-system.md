# 27. Error / Observability System

> Category: Backend / Infra · Generated via gold-standard FILL + adversarial CB-lite verify (2 seats), 2026-08-07 · **revised after verify flagged an issue**.

### Scope

Owns: the stable `ErrorCode` registry (`src/lib/errors/codes.ts`), the single logging/reporting chokepoint (`reportError()` in `src/lib/errors/reportError.ts`), the visible-error pub/sub relay (`subscribeToVisibleErrors`), the two UI surfaces that render a code to the player (`ErrorBoundary` for render-crashes, `GlobalErrorBanner` for everything else tier `'visible'`), and the net that catches exceptions outside React's render cycle (`window.addEventListener('error'/'unhandledrejection')` in `src/lib/globalErrorHandlers.ts`, wired in `src/main.tsx:11`). Does **not** own: any external telemetry/APM sink (explicitly declined, see `.agents/rules/ecc/web/observability.md:42-45` and `MEMORY.md`), WebGL/WebGPU context-loss _recovery_ logic itself (only the reporting of it — recovery lives in `LobbyScene`/`BattleScene`), toast/notification UI for non-error messages, and per-domain retry/fallback behavior (that's each caller's job; this system only logs+surfaces after the caller decides tier).

### Inputs/Outputs

- **In**: `reportError(code: ErrorCode, tier: 'silent'|'visible', err?: unknown, context?: Record<string, unknown>)` — called from any catch block or error boundary in the codebase. `ErrorCode` is `keyof typeof ERROR_CODES` (`src/lib/errors/codes.ts:9-114`), a flat const object, never a TS enum (blocked by `erasableSyntaxOnly`, per file comment line 3-4).
- **Out**: `console.error`/`console.debug` line (`[CODE] ThaiMessage`, err, context) — the only place in the app allowed to call `console.*` directly (oxlint `no-console` exempts this folder). For `tier: 'visible'`, additionally fires every subscriber registered via `subscribeToVisibleErrors(handler: (code, err?) => void): () => void`; `GlobalErrorBanner` is the sole production subscriber (`GlobalErrorBanner.tsx:39-43`).
- No network I/O, no persisted log — a crash screen's only "export" is the player-triggered save backup (`ErrorBoundary.tsx:45-58`, via `exportSave()`/`downloadSaveJson`).

### Dependencies

- **Depends on**: nothing upstream for its core registry/relay path (no imports from combat/hero code) — but not a pure leaf: `ErrorBoundary.tsx` (line 3) imports `exportSave` from `src/data/accountRepository` for its crash-screen backup button (`handleBackup`, `ErrorBoundary.tsx:45-58`), so the account/save domain is a narrow, one-directional upstream dependency of this system's UI half. That import is also why the Feeds list below includes save-domain codes (`SAVE_EXPORT_FAIL` etc.) as things `accountRepository` reports back through this system — the two are mutually coupled at that single call site, not cleanly layered.
- **Feeds**: combat/battle (`RealtimeBattleRoom.tsx`, battle init codes at `codes.ts:79-80` plus asset/context-loss codes at `codes.ts:94,96`), hero/lobby (`LOBBY_SCENE_*` codes for R3F/WebGPU failures, `codes.ts:83-85`), backend (`AUTH_*`, `DB_*`, `STORAGE_*` codes covering Supabase/localStorage failures, `codes.ts:22-68`), economy/save (`SAVE_EXPORT_FAIL`, `SAVE_IMPORT_PARSE_FAIL`, `PLAYER_SAVE_FAIL`, `codes.ts:40-54`). No pvp/social/adventure-specific codes exist yet — those systems would add entries to `ERROR_CODES` when they ship, not build a parallel mechanism.

### World-class bar

**Excalidraw's `TopErrorBoundary`** (real, shipped, MIT, `excalidraw-app/components/TopErrorBoundary.tsx` — closest OSS peer on the "mostly-static, client-heavy app" shape). Verified against the actual source, not from memory: its crash screen offers a reload button, a "clear canvas + reload" button, a read-only `<textarea>` dumping raw localStorage JSON for the user to manually select and copy, a "create GitHub issue" button — and it reports every crash to Sentry via `Sentry.captureException`. Two corrections to the earlier framing: (1) it does **not** offer a "save to disk" action — this project's `ErrorBoundary.handleBackup` (`exportSave()`/`downloadSaveJson`, `ErrorBoundary.tsx:45-58`) produces an actual downloaded file with one click, which is a strictly better data-preservation UX than Excalidraw's manual-copy-from-textarea; (2) Excalidraw's handler ships crash data to third-party telemetry (Sentry), the exact practice this project's own docs explicitly declined (`observability.md:42-45`), so it isn't a peer on the "no external sink" axis even though it's a peer on "no mandatory backend." Net: this project's escape hatch already exceeds the exemplar on the one dimension worth borrowing, no gap to close, but "the pattern is matched" understates it — it's matched-and-improved-on, not matched.

### Low-maintenance-cost design

**Single flat data registry (`ERROR_CODES` object) as the one source of truth**, not a class hierarchy or per-domain error-code enum. Every new failure = one line in `codes.ts` + one `reportError()` call; no factory, no error-type interface, no per-tier subclass. This mirrors the project's own stated style in the file's header comment (`codes.ts:1-8`: "เพิ่ม error ใหม่ = เพิ่ม entry ที่นี่บรรทัดเดียว") and the relay itself is explicitly justified as "the smallest thing that fixes it: a `Set` of callbacks and a loop, no store, no state, no context" (`reportError.ts:24-26`) — a prior, now-reversed decision to have _no_ relay at all was corrected only when three independent call sites proved the abstraction was load-bearing, not speculative (YAGNI honored until evidence, then the minimum fix, not a general pub/sub library).

### Known scars (real historical precedent)

- **Scar**: Excalidraw's localStorage-based autosave hit the ~5MB browser storage quota on large boards and the `setItem` write failed with no error ever surfaced to the user — work kept vanishing silently until someone noticed the board wasn't saving. — Source: excalidraw/excalidraw GitHub issues [#8395](https://github.com/excalidraw/excalidraw/issues/8395) "Going over the local storage limit while using Excalidraw can lead to unintended data loss" and [#8805](https://github.com/excalidraw/excalidraw/issues/8805) "Local storage overflow fails silently, without letting the user know."
  **Test-for-us**: Find every write this system's callers make outside `reportError()`'s reach (localStorage writes in `accountRepository`, any future Supabase/save write) and force one to throw synchronously — e.g. simulate a quota/permission error on `localStorage.setItem` during a save. Confirm the catch block that wraps it actually calls `reportError` with `tier:'visible'` (not `'silent'`, and not un-caught) rather than swallowing the failure — a save that silently fails is functionally identical to Excalidraw's bug regardless of how the error-code registry is designed.

- **Scar**: When Excalidraw's localStorage held corrupted or invalid data, the app threw during startup initialization — before the app's own error boundary was even mounted — leaving users with no recovery path except manually opening devtools and running `localStorage.clear()`. — Source: excalidraw/excalidraw GitHub issue [#471](https://github.com/excalidraw/excalidraw/issues/471) "Don't explode if initialization fails."
  **Test-for-us**: Corrupt whatever this app reads at startup (feed `accountRepository`/localStorage a malformed JSON blob before `main.tsx` mounts) and check whether the throw happens in the gap before `ErrorBoundary`/`globalErrorHandlers.ts`'s listeners are wired up. Try to reach a genuine white-screen-with-no-code state by crashing earlier than the observability system's own setup — confirm there is no such gap, or that the fallback for it isn't "open devtools."

- **Scar**: Excalidraw's own "clear canvas" action didn't actually clear the stored elements; stale data silently resurfaced on the next save/broadcast even though the UI showed an empty canvas — a recovery/reset control that lied about what it had actually done. — Source: excalidraw/excalidraw GitHub issue [#1234](https://github.com/excalidraw/excalidraw/issues/1234) "Clear canvas doesn't clear the stored elements."
  **Test-for-us**: This project's crash screen (`ErrorBoundary.tsx:60-90`) has no analogous destructive control to be buggy in the first place — it offers exactly two buttons, "โหลดใหม่" (reload, non-destructive) and "สำรองข้อมูลเป็นไฟล์" (backup-to-file via `handleBackup`/`exportSave`/`downloadSaveJson`, a non-destructive export); per the code comment at `ErrorBoundary.tsx:35-44`, the one destructive fallback (clearing all local data) is deliberately kept out of this UI entirely and lives only in the browser's own settings, with the backup button existing precisely so a player can save before ever reaching that point. The failure shape worth testing for here isn't "a clear action that doesn't clear" but the adjacent one Excalidraw's bug illustrates — a recovery control that lies about what it captured. Trigger `handleBackup` under realistic crash conditions — mid-write, or with a partially-corrupted in-memory state — and inspect the downloaded file's actual contents. Confirm it's the complete, correct save a panicking player would trust as their backup, not a stale or partial snapshot that looks fine but silently omits what just broke.

This project's own spec (`docs/agent-blueprint/27-error-observability-system.md`, `docs/MASTER_BLUEPRINT_v3.0.md`) — not Excalidraw's fixes — is what "correct" means here; the incidents above only name the failure _shape_ (silent write failure, pre-boundary crash gap, a recovery/backup control that misrepresents what it saved) to go try against this codebase, not a solution to copy.

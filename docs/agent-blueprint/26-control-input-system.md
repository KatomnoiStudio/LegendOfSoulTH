# 26. Control / Input System

> Category: Backend / Infra · Generated via gold-standard FILL + adversarial CB-lite verify (2 seats), 2026-08-07 · **revised after verify flagged an issue**.

### Scope

Owns: translating raw player input (touch joystick, keyboard, in future controller) into the combat-domain input contract — a movement vector plus a buffered queue of discrete attack/skill presses — for the real-time battle runtime. Concretely: `src/game/realtimeBattle/InputSystem.ts` (key-to-vector mapping, press buffering, dead-zone application), `playerInput.ts` (the `MovementInput`/`PlayerInputState` shape + Vec2 conversion helpers), `joystickMath.ts` (dead-zone + unit-circle clamp math), and `combatUILayout.ts` (mobile HUD button sizes, curved Combat Cluster geometry, viewport safe-area placement, and collision checks per blueprint §3.3's locked layout). Does **not** own: rendering the joystick/buttons (that's the HUD component layer, e.g. wherever `layoutCssVars()` is consumed), combat resolution (`RealtimeBattleRuntime.ts` owns hit/damage/skill execution), exploration/overworld movement (`useExploration.ts` currently exists only as dead code — per its own header comment the entire file has been commented out since HetCreep disabled it on 2026-08-07, with no entry point into the game since PR #11 and nothing importing it from `src/main.tsx`; while it was live it only mirrored this module's blur-releases-all-keys pattern by comment reference, not by code sharing — src/hooks/useExploration.ts:152-153, not 51-53, which is a different, unrelated bug-fix comment about Set-based held-direction tracking), or facing/targeting logic (`combatFacing.ts` derives `combatFacing` from the movement vector this system outputs, per blueprint §3.6.1, but that derivation lives outside this module).

### Inputs/Outputs

- In: raw DOM `KeyboardEvent`s via `attachKeyboard(target: Window)`; raw joystick vector via `setJoystick(vector: Vec2)` or `setMovementInput(input: MovementInput)` (`{x, depth}`, -1..1 pre-dead-zone); discrete presses via `pressAttack()` / `pressSkill(slot: SkillSlot)` where `SkillSlot = 'skill1'|'skill2'|'skill3'|'ultimate'` (skills.ts:16).
- Out: `getMoveVector(): Vec2` / `getMovementInput(): MovementInput` (dead-zone-applied, normalized, joystick takes precedence over held keys — InputSystem.ts:95-109); `consumeAttack(): boolean` and `consumeSkill(): SkillSlot | null`, both one-shot pops off internal FIFO buffers so no press is lost or double-fired across simulation ticks.
- Consumer contract (RealtimeBattleLoop via useRealtimeBattle.ts:132-135): each fixed-step tick calls `setMoveInput(input.getMoveVector())`, then drains `consumeAttack()`/`consumeSkill()` before `runtime.step(deltaMs)`.

### Dependencies

- Feeds → **combat system** (`RealtimeBattleRuntime`/`RealtimeBattleLoop`): sole input source for player movement, basic attack, and skill/ultimate triggers.
- Feeds → combat facing derivation (`combatFacing.ts`, consumed by combat system) via the movement vector.
- Depends on → **hero system** only indirectly: skill slot identifiers (`SkillSlot`) are defined in `skills.ts` (hero kit data), so this module's skill-press vocabulary is constrained by whatever slots a hero kit exposes.
- No dependency on adventure/pvp/economy/backend/social systems. Exploration input (`useExploration.ts`) is currently dead/disabled code, not a live sibling system, and was never a dependency either way.

### Done-criteria

1. `InputSystem.test.ts` passes: WASD and arrow keys both map correctly, simultaneous opposite keys cancel to `{x:0,y:0}`, diagonal combos sum correctly, joystick input overrides held keys, blur clears all held keys (no stuck-movement bug).
2. Dead zone: any raw joystick vector with magnitude ≤ `DEFAULT_COMBAT_UI_LAYOUT.deadZone` (0.12) yields `{x:0,y:0}`; joystick output magnitude is scaled/clamped to remain ≤1 for any input beyond the dead zone (`applyJoystickDeadZone`, joystickMath.ts:7-16). This clamp is joystick-path-only — the keyboard path's held-key summation (`getMoveVector()`, InputSystem.ts:100-108) is not normalized and can exceed magnitude 1 on diagonals (the existing test asserting `{x:1,y:-1}` for W+D, magnitude √2, confirms this is current, accepted behavior, not a gap to close under this criterion).
3. Attack/skill presses are edge-triggered, not level-triggered: holding a key down does not repeatedly enqueue — verified by the existing `pressedKeys` guard (`if (!this.pressedKeys.has(event.code))` before incrementing/pushing).
4. `consumeAttack`/`consumeSkill` never lose a press queued within the same tick and never double-deliver a press across two ticks (FIFO drain). **Currently unverified**: `InputSystem.test.ts`'s 9 cases cover only movement/dead-zone/blur and never call `pressAttack`/`pressSkill`/`consumeAttack`/`consumeSkill` (the only other `pressAttack` hits in the repo belong to `ComboSystem.ts`'s unrelated same-named method). This criterion is not done until a test asserting queue length/order before and after drain exists.
5. PC keybinds match blueprint §3.3 exactly: Attack `J`/`Space`, S1 `1`/`E`, S2 `2`/`R`, S3 `3`/`F`, Ultimate `4`/`Q` — any keybind change must update both `InputSystem.ts` and §3.3's table in the same PR.
6. Mobile geometry matches §3.3's curved `S1 → S2 → S3 → ULT` arc around ATK, every rendered target is at least 48px, all button pairs retain the configured minimum edge gap, and the joystick/action cluster stay inside safe areas without colliding on the supported landscape viewport matrix.

### World-class bar

**Celeste** (Matt Makes Games, 2018 — the studio later rebranded to Extremely OK Games) — its input buffering is a time-windowed forgiveness mechanism: a jump/dash press registers slightly before the state that validates it arrives (e.g. pressed before landing, still fires on landing). This module's `pendingAttacks`/`pendingSkillSlots` queue is a narrower relative, not the same mechanism — it has no expiry and no eligibility window; it exists purely to avoid dropping a press that lands between the DOM keydown handler and the next fixed-step `step()` call (same-tick event decoupling, not cross-state forgiveness). The lesson worth keeping is the general one — never poll for discrete actions — not a claim that the two buffers work alike. This module should keep matching that lesson: never regress to polling `pressedKeys` directly for attack/skill (only movement should be polled continuously); discrete actions must stay buffer-and-drain.

### Stay-current note

None — stable surface. The input→vector→buffer contract is decoupled from both the rendering layer (HUD buttons) and the consuming layer (combat runtime), so device-specific changes (gamepad support, new touch gestures) are additive at the `attachKeyboard`/`setJoystick` boundary, not a redesign.

### Low-maintenance-cost design

Single source of truth for mobile control geometry: `DEFAULT_COMBAT_UI_LAYOUT` + `resolveCombatClusterMetrics()` in `combatUILayout.ts` own the dead zone, button scales, arc positions, anchor percentages, and safe-area screen projection consumed by both input math, CSS-variable generation (`layoutCssVars()`), and collision tests — no separate hardcoded copies of button positions to drift. Matches this project's established style of data-driven config over hardcoded constants (see `KEY_VECTORS`/`SKILL_SLOT_KEYS` as plain lookup tables rather than switch statements) and YAGNI: no input-remapping/settings abstraction exists because none was asked for — if custom keybinds are ever needed, `SKILL_SLOT_KEYS`/`ATTACK_KEYS` are already isolated as the single place to make them user-configurable, no premature `InputMapper` interface pre-built for it.

Exemplar used: Celeste (Matt Makes Games / Extremely OK Games, 2018) — same exemplar already cited in docs/agent-blueprint/26-control-input-system.md's "World-class bar" section for its input-buffering approach.

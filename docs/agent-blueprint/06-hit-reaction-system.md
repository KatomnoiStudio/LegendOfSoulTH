# 6. Hit Reaction System

> Category: Combat core · Generated via gold-standard FILL + adversarial CB-lite verify (2 seats), 2026-08-07 · **revised after verify flagged an issue**.

### Scope

Owns the moment-of-impact reaction on the **target**: applying knockback displacement and driving `hitStunRemainingMs`/`invulnerableUntilMs`, which is what actually locks out movement/attack input until stun expires — every gate in the codebase (`MovementSystem.ts:97`, `ComboSystem.ts:76,148`, `SkillSystem.ts:38,100`, `combatButtonState.ts:18,28`) checks `hitStunRemainingMs > 0` (plus `state === 'dead'`), never `state === 'hit'`. `state: 'hit'` is also set (`src/game/realtimeBattle/DamageSystem.ts:63-96`) but it is cosmetic only — the sole consumer of `state === 'hit'` in the entire codebase is `EntitySprite.tsx:113`, which swaps a red tint for visual feedback and gates nothing. It does **not** own damage math (that's `calcDamage`, same file, lines 46-61), does not own the attacker-side interrupt-on-hit-while-casting flow from blueprint §3.6.4/§3.6.6 (not implemented — no `interruptible` field or cast-cancel path exists anywhere in `src/game/realtimeBattle/`, confirmed via grep), and does not own knockdown/get-up (also unimplemented — no `knockdown` field, no `Knockdown`/`GetUp` state in `EntityState`, which is only `'idle' | 'walk' | 'attack' | 'skill' | 'hit' | 'dead'`, `types.ts:25`).

### Inputs/Outputs

- In: `DamageContext { attacker, target: RealtimeBattleEntity, attack: AttackDefinition, elapsedMs, random }` (`DamageSystem.ts:37-43`). Relevant `AttackDefinition` fields actually present: `damageMultiplier: number`, `knockback: number`, `hitShape` (`attacks.ts:28,41`).
- Out (mutates `target` in place): `hp -= amount`; on survival sets `state = 'hit'`, `hitStunRemainingMs = HIT_STUN_MS` (180, `DamageSystem.ts:25,82`), `invulnerableUntilMs = elapsedMs + 120` (`:28,83`), and displaces `target.position` by `push * attack.knockback` where `push` is `horizontalKnockbackVector(attacker.combatFacing)` for `hitShape === 'horizontal'` else `directionVector(attacker.facing)` (`:85-93`). On death instead sets `state = 'dead'`, zeroes `velocity`. Returns `DamageOutcome { amount, critical, defeated }`.
- Consumed downstream: `RealtimeBattleRuntime.tickTimers` decrements `hitStunRemainingMs` every tick (`RealtimeBattleRuntime.ts:464`); `MovementSystem`, `ComboSystem`, `SkillSystem`, and `combatButtonState` all gate on `hitStunRemainingMs > 0` (see Scope), not on `state`.

### Dependencies

- **combat** (HitboxSystem for hit detection feeding into this, ComboSystem/SkillSystem for the attacker's `AttackDefinition`, MovementSystem consuming the resulting stun/knockback lockout) — all within the same `realtimeBattle` combat-core cluster.
- **enemy** — EnemyAISystem reads its **own** `state`/`hitStunRemainingMs` (`EnemyAISystem.ts:85-96`) to freeze itself when the enemy is the one stunned. There is no code path where enemy AI reads a stunned player/target's state to change its chase/attack behavior — grep for `player.state`/`player.hitStunRemainingMs` in `EnemyAISystem.ts` returns zero matches. Any AI-side "exploit the stun window" behavior is not implemented.
- No dependency on hero/adventure/pvp/economy/backend/social systems today.

### Done-criteria

1. `DamageSystem.test.ts` and `DamageSystem.fuzz.test.ts` pass (existing suite already covers this system — extend, don't fork a parallel test file).
2. A hit that leaves `target.hp > 0` always sets `state === 'hit'`, `hitStunRemainingMs === HIT_STUN_MS`, and `invulnerableUntilMs === elapsedMs + HIT_INVULNERABLE_MS` — assert via unit test.
3. Knockback displacement direction is deterministic: for `hitShape === 'horizontal'` it matches `horizontalKnockbackVector(attacker.combatFacing) * attack.knockback`; for all other shapes it matches `directionVector(attacker.facing) * attack.knockback` — regression-test both branches.
4. `MovementSystem` rejects movement input while `hitStunRemainingMs > 0` and accepts it again the tick after it reaches 0 (boundary test at `deltaMs` crossing zero).
5. If/when knockdown or per-attack `interruptible` is implemented (§3.6.5/§3.6.6/§3.6.8), the new `AttackDefinition.knockdown` flag must be **inert against normal-tier enemies** per §3.6.5's tuning-table-is-source-of-truth resolution — a done test must assert a normal mob never enters a knockdown/get-up state regardless of the landing move's `knockdown` flag.

### World-class bar

Separating **hitstun duration from knockback distance as two independently-tunable-per-move numbers** (never derived from one formula) is standard per-move frame-data practice across fighting games with a move-data table (Street Fighter, Tekken, KOF, Smash, and others) — worth borrowing because it's exactly the shape `hitstunMs`/`knockback` already take in this codebase's `AttackDefinition` (§3.6.7); the gap today is that hitstun is a single global `HIT_STUN_MS = 180` constant rather than per-attack, so different move weights currently feel identical on landing.

### Stay-current note

The global `HIT_STUN_MS`/`HIT_INVULNERABLE_MS` constants (`DamageSystem.ts:25,28`) will need to move to per-`AttackDefinition` fields (`hitstunMs` is already speced in §3.6.7 and even given baseline values in §3.6.12) once more than one hit-weight class ships — that's a near-term, already-planned change, not speculative churn.

### Low-maintenance-cost design

Keep hit-reaction tuning as **plain-object data on `AttackDefinition`** (as `knockback` already is in `attacks.ts`), not a class hierarchy or strategy-pattern per reaction type — this project already treats `attacks.ts` as the single source of truth for per-move numbers and `DamageSystem.applyDamage` as the single mutation point (its own doc comment at `DamageSystem.ts:63-67` states this is deliberate: "ทั้งหมดอยู่ที่เดียวเพื่อไม่ให้มีเส้นทางที่ลืมทำบางข้อ" — everything in one place so no path forgets a step). When `hitstunMs`/`knockdown`/`interruptible` land, add them as new fields on the existing `AttackDefinition` object and branch once inside `applyDamage`/`MovementSystem` — do not introduce an `IHitReactionStrategy` interface for what is still a single implementation (YAGNI, matches ECC common-rules bias against premature abstraction).

### Known scars (real historical precedent)

- **Scar**: In _Super Smash Bros. Melee_, Ice Climbers could chain grab-pummel timing ("wobbling") so the opponent never left grab-hitstun, producing a guaranteed 0%-to-death lock with no escape option — the cited incident is a Tennessee four-region tournament-ruleset ban that followed a "fake-ban" prank (Melee received no further balance patches, so the fix lived entirely at the ruleset layer, not in-game). — Source: [SmashWiki — Wobbling](https://www.ssbwiki.com/Wobbling); [Kotaku — "Super Smash Bros. Melee Technique Gets Fake-Banned And Then Actually Banned"](https://kotaku.com/super-smash-bros-melee-technique-gets-fake-banned-and-1832473327)
  **Test-for-us**: Try chaining a grab (or any attack whose `hitStunRemainingMs`/`invulnerableUntilMs` reset happens on a fast enough cadence) back-to-back on the same target and see whether a new `applyDamage` call can land and re-arm `HIT_STUN_MS` before the previous stun value ever ticks down to 0. This codebase already has a named anti-wobble guard, not an open question: every input gate (`MovementSystem.ts:97`, `ComboSystem.ts:76,148`, `SkillSystem.ts:38,100`, `combatButtonState.ts:18,28`) checks `state === 'dead' || hitStunRemainingMs > 0`, and `HitboxSystem.ts:92` (`if (target.invulnerableUntilMs > elapsedMs) return false`) rejects a hit while the target is still inside its post-hit invuln window — `DamageSystem.ts:27-28`'s own comment states `HIT_INVULNERABLE_MS` exists specifically to prevent "โดนรัวจนขยับไม่ได้เลย" (getting hit repeatedly with no chance to ever act). Don't take that guard on faith — try to construct the loop anyway: e.g. multiple simultaneous hitboxes that all resolve before `invulnerableUntilMs` is set from the first hit, or a skill/attack whose active-hitbox window outlasts its own `HIT_INVULNERABLE_MS` so a second hit from the _same_ attack lands after invuln was granted but before stun is consumed. Confirm the guard actually closes every path, not just the obvious one.

- **Scar**: Before hit-stun deterioration existed as a design pattern, fighting games could produce genuine infinite combos: hitstun from repeated hits didn't decay within a combo, so once a loop connected it could be repeated indefinitely — this is exactly the failure mode hit-stun-deterioration mechanics were later introduced to close. — Source: [SuperCombo Wiki — Hit Stun Deterioration (Marvel vs. Capcom 3)](https://wiki.supercombo.gg/w/Marvel_vs_Capcom_3/Combo_Limiters/Hit_Stun_Deterioration); [infil.net Fighting Game Glossary — Hit Stun Deterioration](https://glossary.infil.net/?t=Hit+Stun+Deterioration). _(Note: these two sources document the general mechanic and the design problem it exists to solve, not a specific Street Fighter II Champion Edition / M. Bison case — that named specific was dropped rather than asserted, since it could not be independently verified this session (WebSearch budget exhausted) and neither cited source actually supports it. If a Bison/Scissor-Kick-specific claim is wanted, it needs its own SF2CE-specific citation, e.g. SRK wiki or Shoryuken forums.)_
  **Test-for-us**: Land repeated hits on the same target back-to-back within one continuous engagement (not a single grab-lock, but a normal multi-hit combo/attack string) and check whether `HIT_STUN_MS` being a single flat global constant (`DamageSystem.ts:25`) means every hit in the string re-applies the _same_ fixed stun regardless of how many hits already landed — try to find a hit-rate/attack-speed combination where the target is functionally never able to act again for the rest of the engagement, purely from stacking flat per-hit stun with no combo-length-based falloff.

- **Scar**: _Tekken 7_'s Season 2 patch notes include a fix for a bug where a hit that knocked the opponent into a wall left them unable to perform an ukemi (tech roll / recovery input) afterward — a specific attack+geometry interaction silently denied the target's normal post-hit recovery option. — Source: [EventHubs — "Tekken 7 Season 2 patch notes released"](https://www.eventhubs.com/news/2018/sep/03/tekken-7-season-2-patch-notes-released/) ("Opponent was unable to do an ukemi when hitting a wall, so this was fixed.") _(⚠️ unverified this session: the quoted fix text itself is confirmed accurate against the source, but the specific attribution to Asuka's Rage Art / `During Rage d/f+1+2` notation could not be independently re-checked — WebSearch budget was exhausted before this task ran. Verify that character/input attribution directly against the EventHubs page before treating it as established; the underlying "wall + ukemi denial was a real patched Tekken 7 bug" claim is solid either way.)_
  **Test-for-us**: Land a knockback hit that drives the target into map/arena boundaries under each `hitShape` branch (`horizontal` via `horizontalKnockbackVector`, and the default `directionVector` branch, `DamageSystem.ts:86-89`) and confirm `hitStunRemainingMs` still decrements normally and `MovementSystem` unlocks input the tick after it reaches 0 in every case — per Done-criteria #4, but specifically probe the wall/boundary-collision case, since that's exactly the kind of geometry-dependent edge case that broke recovery in the cited incident.

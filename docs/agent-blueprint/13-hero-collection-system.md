# 13. Hero Collection System

> Category: Hero / Progression · Generated via gold-standard FILL + adversarial CB-lite verify (2 seats), 2026-08-07 · **revised after verify flagged an issue** · **amended 2026-08-10 per design-lock 3.a (see below) and onboarding citation-rot pass**.

### Scope

Owns: the hero roster as unlockable _content_ (`ROSTER` in `src/game/characters.ts:70-197` — id, name, rarity, archetype/`role`, base stats, model) and the single **client-side** account ownership ledger write-path (`grantCharacter` in `src/data/accountRepository.ts:753-783`, mirrored in `accountRepository.supabase.ts:682-701`) that turns "hero exists in the game" into "this account owns it" (`OwnedCharacter` in `src/types/player.ts:26-50`). It also owns the design constraint from §4.1: every roster entry must be a distinct archetype, never a reskin. This is **System #13 "Hero Collection System"** in `AGENT_BLUEPRINT.md:83` ("gacha unlock, archetype-differentiation rule. Source: §4.1") — see Dependencies below for a doc-tracking note tied to that numbering.

> **Design-lock 3.a (2026-08-10)**: hero ownership legitimately has TWO write paths now. `grantCharacter` remains the single CLIENT-SIDE path (local + Supabase RPC-fronted). Server-authoritative RPCs — currently `perform_gacha_pull` — write `owned_characters` directly inside their own transaction (`supabase/migrations/20260809073000_p9_gacha_server_authority.sql:254-263`) as a **sanctioned exception**, not drift: server-side atomicity for a paid-pull RPC is a stronger guarantee than routing back through a client-callable function. Done-criterion 5 below is amended accordingly.

Does NOT own: the RNG/roll/pity/cost mechanics (**Gacha System #23** — shipped, see Dependencies); leveling/star-ascension/skill-level math (**Progression #14** / **Star Ascension #15** — `OwnedCharacter` already carries `star`/`shards` fields seeded by this system's `grantCharacter` write-path, but computing/advancing that math is still #14/#15's job, not #13's); the hero's actual combat kit/kit-file pattern (**Hero Kit/Archetype System #12**).

### Inputs/Outputs

- In: `grantCharacter(uid: string, characterId: string): Promise<CharacterGrantResult>` — `characterId` must resolve via `getCharacter()` (`characters.ts:199-202`).
- Out: `CharacterGrantResult` = `{ ok: true, player: Player, characterId: string } | { ok: false, error: string }` — type declared at `accountRepository.shared.ts:74-75` (imported into `accountRepository.ts`); the `grantCharacter` function signature returning it is at `accountRepository.ts:753-756`. On success, appends one `OwnedCharacter` built by `createInitialOwnedCharacterProgress` (`src/game/progression/progressionMigration.ts:29-46`): `{ characterId, level: 1, exp: 0, expToNext: getExpToNextForLevel(1), obtainedAt: ISOString, skillLevels: <default>, talentState: { unlockedNodes: [] }, awakeningState: { tier: 0, unlockedEffects: [] }, progressionVersion: 1, star: 1, shards: 0 }` to `player.ownedCharacters`; does not touch `teamSlots` (comment at `accountRepository.ts:751` — team placement is a separate player choice). The Gacha RPC path (design-lock 3.a) builds its own row server-side inside `perform_gacha_pull` — see Dependencies — not through this function or `createInitialOwnedCharacterProgress`.
- Static content shape consumed by everything downstream: `Character` interface (`characters.ts:42-63`), `Rarity` union (`characters.ts:17`).

### Done-criteria

1. `grantCharacter` on an already-owned `characterId` returns `{ ok: false }` and leaves `ownedCharacters` unchanged (existing behavior at `accountRepository.ts:765-767`) — covered by regression + concurrency tests at `src/data/heroCollection.test.ts:41-76`.
2. `grantCharacter` on an unknown `characterId` returns `{ ok: false }` without touching the DB (`accountRepository.ts:757`) — covered at `src/data/heroCollection.test.ts:78-97`.
3. Every `ROSTER` entry has a `role` (archetype) distinct from every other entry — currently true for all 6 (นักรบกองหน้า / นักรบหนัก / ผู้สนับสนุน / นักธนูระยะไกล / ผู้ควบคุมสมรภูมิ / ผู้เรียกวิญญาณ, `characters.ts:77,98,119,140,161,182`); a data-lint/test now asserts this (`src/data/heroCollection.test.ts:100-112`), so §4.1's "no reskin" rule is machine-checked, not just eyeballed.
4. `accountRepository.ts` and `accountRepository.supabase.ts` implementations of `grantCharacter` stay behaviorally identical (same success/error shape, same `OwnedCharacter` defaults) — covered by `src/data/heroCollection.test.ts:115-149` (`describe('Local vs Supabase Shape Parity - Done-criterion #4')`, key-set + type parity between `createInitialOwnedCharacterProgress` and `mapOwnedCharacterRow`), plus the compile-time `AccountRepositorySubset` assertion (see Dependencies).
5. **Amended 2026-08-10 (design-lock 3.a)**: no second write path to `ownedCharacters`/`owned_characters` is introduced anywhere in `src/` outside `grantCharacter`, EXCEPT a server-authoritative RPC transaction that never round-trips through client-callable `grantCharacter` — currently `perform_gacha_pull` only. Grep gate over `src/` (per the file's own comment at `accountRepository.ts:749`) still holds for the client-side surface; it cannot see SQL-layer writes by construction, so any _new_ server-side grant path (future quest/login-reward RPC, etc.) must be checked by hand against this exception list, not assumed clean by the grep passing.

### World-class bar

**Brawl Stars (Supercell)** — same genre shape (real-time skill-based action combat, large collectible-character roster feeding PvP), and Supercell is publicly disciplined about never shipping a Brawler that's mechanically a reskin: every new character brings a genuinely distinct Basic/Super interaction before it's allowed into the pool. The concrete pattern worth borrowing isn't a code pattern from their client (not observable) but their _process_ gate — treat archetype-uniqueness as a checked property of the content pipeline, not a design-review judgment call. That's directly actionable here as item 3 above: a small test/lint over `ROSTER` that fails the moment two heroes collide on archetype, catching the §4.1 anti-pattern mechanically as the roster scales past 6.

### Stay-current note

With only 6 heroes and blueprint's own P10 ("Hero Collection expansion", `MASTER_BLUEPRINT_v3.0.md:550`) still pending, archetype-uniqueness checking by eye is fine today but will stop scaling once the roster grows past a handful — that's the one part of this design plausibly needing a real automated check later, not a redesign.

### Low-maintenance-cost design

Keep `ROSTER` a flat plain-object array (already the case, `characters.ts:70-197`) rather than a class hierarchy or per-archetype subtype/interface — there's exactly one shape (`Character`) and one archetype differentiator (`role`, a plain string), so no factory/strategy abstraction is warranted for 6 (soon more, but still homogeneous) data rows. Equally, keep `grantCharacter` the single CLIENT-SIDE mutator of `ownedCharacters` — the file states this as policy ("เมื่อมีระบบได้ตัวละครของจริงแล้ว ให้ระบบนั้นเรียกฟังก์ชันเดียวกันนี้ ไม่ต้องเขียนทางเพิ่มตัวละครเส้นใหม่", `accountRepository.ts:748-749`), and Gacha System #23 turned out NOT to extend this call site — it grants server-side via its own RPC transaction instead, sanctioned as an exception by design-lock 3.a (see Scope/Dependencies) rather than the originally-planned shared call site. Both the flat-array roster and the single client-side mutator remain the project's own established style (data-driven config over hardcoded branching, single source of truth over premature interfaces) — no new abstraction is justified until a second concrete _client-side_ unlock mechanism actually exists to justify one.

### Known scars (real historical precedent)

- **Scar**: A special-event login-timing bug let players receive the "New event!" entry reward twice by logging in around 5:00 PM on the event's start day — the reward grant fired a second time instead of being rejected as already-claimed. — Source: NamuWiki, "Brawl Stars/Bug" (en.namu.wiki/w/브롤스타즈/버그)
- **Test-for-us**: Call `grantCharacter(uid, characterId)` for the same account+hero twice back-to-back (and again racing two calls concurrently, e.g. via `Promise.all`), including across a process/day boundary if a future quest or login-reward path calls it — confirm the second call always returns `{ ok: false }` and `ownedCharacters` never ends up with two entries for the same `characterId`. This exercises done-criterion 1, but under concurrency/repeat-call pressure, not just a single sequential re-call.

- **Scar**: In the Pizza Planet event, leftover event currency from the _previous_ event incorrectly carried over and converted into the new event's currency instead of resetting to zero, so some players started the new event already holding unearned currency; Supercell later confirmed the cause and paid out compensation. — Source: talkesport.com, "Brawl Stars Pizza Planet Event Bug: Causes, Fixes, and Compensation Detail"; corroborated by sportskeeda.com, "Brawl Stars offers compensation for Pizza Planet event bugs"
- **Test-for-us**: When any future feature (gacha, seasonal quest, login-reward) grants a hero — via `grantCharacter` (client-side) or its own sanctioned server-side RPC (design-lock 3.a) — try running that flow across a reset/campaign boundary (e.g. simulate leftover in-flight state from a prior session/version) and check no `OwnedCharacter` entries appear in the ledger that the account didn't actually earn in the current cycle — i.e. state from an old code path or stale client build can't leak a hero grant into the new one.

- **Scar**: A "99 Brawler Quest" feature failed to recognize that a player already owned certain brawlers even though the underlying unlock had genuinely happened — a downstream consumer read stale/incorrect ownership state, distinct from the grant itself. Supercell's official account confirmed it as a tracking desync, not a lost unlock. — Source: Brawl Stars official X/Twitter account (x.com/BrawlStars, "BUG CHECKPOINT: 99 — We're aware of the issue causing the 99 Brawler Quests not recognising Brawler ownership")
- **Test-for-us**: This project has two live implementations of `grantCharacter` (`accountRepository.ts` local vs `accountRepository.supabase.ts` production, per the Dependencies section's flagged drift risk). Grant a hero through one implementation, then read `ownedCharacters` through every other consumer that will eventually depend on it (Progression #14, Star Ascension #15, any future quest/achievement check) and confirm they all agree a hero granted by one path is recognized as owned everywhere — not just by whichever function wrote it.

This project's own spec — `docs/agent-blueprint/13-hero-collection-system.md` and `docs/MASTER_BLUEPRINT_v3.0.md` — decides what "correct" behavior looks like here; Brawl Stars only supplies the shape of failure to test for, not the fix to copy.

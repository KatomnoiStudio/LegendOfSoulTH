# 2. Combat Facing System

> Category: Combat core · Generated via gold-standard FILL + adversarial CB-lite verify (2 seats), 2026-08-07 · **revised after verify flagged an issue**.

### Scope

`combatFacing.ts` (`src/game/realtimeBattle/combatFacing.ts`, 51 lines) owns deriving and mutating the **`CombatFacing`** axis (`'left' | 'right'`, `types.ts:23`) — the attack-only left/right facing that Blueprint §3.2 locks separately from the 8-way movement `Direction8` sprite facing (§3.1, `types.ts:19-20,39,41`). It owns: deriving facing from a movement/joystick vector with a deadzone + "keep previous facing on vertical-only input" fallback (§3.6.1 row "Vertical-only movement"), snapping an attacker's facing toward a target's X position (`faceTargetHorizontally`, used for enemy AI and any future skill-specific target lock per §3.6.1), producing the unit knockback vector for a given facing, and exporting a `Direction8`→`CombatFacing` mapping (`combatFacingFromDirection`) that is unit-tested but has **zero production callers** repo-wide — `createRealtimeBattle.ts:47,96` sets initial `combatFacing` via hardcoded `'right'`/`'left'` string literals, never by calling this function, so despite living in this module it does not actually drive spawn-state derivation today. It does **not** own: hitbox shape/reach math (`HitboxSystem.ts` consumes `attacker.combatFacing` but owns `hitsHorizontal`/`hitsRadial`), sprite frame selection (`EntitySprite.tsx:100` keys off `entity.facing`, the `Direction8`, never `combatFacing`), knockback/damage application (`combatReaction.ts:68-81`'s `applyKnockback` consumes `horizontalKnockbackVector` and applies it — `DamageSystem.ts` no longer imports from `combatFacing.ts` at all; it delegates entirely to `combatReaction.ts`'s `applyCombatReaction`), combo state (`ComboSystem.ts:102` copies `combatFacing`→`facing` to lock sprite direction mid-combo but doesn't compute it), or raw input capture (`RealtimeBattleRuntime.ts:162` owns `moveInput` and calls into this module per tick).

### Inputs/Outputs

- `combatFacingFromDirection(facing: Direction8): CombatFacing` — pure 8→2 mapping, `up`/`down` default `'right'`.
- `combatFacingFromVector(vector: Vec2, fallback: CombatFacing): CombatFacing` — `x < -0.12 → left`, `x > 0.12 → right`, else `fallback` (deadzone constant is inline, no config).
- `horizontalKnockbackVector(facing: CombatFacing): Vec2` — unit vector `{x: ±1, y: 0}`.
- `faceTargetHorizontally(attacker: {position: Vec2; combatFacing: CombatFacing; facing: Direction8}, target: Vec2): void` — mutates both `attacker.combatFacing` and `attacker.facing` in place based on `target.x >= attacker.position.x`.
- `applyCombatFacingFromMovement(entity: {combatFacing: CombatFacing}, direction: Vec2): void` — mutates `entity.combatFacing` via `combatFacingFromVector`.

No async, no network, no persisted state — pure/mutate-in-place functions over `types.ts` shapes only.

### Dependencies

- Depends on: `types.ts` (`Vec2`, `Direction8`, `CombatFacing`) only — zero cross-system imports.
- Consumed by (within Combat core / this project's naming — `AGENT_BLUEPRINT.md:44` does list this as taxonomy entry 2, "Combat Facing System"): `MovementSystem.ts:131` (movement tick), `RealtimeBattleRuntime.ts:198` (per-frame input pipeline), `EnemyAISystem.ts:262` (enemy target-facing → feeds **enemy system**), `AllyAISystem.ts:39,45` (summon-ally target-facing → also feeds **enemy system**'s shared AI core per §3.8.3), `HitboxSystem.ts:48` (attack hit test → feeds **hero/combat** basic-attack resolution), `combatReaction.ts:75` (knockback direction — `DamageSystem.ts` delegates to `combatReaction.ts`'s `applyCombatReaction`/`applyKnockback` and no longer imports from `combatFacing.ts` directly), `ComboSystem.ts:102` (facing lock during combo lockout), `createRealtimeBattle.ts:106,192,224` (initial entity state). No dependency on adventure/pvp/economy/backend/social systems, and nothing outside Combat core feeds into it.

### World-class bar

**Streets of Rage 4** (Dotemu/Lizardcube/Guard Crush Games, 2020) — the modern reference for the "2.5D plane, up/down = depth, attack locked to left/right" belt-scroller model this blueprint explicitly specifies (§3.1, §3.2). The genre convention this blueprint follows (and which this module already implements): keep the **sprite/movement facing** (continuous, 8-way, cosmetic) and the **attack-axis facing** (binary, drives hitbox math) as two separate pieces of state that sync opportunistically rather than one field serving both — exactly the `facing` vs `combatFacing` split already in `types.ts:73,75`. This is a general architecture principle for the 2.5D-depth/L-R-attack-axis model, not a claim about SoR4's own (closed-source) internal implementation — preserve the split here regardless; don't collapse it for "simplicity."

### Stay-current note

The `±0.12` vector deadzone in `combatFacingFromVector` is a hand-tuned magic constant with no data-driven backing, and `faceTargetHorizontally` today has two callers — `AllyAISystem.ts:39,45` and `EnemyAISystem.ts:262` — §3.6.1 explicitly allows future skills to opt into "skill-specific target lock" beyond the Ultimate, which will add more callers and likely surface a need to retune or parameterize that deadzone per input device (touch vs analog stick vs keyboard). Separately, `combatFacingFromDirection` is exported and unit-tested but has zero production callers today (see Scope) — worth flagging for removal or for wiring into `createRealtimeBattle.ts` next time that file's hardcoded facing literals are touched, rather than letting it drift as untracked dead code.

### Low-maintenance-cost design

The whole module is plain exported functions over `Vec2`/`CombatFacing` plain objects — no class, no interface, no DI container — matching every sibling `*System.ts` file in `src/game/realtimeBattle/` (`MovementSystem.ts`, `DamageSystem.ts`, `HitboxSystem.ts`, `EnemyAISystem.ts` are all plain function modules — confirmed by grep: `MovementSystem.ts`, `DamageSystem.ts`, and `EnemyAISystem.ts` each `import { fn } from './combatFacing'`; `HitboxSystem.ts` has no import from this module at all and instead reads `attacker.combatFacing` as a plain data field — either way, never a service instance). One file, one concern, one implementation of each function — resist wrapping this in a "FacingService"/strategy interface; there is exactly one behavior per function and the only tunable (the `0.12` deadzone) is a single inline constant, not a config surface that needs abstracting.

Exemplar used: Streets of Rage 4 (Dotemu / Lizardcube / Guard Crush Games, 2020) — same exemplar the file cites. No substitution needed: SoR4 is closed-source, so there's no engine postmortem/bug-tracker to mine, but its official patch notes and Steam Community bug threads document real, specific facing/hit-detection failures in the shipped game.

### Known scars (real historical precedent)

- **Scar**: In SoR4's September 2020 balancing patch, the enemy Raven had to be explicitly fixed to "turn towards the target when rising" — i.e., before the fix, an enemy recovering from a knockdown/rising state attacked using a stale facing instead of re-deriving it from the target's actual position. — Source: Dotemu official blog, "Streets of Rage 4 new balancing patch now available" (dotemu.com/streets-of-rage-4-new-balancing-patch-now-available/), dated "07/09/2020". That date string alone is ambiguous between DD/MM and MM/DD; resolved via a contemporaneous secondary source that spells the month out: Wccftech, "Streets of Rage 4 Sells Over 1.5 Million, Update Includes Tons of Fixes and Balance Tweaks" by Nathan Birch, published September 7, 2020 (wccftech.com/streets-of-rage-4-1-5-million-update/, also cited by Wikipedia's Streets of Rage 4 article for the same 1.5-million-downloads/balance-patch milestone) — confirming the Dotemu date is DD/MM, i.e. 7 September 2020, not July.

Check whether `EnemyAISystem` calls `faceTargetHorizontally` before the next attack resolves — or whether the attack/knockback fires toward the pre-interrupt (stale) `combatFacing`.

- **Scar**: Steam Community bug reports describe SoR4 enemy weapon-rush attacks connecting on the player "from behind" even after the player evaded past the enemy, while the player's own weapon attacks needed near-pixel-perfect vertical alignment to land — an asymmetric, apparently facing-independent hit-detection gap reported by multiple players (not confirmed patched in official notes). — Source: Steam Community discussion, "Enemies with weapons need to be fixed" (steamcommunity.com/app/985890/discussions/0/2252307485539200865/)
  **Test-for-us**: Start an attack, then move the target across the attacker so it ends up on the opposite side mid-animation (target's X crosses the attacker's X before the hit-frame resolves, or `combatFacing` flips mid-attack from new input). Verify `HitboxSystem`'s `dx * sign < -hurtboxRadius` guard reads the facing/position _at hit-resolution time_, not a value captured at attack-start — try to land a hit "from behind" the attacker's current facing.

- **Scar**: The same Steam thread documents a second, separate asymmetry: players report that being positioned slightly above an enemy lets an attack connect normally, but being slightly below the enemy at the same horizontal distance sometimes prevents the hit entirely — the depth/vertical axis interacting inconsistently with the horizontal-facing hit check. (Community-reported; unverified whether ever patched — flagging as ⚠️ unverified-fix-status, but the mechanical complaint itself is real and documented.) — Source: same Steam Community discussion.
  **Test-for-us**: Since `combatFacing` here is derived purely from `vector.x` (the depth/Y axis never enters `combatFacingFromVector`), check whether `HitboxSystem`'s consumption of `attacker.combatFacing` for `hitsHorizontal` produces symmetric hit/no-hit results for a target offset the same horizontal distance but on opposite sides of the attacker on the depth (Y) axis — confirm depth offset never silently gates a hit that the facing math alone would allow.

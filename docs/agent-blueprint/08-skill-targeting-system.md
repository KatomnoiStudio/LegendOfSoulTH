# 8. Skill-Targeting System

> Category: Combat core · Generated via gold-standard FILL + adversarial CB-lite verify (2 seats), 2026-08-07 · **revised after verify flagged an issue**.

### Scope

Owns: the per-skill decision of _which enemy_ an attack's hit-resolution locks onto, for skills whose kit row is explicitly flagged `targetLock: 'nearest'` (currently only the Monkey King Ultimate, §3.7) — selecting the nearest enemy from `state.enemies[]` at cast start and persisting that same target through the skill's currently-shipped single startup→active→recovery window (`MONKEY_GOLDEN_FURY`, `attacks.ts:169-183`, itself commented "placeholder content, P3 framework").

**Explicitly does NOT own** (in addition to the items already excluded below): the "4 strike phases" strike-sequencing described in §3.7 ("Ultimate strike-phase resolution") or the `interruptible` hyper-armor field (§3.6.12) — neither exists in code today (`grep -rn "phase" src/game/realtimeBattle` and `grep -rn "interruptible" src/` both return zero hits; `SkillState`/`stepSkill` in `SkillSystem.ts` track one `sinceStartMs` against one attack's `totalDurationMs`, no phase index). Per the project's own system taxonomy (`AGENT_BLUEPRINT.md:46` vs `:50`), per-phase interrupt/`phaseOverrides` belongs to system #4 "Skill/Cast System", not system #8 "Skill-Targeting System" that this contract scopes. Building the phase container is a separate, currently-unscoped prerequisite — see Dependencies.

Also does not own: basic-attack hit detection (multi-target, no lock — §3.6.2, `HitboxSystem.ts`), movement/facing/camera soft-target or auto-snap (explicitly cut, §3.6.1 + §3.6.10), damage/knockback math (`DamageSystem.ts`), or the enemy-side AI's own player-targeting (`EnemyAISystem.ts:100`, unrelated distance check).

### Inputs/Outputs

Not implemented yet, so this is the contract to build against `AttackDefinition` (`src/game/realtimeBattle/attacks.ts:15`), not existing code:

- **Input:** `state.enemies: RealtimeBattleEntity[]` (positions) + caster position, read once at cast start (skill activation, not per-frame).
- **New field on `AttackDefinition`:** `targetLock?: 'nearest'` (absent = no lock, current behavior for all shipped skills).
- **Output:** a resolved `lockedTargetId: string | undefined` held on the skill's runtime cast state (alongside existing `SkillState` cast bookkeeping in `SkillSystem.ts` — `definition`, `sinceStartMs`, `hitTargets`), consumed by `HitboxSystem.ts` in place of the normal hit-shape sweep for that skill's active window. Held for the duration of the current single active window; there is no phase boundary to persist across yet (see Scope). The field is additive and forward-compatible — a future per-phase cast loop can keep reading the same `lockedTargetId` on every active window without this contract's logic changing.

### Dependencies

- **combat/hero systems** (this repo's actual module boundary, not the 28-system list which doesn't map 1:1 onto this codebase): consumes `AttackDefinition` (`attacks.ts`), `RealtimeSkillDefinition`/`RealtimeSkillKit` (`skills.ts`), feeds into `HitboxSystem.ts` and `DamageSystem.ts`.
- **enemy system**: reads `state.enemies[]` (`createRealtimeBattle.ts:21`) for candidate positions.
- No dependency on backend/economy/social/pvp/adventure — this is client-side combat-frame logic only.
- **Resolved dependency:** system #4 now owns per-phase interrupt/`phaseOverrides`; all 4 Ultimate strikes keep the same locked target, telegraph/startup/active have hyper-armor, and recovery remains interruptible. Targeting code must not reacquire a different enemy between strike slices.
- **Conflicting mechanism to reconcile before phase-spanning ships:** today's anti-repeat-hit dedup (`hitTargets: Set<string>` on `SkillState`, `SkillSystem.ts:16`; consumed as `alreadyHit` in `HitboxSystem.ts:36/91`, comment "ศัตรูแต่ละตัวโดนได้ครั้งเดียวต่อการร่าย" — each enemy can be hit only once per cast) is scoped per-cast, not per-window. §3.7's "4 clones converging on one target" requires the _same_ locked enemy to take 4 separate hits across 4 phases of one cast — which the current per-cast dedup would suppress after phase 1. This contract's single-window target-lock does not touch or need to touch `hitTargets`; whoever builds the phase system must redesign the dedup scope (e.g. per-phase instead of per-cast) as part of that work, not this one.

### Done-criteria

1. A skill with `targetLock: 'nearest'` and 0 enemies in `state.enemies[]` at cast time does not crash and resolves to a defined no-target/whiff behavior (specify one: skip damage, or fall back to facing-direction hit shape) — unit test covers empty-enemies case.
2. Locked target is captured once at cast start and reused unchanged for the rest of that cast's active window, even if a _closer_ enemy appears mid-cast — unit test: spawn a second, closer enemy after cast start but before the active window resolves; assert damage still resolves against the originally-locked enemy, not the new closer one. (Scoped to the current single-window Ultimate — see Scope. When system #4's phase infra ships, this criterion should be extended with a phase-boundary variant; that extension is out of scope here because there is no phase boundary to test against yet.)
3. If the locked enemy dies or leaves `state.enemies[]` before the skill's active window resolves, damage is skipped for it (no crash on stale id) — unit test.
4. Skills without `targetLock` are unaffected — existing `HitboxSystem.test.ts` / `DamageSystem.test.ts` pass unchanged.
5. This contract's target-lock resolution does not read or mutate `hitTargets`/`alreadyHit` — verified by criterion #4 passing with zero changes to `SkillSystem.ts`'s existing dedup lines (16, 66, 102, 112) and `HitboxSystem.ts`'s existing dedup lines (36, 91). This keeps the per-cast dedup vs. per-phase-hit conflict flagged in Dependencies fully contained to future phase-system work, not leaked into this contract's diff.

**Explicitly out of scope / not a done-criterion here:** asserting `interruptible: false` across "all 4 Ultimate phases" (§3.6.12). Neither `interruptible` nor a phase container exists in code; this belongs to system #4 "Skill/Cast System" per `AGENT_BLUEPRINT.md:46`, and should be a done-criterion on _that_ system's contract once it's written, tested there alongside its own phase machinery — not folded into this system's target-selection tests.

### World-class bar

**Genshin Impact / Honkai: Star Rail ultimates** (named directly in the blueprint, §3.7) — the pattern worth borrowing: ultimate target-lock is acquired once at cast start and held for the full multi-hit sequence regardless of battlefield changes mid-animation, rather than re-querying nearest-enemy every strike (which would look erratic when enemies move/die between hits). This repo's blueprint already names this exemplar and pattern explicitly — no invention needed here. Note: the exemplar's _full_ pattern is multi-hit-across-a-sequence; this contract delivers the target-lock half of it (correct today, against the single-window Ultimate) — the multi-phase-sequence half ships when system #4's phase infra lands, per Dependencies.

### Stay-current note

None — stable surface. This is a narrow, single-consumer selection rule (nearest-at-cast-start, persist-through-the-cast) scoped to one flag on one field; it doesn't touch rendering, input, or platform APIs that genre/tooling churn would affect.

### Low-maintenance-cost design

Single source of truth, no new abstraction: add `targetLock?: 'nearest'` as one optional field on the existing `AttackDefinition` interface (`attacks.ts:15`) — the same file already carries the project's stated rule that "ค่าจังหวะทุกตัวอยู่ในไฟล์นี้ไฟล์เดียว ห้ามกระจายไปเขียนใน component" (`attacks.ts:2-5`). Do not build a generic `TargetingStrategy` interface/registry for a single `'nearest'` case with one consumer (Ultimate) — that's the exact one-implementation-interface YAGNI trap this project's own style avoids elsewhere (data-driven config over hardcoded values, but no premature polymorphism). Resolve the locked-target id with a plain `distanceBetween` loop over `state.enemies[]` (the helper pattern already used at `EnemyAISystem.ts:100`) inline in `SkillSystem.ts`'s cast-start handling — no new file, no new dependency.

This low cost holds **only for the scope stated above** (single-window lock-and-persist). It does not include, and should not be read as pricing, the phase-sequencing data model or the per-cast-vs-per-phase dedup rework flagged in Dependencies — those are a materially larger, separately-scoped piece of work that a future system #4 contract should price on its own terms.

### Known scars (real historical precedent)

⚠️ **Unverified (source-grounding canary)**: the three patch numbers/dates below (Genshin 2.6 / 2022-04-06, HSR Argenti Patch 1.6, Genshin Nilou fix in 3.2) are version-sensitive facts. This session's web-search budget was already exhausted before they could be re-checked against primary HoYoverse patch-note pages — confirm against official patch notes before treating this doc as final. The article titles/existence themselves were confirmed real by a prior citation pass.

- **Scar**: Genshin Impact's Yae Miko totems switched to strict "attack the nearest enemy" logic in Patch 2.6, which backfired badly in ordinary combat (nearest enemy shielded, behind an obstacle, or otherwise a bad pick) — HoYoverse publicly apologized for not testing all combat scenarios and rolled the change back in a follow-up update (2022-04-06). — Source: GamesRadar+ ("Genshin Impact makes 'adjustments' to Yae Miko's broken targeting"), PCGamesN ("Genshin Impact's Yae Miko targeting fix is getting fixed")
  - **Test-for-us**: Construct a multi-enemy scene where the geometrically-nearest enemy is a bad pick by any other measure this project cares about (e.g. an enemy that's about to leave `state.enemies[]`, or one placed adversarially close but behind/past the caster's facing) and confirm the `nearest` resolution still produces a **defined, deterministic, non-crashing result** — same bar as the other two scars below (determinism/no-crash, not "does it look bad to a player"). This project's own Done-criteria (`docs/agent-blueprint/08-skill-targeting-system.md`) and its "Low-maintenance-cost design" section deliberately specify a plain `distanceBetween` loop with no facing/obstacle/shield awareness ("no premature polymorphism") — so this test must not smuggle in HoYo's fix (avoidance logic) as the pass bar. It only checks that the plain-nearest algorithm this project chose to ship still resolves predictably, not that it picks the "smart" target.

- **Scar**: Honkai: Star Rail's Argenti Ultimate resolves multiple bounce-hits against a target pool; when enemies died before all bounces resolved, the bounce-selection logic kept landing hits on already-dead enemies instead of redirecting to the remaining living target, silently gutting his single-target damage. HoYoverse confirmed the bug and fixed the targeting logic in Patch 1.6. — Source: Prydwen Institute blog ("Argenti is bugged and not working as he should!", 2023-12-12); Honkai: Star Rail Fandom wiki Version 1.6 patch notes
  - **Test-for-us**: For done-criterion #3 (locked enemy dies/leaves before the active window resolves), don't just assert "no crash" — assert the _damage/hit outcome_ explicitly: write the test to catch a silent-no-op failure mode (hit resolution runs against the stale `lockedTargetId` and produces zero damage/effect without any error) as distinct from a correctly-skipped hit, since the real-game bug was exactly this kind of quiet waste, not a crash.

- **Scar**: Genshin Impact's Nilou Elemental Burst ("Dance of Abzendegi") intermittently executed its full animation but dealt zero damage to any enemy. Nilou released in Version 3.1 (~2022-09-28); the bug was reported at launch and a fix shipped in the very next version, 3.2 (~2022-11-02) — one patch cycle, not a prolonged multi-patch neglect. — Source: GameRant ("Genshin Impact Players Complain About Nilou's Frequent Elemental Burst Bug", 2022-10-20); Genshin Impact Fandom wiki Version 3.2 patch notes
  - **Test-for-us**: Stress the 0-enemies / enemy-removed-at-cast-boundary path (done-criterion #1) for a silent "cast plays, resolves, but nothing happens and no whiff/no-damage state is ever surfaced" outcome — confirm the no-target case is deterministic and always resolves to the one specified behavior (skip damage or facing-direction fallback), never to an ambiguous "ran but did nothing" state that would look like this exact bug to a player.

None of the exemplar's own fixes are prescriptive here — this project's own contract (`docs/agent-blueprint/08-skill-targeting-system.md` Done-criteria, and `docs/MASTER_BLUEPRINT_v3.0.md`) is what "correct" means for this system; the incidents above only establish _what shape of failure_ (wrong-target picked deterministically-but-badly, silently-wasted hits on a stale target, silent zero-effect resolution) is worth actively trying to reproduce against this codebase's own logic. The Yae Miko test in particular is bounded to determinism/no-crash, not "player perception of the pick," because this project's contract explicitly declines the avoidance logic that would be needed to satisfy a player-perception bar.

# 20. PvP Power Normalization

> Category: PvP · Generated via gold-standard FILL + adversarial CB-lite verify (2 seats), 2026-08-07 · **revised after verify flagged an issue**.

### Scope

Owns the ephemeral stat-normalization step applied to a hero's **Hero Level** and **Skill Level** for the duration of a ranked PvP match, so that only **star tier** produces a power difference in ranked (blueprint §3.8.5, §6.2 line 458). It does **not** own: the star-gap bound itself (★6 ≤ 130% ★1 — this number appears in §3.8.5's own prose, paraphrasing fork issue #35; §4.3 only says the gap "must be bounded," no number, so §4.3 is not an independently-numbered source for 130%); matchmaking/rank-band/MMR/Elo (§6.2, numbers deferred to P13); the PvP combat core, movement, or damage pipeline (§6.3 — reuses the existing PvE combat entities verbatim); or opposing-player knockdown-tier mapping (§3.8.7, deferred to P12). PvE progression and PvE stat computation are explicitly untouched by this system (§6.2).

**Dependencies shipped**: #14 Progression System and #15 Star Ascension System both landed (TASKS.md rows 21/23) before this contract's own implementation (PR #95). `resolveFinalCombatStats()` (`src/game/progression/heroStatsResolver.ts`) provides the level-driven attack/defense formula and `statsAtStar()` (`src/game/heroes/starScaling.ts`) provides the star-to-power scaling, both wired into `createPlayerEntity()` (`src/game/realtimeBattle/createRealtimeBattle.ts:94-95`).

### Inputs/Outputs

- **In:** an `OwnedCharacter`-shaped record (`characterId`, `level`, `exp`, `skillLevels`, `star` — see `src/types/player.ts:26-50`) plus the `RANKED_BASELINE` constant (`{ heroLevel: progressionConfig.maxHeroLevel, defaultSkillLevel: progressionConfig.defaultSkillMaxLevel }`, `src/game/pvp/rankedNormalization.ts:9-12`). `OwnedCharacter` already has both a required `skillLevels` field and an optional `star` field (default ★ 1) — landed as part of #14/#15, not this system's own scope.
- **Out:** a derived, in-memory combat-stat snapshot (not a new persisted type) fed into whatever level/skillLevel/star-aware stat computation `createPlayerEntity()` ends up doing once Progression (#14) and Star Ascension (#15) ship — `level`/`skillLevel` replaced with the ranked baseline, `star` passed through unmodified. Never written back to `Player`/`OwnedCharacter` or `localStorage`/Supabase — match-scoped only.
- **Today's actual entity-construction path**, verified in `src/game/realtimeBattle/createRealtimeBattle.ts` (`createPlayerEntity()`, called from `createRealtimeBattle()`): `atk`/`def`/`maxHp` are all level- and star-scaled. `resolveFinalCombatStats({ heroId, level })` (`src/game/progression/heroStatsResolver.ts`) computes level-scaled stats, then `statsAtStar(leveledStats, owned?.star ?? 1)` (`src/game/heroes/starScaling.ts`) applies the star multiplier — both at `createRealtimeBattle.ts:94-95`. `skillLevels` and `star` both exist on `OwnedCharacter` (`src/types/player.ts:37,47`). Swapping in `RANKED_BASELINE.heroLevel`/skill caps therefore affects the full `atk`/`def`/`maxHp` triple.

### Dependencies

- **#14 Progression System (Hero Level/Skill Level)** — Tier 1, **shipped and graduated** (TASKS.md row 21, 100%, PR #52). Owns the EXP curve and the skill-level scaling formula (`SkillProgressionSystem.ts`, `heroStatsResolver.ts`) this system normalizes against.
- **#15 Star Ascension System** — Tier 2, **shipped, CI-green at 90%** (TASKS.md row 23). Owns the star field and the star-to-power scaling formula (`starScaling.ts`, canonical 1.00/1.06/1.12/1.18/1.24/1.30 multipliers) that produces the §4.3-bounded power gap this system preserves via pass-through.
- **hero/character system** — source of `level` per owned character today (`src/types/player.ts`, character data module); source of `star`/`skillLevel` once #14/#15 exist.
- **combat entity construction** (`createPlayerEntity()` in `src/game/realtimeBattle/createRealtimeBattle.ts`, called from `createRealtimeBattle()`) — the actual integration point: this is where `level` currently feeds `calcMaxHp`, and where a future skillLevel/star-aware calc would live. **Not** `DamageSystem.ts`/`calcDamage` — that function only consumes already-computed `atk`/`def`/`hp` off a `RealtimeBattleEntity` mid-hit and never touches `level`/`skillLevel`/`star`; per §6.3's "same combat core," this system only needs to substitute inputs before `createPlayerEntity()` runs, not inside the damage math.
- **pvp system** (matchmaking/rank-band) — feeds this system a matched pair of heroes; that system does not exist in `src/` yet either (no `pvp`/`ranked`/`mmr`/`elo` code found by repo-wide grep) — tracked separately as #19, not a blocker for this contract's own scope.
- Not depended on by economy, backend, or social systems.

### Done-criteria

1. `OwnedCharacter` has `star` and `skillLevels` fields (`src/types/player.ts:37,47`) — landed as part of #14/#15, following the existing optional-field pattern (`star?: number`, defaulting to ★ 1 for legacy records, same shape as `player.inventory ?? []` / `normalizePlayer`, `src/data/accountRepository.ts:336`). Satisfied.
2. A pure function `toRankedStats(char, baseline)` returns identical `level`/`skillLevel` output for two `OwnedCharacter`s with the same `star` but different `level`/`skillLevel` — unit-testable, no RNG/IO.
3. Same function, `star` field on the output is byte-identical to the input `star` (pass-through, unmodified) for two `OwnedCharacter`s with different `star`. Now that #15 has shipped a star-to-power formula (`statsAtStar()`), the 130% bound is directly testable and tested: `rankedNormalization.test.ts` ("★6 remains within the existing 130% cap after ranked normalization") asserts `sixStar.hp/atk/def / oneStar.hp/atk/def <= 1.3` end-to-end through `createRankedPlayerEntity()`, in addition to this pass-through check.
4. Calling this function must not mutate the input `OwnedCharacter`/`Player` object (no write-back) — assert via reference/deep-equality check in the test.
5. A regression test confirms the PvE stat path (adventure/`WukongAdventure` battles, i.e. `createPlayerEntity()` called outside a ranked-match context) is untouched — i.e. this function is never called outside a PvP match context.

### World-class bar

Named exemplar (also the one the blueprint itself cites, §3.8.5): **Summoners War's ranked arena.** The one pattern worth borrowing: normalize level/skill investment to a fixed ranked ceiling so that rarity/investment (here: star) remains the _only_ intended axis of power difference — everything else gets clamped to baseline, not scaled down.

### Stay-current note

§4.2 currently defers Talent, Awakening, Equipment, and Loot affixes to a later phase. Once any of those ship, this system's normalized-field set (today just Level + Skill Level) will need to expand to cover them too, or the same "fresh vs. maxed" gap this system exists to close reopens through the new layer. Separately: #14 (Progression) and #15 (Star Ascension) landing is not just a dependency to wait on — once their stat formulas exist, Done-criterion #3 above should be revisited to add a real power-gap assertion against those formulas, since today's pass-through check is a weaker stand-in.

### Low-maintenance-cost design

One `RANKED_BASELINE` constant (single source of truth for the ranked level/skill-level cap) feeding one pure function that swaps those two values before `createPlayerEntity()` builds the combat entity — no parallel PvP stat pipeline, no `IStatNormalizer` interface/strategy class for what is a single implementation. This matches the project's established style: small pure `normalize*` functions over class abstractions (`normalizeTeam` — `src/game/team.ts:51`; `normalizePlayer` — `src/data/accountRepository.ts:336`), and §6.3's own instruction that PvP reuses the PvE combat core rather than forking it. Once #14/#15 add real level/skillLevel/star-driven stat math inside `createPlayerEntity()`, this system's substitution point stays the same — it swaps two input values before that function runs, regardless of how much heavier the math behind it gets.

### Known scars (real historical precedent)

- **Scar**: Clash Royale's "Classic Decks" mode — which normalizes every card to one fixed level so real card investment doesn't matter in that mode — shipped with card levels that didn't match the intended normalized values, and had to be hotfixed. Source: Supercell official Clash Royale blog, "Maintenance – Bug Fixes and Balance Changes" release notes (19 Jun 2024): _"Corrected card levels in Friendly Classic Decks to match expected levels."_ (supercell.com/en/games/clashroyale/blog/release-notes/maintenance-bug-fixes-and-balance-changes/) — verified by direct fetch of that URL; quote and date match verbatim.
- **Test-for-us**: Feed `toRankedStats()` a wide spread of real `OwnedCharacter` level/skillLevel combinations — including values at, above, and below `RANKED_MAX_LEVEL`/`RANKED_MAX_SKILL_LEVEL`, and characters that were already sitting exactly at the baseline — and diff every output field against the `RANKED_BASELINE` constant. Try to find any input where the normalized `level` or `skillLevel` comes out as something other than an exact match to baseline (drifts, is left un-clamped, or silently passes the _input_ value through instead).

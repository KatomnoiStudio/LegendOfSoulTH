## Rules (from BELT-PORT.md §2 — the registry inherits them, restated once)

- PIN model + effort on EVERY dispatch. Unpinned = inherits the session, silently.
- fable = FLIP-ONLY, never a standing default in any row. haiku = NEVER (category mismatch).
- **Where fable CAN land (per role, from the grounded table — a flip is recorded in the row's notes, spend-consent-gated every time):**
  - Implementation / engine: candidate ONLY after a lower tier is PROVEN insufficient on that task (≥2 bounced rounds on a hard bug / architecture) — flip, then the row returns to standing.
  - Review / QC: DOWNGRADED candidate — escalation after ≥2 stuck rounds, at effort **high not xhigh** (its measured review failure mode is NOISE: worse precision + noisier comments than the prior top tier on a dated 105-example benchmark).
  - Docs / ship-text / throwaway probes: NEVER.
  - Belt end / main seat: outside routing entirely — user-set (the owner picking fable for their own session, as now, is the owner's call, not a registry event).
- **New system = new ratification (owner ruling 2026-08-09):** a new `docs/agent-blueprint/NN-*.md` contract does NOT silently inherit the 2/dispatch formula. It enters the Per-system headcount table only through the same walk systems 1–28 got — ground scope/size/kinds → propose → owner ratifies → row lands. **No dispatch to a system whose row does not exist yet.** **Then HIRE its caretaker IMMEDIATELY** (owner ruling, same day) — a newborn system starts staffed; **main is FORBIDDEN from carrying a newborn's work via the deepest-knowledge fallback**. The lazy caretaker-row rule applies to the pre-belt backlog (systems 1–28), never to newborns.
- **Recurrence trigger (owner ruling 2026-08-09):** the main/aide fallback is for ONE-OFFS. The same topic landing on main repeatedly → hire a caretaker for that TOPIC (propose row → owner ratifies → hire immediately). Main จับฉ่าย — grab-bag, never pack-mule; a recurring line of work is always somebody's standing job, never main's.

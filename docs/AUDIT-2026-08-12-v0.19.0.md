## 1. The two findings that cost a player something today

### 1.1 Skill upgrades charge gold and deliver nothing

`src/game/realtimeBattle/DamageSystem.ts:58` is the entire damage formula:

```ts
const base = attacker.atk * attack.damageMultiplier * variance
```

`attack.damageMultiplier` belongs to the **move**. Nothing in the formula reads the **skill level**.

- `resolveSkillDamageMultiplier` (`src/game/progression/skillProgressionResolver.ts:73`) — **0 callers**.
- `getEffectiveLevels` / `applySkillExp` (`src/game/realtimeBattle/SkillProgressionSystem.ts:36,69`) — **0 importers outside tests**. The four real importers take only `createDefaultSkillLevels` and the `SkillSlotId` type.
- `grep skillLevel|damageScale` in `DamageSystem.ts` and `SkillSystem.ts` — **0 hits each**.

Meanwhile the UI promises the buff: `src/game/progression/progressionConfig.ts:86-93` ships the ladder `damageScale 1 → 1.05 → 1.1 → 1.15 → 1.2` at costs `50 + 80 + 120 + 180 = 430 gold` per skill, surfaced through `progressionViewModel.ts:38-44`.

The server side is **correct in every respect** — `spend_progression_upgrade` (641 lines, `20260810180000_p26_progression_cost_authority.sql`) debits the gold, writes the ledger, and CAS-guards replay. It is faithfully charging for an effect that was never wired.

**Same shape, second instance**: `ascendCharacterStar` (`src/data/accountRepository.supabase.ts:933`) has **0 callers** outside its own definition. Shards are granted and shown to the player (`GachaModal.tsx:124`, `"ตัวซ้ำ +N ชิ้นส่วน"`) with no path to spend them.

Both are invisible to the toolchain: `tsc -b` and `oxlint --deny-warnings` **both exit 0**. Every line is valid. Nothing calls it.

### 1.2 A completed reward can show one number and pay another

`src/game/reward/rewardGrantService.ts:71` reuses **one `refId` for every currency entry** in a resolve. `p5-test-dungeon` yields three distinct gold entries (75 + 50 + 15, `rewardConfig.ts:16,24,51`), and `mergeEntries` (`rewardResolver.ts:25-41`) only merges byte-identical ones, so all three are granted under the same id.

The second `earn_gold` hits `currency_transactions_profile_ref_unique` (`0013_reward_idempotency.sql:29`) → `unique_violation` → the RPC returns the profile **uncredited** (`0013:60-64`) → `accountRepository.supabase.ts:682` sees `error == null` → `{ok: true}`.

**Result screen shows 125 gold. The player receives 75.** The dedupe built to stop double-grants silently eats a legitimate second grant.

**Currently dormant** — `DungeonSession` is never rendered (imported only by its own test), and the repo documents this at `rewardGrantService.ts:118-133` as a `⚠ DORMANT TRAP` with the required fix order. Four sibling findings in the same file are dormant for the same reason and are **not** reported as new; the project already wrote them down.

### 1.3 Two tabs of one account delete each other's friends — and the dead backend guards what the live one does not

`savePlayer` (`src/data/accountRepository.supabase.ts:573-668`) writes `profiles` → `friends` → `team_slots` with no version column, no compare-and-swap, and no transaction. The friends step prunes from a list held in **client memory**:

```
delete from friends where profile_id = … and friend_uid not in ("<the list this tab loaded>")
```

Tab A adds friend X (`:635` upsert, `:639-647` prune). Tab B, still holding a `player` object from before X existed, saves anything at all — a name change, a team swap, a progress flag — and its prune deletes X. `savePlayer` returns `true`, `updatePlayer` returns `true`, and the panel has already told the player _"เพิ่ม…เป็นเพื่อนแล้ว"_. The same shape clobbers `team_slots` (`:667`) and `progress.flags` (`:583`).

A grep of that file for a `state_version`/`updated_at` guard returns nothing. **The localStorage backend — the one that is dead code — guards this exact case** with a `rev` compare-and-swap (`accountRepository.ts:223-234`), and every caller there converts the failure into a visible error. The guard exists in the repository; it is on the wrong backend.

## 2. The migration chain cannot rebuild an environment — and the likelier failure is the dangerous one

### 2.1 First blocker — CRITICAL

`0006_guest_cleanup.sql:15` and `0007_audit_log_cleanup.sql:17`:

```sql
create extension if not exists pg_cron with schema extensions;
```

Verified against three independent sources:

| source                                                                                               | what it establishes                                                                                                                                                                                                                     |
| ---------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `pg_cron.control` (upstream)                                                                         | `relocatable = false`, `schema = pg_catalog`                                                                                                                                                                                            |
| [PostgreSQL CREATE EXTENSION docs](https://www.postgresql.org/docs/current/sql-createextension.html) | _"If the extension specifies a `schema` parameter in its control file, then that schema cannot be overridden with a `SCHEMA` clause. Normally, an error will be raised"_ — and `IF NOT EXISTS` suppresses only the already-exists error |
| [supabase/supabase#28261](https://github.com/supabase/supabase/issues/28261)                         | _"pg_cron SQL activation instructions are incorrect"_ — this exact statement is a documented Supabase docs bug; the correct form is `with schema pg_catalog`                                                                            |

The repo copied a statement that was already wrong upstream.

**CI is structurally unable to catch it.** `src/data/progressionCostAuthority.integration.test.ts:47-52` regex-replaces that exact line out before executing the chain.

### 2.2 Second blocker — HIGH

`0014_dead_account_cleanup.sql:46-50` seeds three hard-coded UUIDs into a table whose `profile_id` is `references public.profiles(id)` (`:33-34`). `on conflict (profile_id) do nothing` absorbs a unique conflict; it does nothing for a foreign-key violation (23503).

The repo's own test comments the workaround: _"Fixtures are inserted after this file, because 0014's exempt seed FKs into profiles"_ (`progressionCostAuthority.integration.test.ts:33`). And `20260810170000:58-68` re-seeds the identical rows with the **correct** `where exists (...)` guard and the comment _"A profile that no longer exists is skipped rather than failing the paste."_ The fix was written and never backported to the file that runs first.

### 2.3 The synthesis — which failure you get depends on a condition nobody controls

| pg_cron already installed?                                             | what happens                                                                                                                                                         |
| ---------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **No**                                                                 | `0006:15` errors → the whole file rolls back → **the cron at `0006:38` is never scheduled** → chain halts at file 6 of 28. Nearly empty, but safe.                   |
| **Yes** (dashboard-enabled Supabase project — the common restore path) | `IF NOT EXISTS` short-circuits → 0006 commits → **`cleanup-stale-guest-accounts` is ARMED** with the unhardened body → `0014` aborts → chain halts at file 20 of 28. |

In the second case the armed job is `0006:24-35`: `delete from auth.users where is_anonymous is true and created_at < now() - interval '30 days'` — **age only, no activity test**. The hardening rewrite that adds activity checks and exemptions is file 25 (`20260810160000:60-115`); the disarm is file 28 (`20260811000000:79-81`). Neither applies.

**What the person on the other end experiences**: a guest who has played every day for a month opens the app on day 31 at 03:00 UTC and their account is gone — heroes, gold, gems, friends, history — via `on delete cascade`, with no notice. The repo records `pitr_enabled: false` and an empty backup list (`20260811000000:36-37`). There is no undo.

The out-of-frame observer assembled this consequence chain independently and correctly flagged that it could not verify the pg_cron half; `main` verified it, which moved the observer's answer and made the outcome worse rather than better.

**A related self-falsification**: `20260811000000`'s stated premise is that replaying the chain re-arms _both_ jobs, "not a theory: a seat replayed the chain in PGlite and watched both jobnames come back." A harness where `0014`'s FK insert survives is not the fresh environment the file exists for. The file's central claim is falsified by the chain it was written to protect.

### 3.5 resilience-audit (Heavy, all 3 sections returned)

### 3b.2 Scale — the database, and what actually ships

**CRITICAL — `pvp_rooms` is being used as a 20 Hz tick buffer.** `usePvPRoom.ts:104` runs `setInterval(…, 50)` per client and both clients run it, so a single match drives up to 40 edge-function invocations per second. Each one selects the entire `authoritative_state` jsonb, rewrites the whole blob back onto **one row**, and fires an AFTER-UPDATE trigger that inserts the same blob into `realtime.messages`. Two writers doing compare-and-swap on one row at that rate collide by construction — and the author knew: there is a dedicated `PVP_STATE_VERSION_CONFLICT_RETRY` log path. A hundred concurrent matches is roughly 4,000 heap tuple versions per second for autovacuum to chase, on a table that also never shrinks.

That last clause is its own **HIGH**: the reaper's predicate is `expires_at <= now() and status <> 'completed'`, so completed rooms are excluded — and nothing else ever deletes them. Every finished match leaves a permanent row carrying its full final state blob, and the per-minute job scans all of them forever. It scans, because verified by hand: `pvp_rooms` has exactly one non-primary index, `(host_profile_id, guest_profile_id, status)` — **`expires_at` appears in no index in any position**. A partial index on `expires_at where status <> 'completed'` fixes both halves.

**HIGH — an RLS policy with an index-defeating cast, multiplying against the row above.** `20260809064000:334` compares `room.id::text = substring(realtime.topic() from 5)`. Casting the _column_ means the uuid primary key cannot be used, so each evaluation seq-scans `pvp_rooms` — and this policy runs per row of `realtime.messages`, which receives one row per state commit. The two findings multiply. Casting the other side (`room.id = substring(...)::uuid`) keeps it sargable.

**HIGH — the hottest read path in the app has no usable index.** `battle_history` carries exactly one non-primary index, and it is partial: `(profile_id, external_id) where external_id is not null`. The query is `profile_id = X order by finished_at`, which does not imply that predicate — Postgres decides implication from the query text, not from the fact that the writer always supplies an external id. So: full seq scan plus a sort, with the RLS qual evaluated per row of the whole table, inside `loadPlayer`, which has **13 call sites** — after every gold grant, item grant, gacha pull, upgrade, battle commit, login and guest sign-in. This also reframes an earlier finding: the missing `.limit()` on that select is real, but **adding it changes nothing without the index**, because the scan and sort happen first either way.

And it connects forward: if the disarmed account-deletion crons of §2.3 are ever re-armed, their predicates are correlated `not exists (…battle_history…)` and `(…currency_transactions…)` subqueries against exactly these unindexed columns. The indexes stop being an optimisation and become a prerequisite.

**What actually ships, measured rather than estimated.** The premise this pass was given — that the repository's 488 PNGs ship — was **wrong, and the agent checked instead of accepting it**: all 488 live in `assets/raw/` and `assets/archive/` as build-time sources, and `find dist -name '*.png'` returns zero. Real shipped payload is **14.28 MB across 383 files**, which for a four-character action RPG is reasonable and is not a problem worth manufacturing.

The number nobody had computed is the decoded one. There are **no sprite sheets** — `battleSpriteSequences.ts:76` emits one URL per frame, so one animation frame is one file is one HTTP request. A four-kind battle is **322 requests / 11.97 MB on the wire**, which decodes to **374 MB RGBA8, or 499 MB once three.js generates mipmaps by default**. `battleAssets.ts:22` holds every one of those textures in a module-level `Map` with no eviction and no `dispose()` anywhere; the header calls it "not a memory leak" because the frame _count_ is fixed, which is true of count and not of resident bytes — the cache survives back into the lobby and across every subsequent battle.

**The bundle gate was tested, not reasoned about.** In a scratch copy of the script and a real `dist/assets`: a 41,943,040-byte PNG dropped into `public/` → **exit 0**. The same file placed directly inside `dist/assets` → **exit 0**. Ten synthetic 60 KB-gzip app chunks, +600 KB total → **exit 0, "ผ่านทั้งหมด"**. The filter is `.endsWith('.js')` and no total is ever summed, so no image, font, audio or CSS file can fail this gate by any path. It is correctly wired into CI and into the release path; it simply weighs about 13% of what ships.

One easy win found along the way: `LobbyScene.tsx` renders a `<Canvas>` containing five lights and, per `grep`, **zero meshes** — `SHOW_ARENA_SLOTS` is `false` and the temple art is a CSS background. That empty scene still pulls both Three.js renderer backends, WebGL and WebGPU, for **385.7 KB gzip — 64% of the JavaScript a first-time visitor downloads**. Not mounting the Canvas while the flag is off takes first visit from 1.51 MB to 1.13 MB.

Recorded because it was checked and is fine: the critical/deferred split (room open blocks on 3.34 MB, not 11.97 MB) is the best engineering decision in this audit; `optimize-images.mjs` is a real pipeline with per-directory quality and width caps that measurably bind; audio is exemplary at 80 KB with zero preload; the world-chat _read_ is O(200) at any table size thanks to a correctly matched index — only the client fan-out is a problem; and the cache-hashing gap was already filed in `docs/OPEN-FINDINGS-2026-08-12.md`, so it is not re-filed here.

### 3b.3 Contract drift — the client and server agree

This closes the item the board itself listed as unchecked. Every one of the **17 RPCs matches**: client call sites and current server signatures were laid side by side, with "current" computed by applying migrations in filename order, and no mismatch in arity or type was found.

The 21-argument → 18-argument change that prompted the concern was done correctly — an explicit `drop function if exists` whose type list byte-matches the retired signature, so no stale overload survives — and it is **pinned in CI** by a test asserting exactly one `pg_proc` row across the whole chain. The same discipline had already closed the `grant_item` overload earlier.

What is not enforced is _order_. `git grep supabase` across the workflows returns only environment-variable lines: there is no `supabase db push`, no migration step, no function deploy. The ordering constraints live in SQL comments and prose ledgers. And the 18-argument transition is unsafe in **both** directions while it is in flight — migration-first breaks the shipped client, client-first breaks against the not-yet-migrated server — so the only safe path is deploy-then-paste-immediately, which is what was done. The de facto protection is asymmetry rather than enforcement: the client redeploys automatically on a version bump while SQL waits for a human, so the default drift runs in the safe direction and the risk is a human pasting early.

Three narrower contract gaps: the TypeScript `GoldSource` union still includes `'topup'`, which the current server body raises on — the compiler green-lights a call the database rejects, unreachable today only because the live callers hardcode `'drop'`. `CurrencyTransaction.source` declares four values where the server's CHECK admits eight and actively writes four more. And `commit_lobby_battle_progression`'s `p_flags` jsonb has **no size bound**, while its sibling RPC bounds its own jsonb at 8 KB — and the client appends keys to that object every battle and re-sends the whole accumulated blob on each commit.

**Seven places branch on server-produced strings.** One is deliberate and greppable (`PVP_STATE_VERSION_CONFLICT`, and renaming it silently converts every retry into a 500). Two branch on Postgres's own English error prose via `.includes('duplicate')`, which depends on server `lc_messages` and is declared nowhere. And `pvpAuthorityError.ts` passes the edge function's error body straight to the player's screen — a body that includes raw Postgres exception text, Thai `raise exception` strings included, with no allowlist in between.

**Serialization has no version gate anywhere — and the mechanism that looks like one does not exist.** `PROGRESSION_SCHEMA_VERSION` has zero readers; `ProgressionSaveData.schemaVersion` is a type nothing implements; `progressionVersion` is written as a literal and read by no gate, and it **cannot** persist because no such column exists in any migration. So none of the seven jsonb payloads carries a version, and all seven rely on `??` shape-blindness.

That matters most for `pending_lobby_rewards.dropped_items`, whose entire purpose is to survive a reload or a deploy — that is, to be read by a build other than its writer. It is cast with a null-only fallback and zero element validation; the server checks `jsonb_typeof` and an 8 KB bound but never element keys. A row written before a key rename and read after produces `grant_item(undefined, …)`, the RPC raises, and the pipeline returns its failure **above** the `onClearPending` call — so the row is never cleared and the loop repeats on every lobby entry, forever.

Recorded as already guarded, because it was checked: the localStorage account store has a genuine reader version gate that refuses to overwrite on mismatch, sessions are dropped on both expiry and an app-version change, `Array.isArray` checks guard three fields with a visible report rather than a render crash, the SQL↔TypeScript parity of `item_catalog` and `progression_cost_catalog` is pinned by tests that run in plain `npm run test`, and the edge function is the one place in the repository that genuinely fails fast on missing configuration.

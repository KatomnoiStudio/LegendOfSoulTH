### Audit notes (read before claiming from the tail)

- **Where the value is**: U1–U26 are the load-bearing set — each is either a shipped feature that silently does nothing, a LOCKED-blueprint violation, or a trust-boundary gap. U27–U34 are real but discretionary; several carry an owner-decision component rather than being straightforward fixes, so weigh them, don't queue them. U35–U40 are small and correct but mostly matter later — do them while already inside the file for a higher row (U35/U37 ride with U13, U36/U38 with U29, U39/U40 with U17), not as standalone PRs. U41–U45 are honestly marginal today: two are latent-only defects with no current manifestation. Nothing below U45 was worth writing down — several candidates (boss leash/reset/enrage, the `spawnWaveAt` duplicate-id path, the migration filename-ordering hazard) were dropped in-cluster precisely because nobody could ground them.
- **Cross-cutting themes the audit found.** (1) **Write-only state** — values authored, validated, persisted and tested that no production code ever reads: `activeBuffs`, `aiRole`, `comboWindowStartMs/EndMs`, star/talent/awakening multipliers, `effectEvents`, `defend.position`, `world_chat_messages.author_id`, `softTarget`'s `maxRange`, plus two whole modules (`performGachaPull`, `ascendStar`) with no caller at all. (2) **The graduation ledger certifies itself** — scar tests that mock the module they claim to pin, TASKS.md rows at 100% for loops that do not close, and contracts still describing shipped systems as "not implemented". That is how these shipped behind 811 green tests. (3) **The client is authoritative over values the server commits** — reward amount, item id, level/exp/talent/awakening, and an energy gate stored nowhere at all, so the cost side of the loop is resettable with F5 while the grant side has a durable ledger. (4) **Symmetric mechanisms fixed on one side only** — interrupt resolution wired player-side but not enemy-side, focus-loss guarded on keyboard but not touch, hit-stop on basic attacks but not skills, buffering on the combo but not the skill queue. In nearly every case the machinery already exists and the second call site was never added.
- **Honest coverage gaps.** **Nothing was executed in the 7-cluster pass** — no cluster ran `npm test`, typecheck, lint, or the game; every claim there is static reading, hand-simulation, or grep, and the 811-green baseline was taken on trust. (The 2 backfill agents DID run probes under vitest, which is why U2 and U8 carry measured numbers rather than inferences.) **Not audited at all**: PvP/Ranked (#25), PvP Power Normalization (#26), Monetization/Shop (#28) — Netcode (#27) got only the readiness angle that fell out of World Chat. **Outside every cluster's scope**: the LobbyScene R3F/Three.js/WebGPU layer (context-loss reporting, frame budget, mobile perf), the asset/build/CI/deploy pipeline, bundle size, i18n, PWA/offline, and accessibility beyond U25. **Exemplar grounding is the systematically weakest part** — verified against primary or strong secondary sources: Apple App Store Guideline 3.1.1, Genshin poise/interruption resistance, Genshin normal-attack-into-skill cancelling, HSR ultimate interrupt/queue, HSR in-game-mail compensation, Genshin Resin offline accrual, Summoners War world-chat spam/report. ### Readiness-audit caveats

- **The dedupe check could not be run as designed.** The agents read `TASKS.md` on `master`, where the Upgrade Tasks table does not exist yet — it is on this branch, unmerged. So "does this duplicate a U-row?" was answered from a summary rather than the rows themselves, and the **Relates to** column reflects each agent's own reconciliation, some of it explicitly uncertain. Re-check R6/R7/R14/R15 against U10/U20/U31 once both tables live on `master` together.
- **One R-row disproved a U-row, and that is why U20 now carries a correction.** The power-normalization agent found that star scaling **is** fed into combat as of PR #92 (`createRealtimeBattle.ts:95` calling `statsAtStar`, pinned by `battleVitals.test.ts:102-110`) and that the two star tables are **already collapsed** — `STAR_ASCENSION_TABLE` now derives every `statMultiplier` from `STAR_MULTIPLIERS`, and `StarAscensionSystem` imports `starScaling`'s `statsAtStar`. Both were verified independently before U20 was edited. This is precisely the failure mode the Rebase note above predicted and admitted the mechanical check could not catch: a row whose _reasoning_ was overtaken by later work without any cited filename or identifier changing.
- **Scope honestly not covered**: these four systems have no implementation to audit, so nothing here is a code-quality finding about them — only about what existing code does _to_ them. No agent designed a rating system, matchmaking, a netcode model, or a shop catalog, and any finding that drifted that way was refuted rather than kept.
